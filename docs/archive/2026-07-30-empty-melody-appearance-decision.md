# 詞先で置く「空のメロ」の見た目 — 裁定材料（2026-07-30）

2026-07-30 のオーナー裁定で、詞先の歌詞の置き場は**案(い)＝人が合図して空のメロを置き、そこに書く**に決まった
（代わりに既存メロディなどからのコピー機能を充実させる）。残った枝はひとつ——**その空のメロがネタ帳でどう見えるか**。

きっかけのオーナー発言（原文）：
> ただ、**プレイスホルダー用の空メロディができるのは見た目には微妙ね。ネタ帳からは非アクティブで見えなくする？？ プレイスホルダーのシングルトン的空メロディはなにかが入った瞬間新しいメロディを産むとか？？**

疑問符つき＝思いつきの提示であって決めではない、と読んでいる。だから「言われた2案のどちらか」ではなく、
**何もしない案と、第3の案を足した4案**で material を作った。決めるのはオーナー。

---

## 0. まず事実（実コードで確認した「微妙」の正体）

「空のメロがネタ帳に並ぶと微妙」の中身を実装で特定した。**カードが空白になる**のが実害。

- `apps/web/src/components/MiniRoll.tsx:51`＝**音符が0個なら `null` を返す**（縮小ピアノロールを描かない）。
- ネタ帳のカードは 種別ラベル＋id＋`label`（title か text の先頭）＋ MiniRoll ＋タグ（`NetaList.tsx:300-325`）。
  ＝**音符0個のメロは、絵が丸ごと消えて「種別=メロディ」とだけ書かれた空白のカードになる。**
- 詞先で置いた空メロには**歌詞（句）が入る**が、句は `content.lyric.phrases` にあり、
  カードの `label` は `title`／`text` を見る＝**今のままでは歌詞もカードに出ない。**

＝いま「微妙」なのは *空メロが一覧に存在すること* そのものより、**中身があるのに空っぽに見えること**。

補助の事実：
- **音符0個のネタは尺の計算で1小節と数えられる**（`apps/web/src/sectionContext.ts:81` の `childDur`・`:88` の `contentDur`＝どちらも音符が無ければ `ctx.BPB`）。
  ＝空メロを曲に置くと、その位置の曲の長さがその分ずれる。**これはどの案を選んでも手当てが要る**（design §31-10 スライス5）。
- **一覧の絞り込みに「除外」は無い**（`apps/api/src/schemas.ts:32-48` の `listQueryShape`＝`tags` は含む方向のみ・`scope` は `project|library|all`）。
- `scope` の enum は**閉じていて3用途で共有**（`schemas.ts:6`＝http・mcp・型）。値を足すと `usePlacePicker.ts:85` と `FormStrip.tsx:403` の
  「library のものは置くときに複製する」分岐にも波及する。
- **共有されたメロへの書き込み確認は、ネタ帳から直接開くと出ない**（`apps/web/src/useCowGuard.ts` の `guardAction` 冒頭＝`parentId` が無ければ素通し。
  `parentId` は曲/セクションから潜ったときだけ付く）。

## 1. 案（4つ）

| | 案 | 中身 |
|---|---|---|
| **A** | **何もしない** | 空メロも普通のネタとして一覧に出る。実装ゼロ |
| **B** | **カードの見せ方を直す**（第3の案） | 隠さない。音符0個のメロのカードに**歌詞（句の表記）を出す**。歌詞も音符も無ければ「まだ空」と出す |
| **C** | **一覧から隠す**（オーナー案 (い-a)） | 空メロに「非アクティブ」の状態を持たせ、ネタ帳の既定の一覧から外す |
| **D** | **共有の空メロ1つ**（オーナー案 (い-b)） | プレースホルダー用の空メロは1つだけ存在し、何かが入った瞬間に新しいメロを産む |

## 2. メリット・デメリット・上位との整合

| | メリット | デメリット | 上位（原則・確定）との整合 |
|---|---|---|---|
| **A** 何もしない | 実装ゼロ・仕組みが増えない。空メロも「人が合図して作った実体」なので筋は通る | **カードが空白**＝オーナーが「微妙」と言った状態がそのまま残る。詞先で置くほど空白カードが増える | 原則7（黙って実体を作らない）と整合。**ただし過去裁定「状況が書かれたい。しっかりよくハマってるのか、そもそも歌詞がないメロがないのかなど」に応えていない** |
| **B** 見せ方を直す | 空白カードが消える＝「微妙」の実害が消える。**中身を隠さず見せる**方向なので、あとで隠す案（C）を足す余地も残る。触るのは表示だけ（`MiniRoll`／`NetaList` の label）でデータの形も一覧の仕組みも増えない | 一覧に出る件数は減らない（詞先を多用すると一覧が伸びる）。「歌詞だけのメロ」という見え方に慣れが要る | 原則7と整合。**過去裁定「状況が書かれたい」に正面から応える**。「メロの形は常に矩形（縮小ピアノロール）」の裁定とは衝突しない（音符が無い＝描く矩形が無い場合の話） |
| **C** 一覧から隠す | 一覧が汚れない。オーナーの言葉どおり | **仕組みが1つ増える**（非アクティブという状態と、その出入りの規則）。`scope` 拡張なら enum が3用途共有で波及（`usePlacePicker.ts:85`・`FormStrip.tsx:403`）、タグ方式なら**一覧に「除外」フィルタを新設**する必要がある（今は含む方向しか無い）。**隠したものを人がどう見つけるかを別に作る**羽目になる（隠れたまま二重に作る事故） | 原則7とは無矛盾。ただし「**ゴミが増えるのは嫌なので暗黙の操作はあまり増やさないでほしい**」に対しては、**ゴミを隠す**方向＝ゴミが増えるのを止めてはいない |
| **D** 共有の空メロ1つ | 一覧に空メロが1つしか出ない（並ばない） | **「何かが入った瞬間に新しいメロを産む」＝機械が黙って実体を作る**。産んだメロの命名も要る。さらに `useCowGuard` の穴（ネタ帳から直接開くと確認なしで原本へ書く）を**先に塞がないと、共有の空メロを開いて書いた瞬間に他の作業を壊す**。実装は4案で最重量 | **原則7・過去裁定「実体を明確に作る合図なければ作られたくない」と正面から衝突する。** オーナー自身が置き場の議論では「空のメロディを作る方が無難」と言い、その根拠が「人が合図する」ことだった＝この案はその根拠を自分で外す |

## 3. 推し＝**B（カードの見せ方を直す）**

理由を3つ。

1. **「微妙」の実害はカードの空白**であって、空メロが存在すること自体ではない（§0 の実測）。実害に直接効く。
2. **仕組みを増やさない。** 表示を直すだけで、データの形も一覧の絞り込みも `scope` enum も触らない＝波及ゼロ。
   C は状態と出入り規則、D は暗黙生成と命名とガード修理を新しく背負う。
3. **過去裁定に沿う。**「下書き/確定の色分けは情報ゼロ。代わりに**状況が書かれたい**」に対して、
   B は「この枠には歌詞だけがある」という状況をカードに出す＝裁定そのものの実装になる。

**Dは推さない。** オーナー自身の案だが、置き場を(い)に決めた根拠（人が合図するから原則7に触れない）を、この案が打ち消してしまう。
**Cは急がない。** B を入れたあとで一覧が実際に伸びて困ったら、そのとき足せばよい（B は C の邪魔をしない）。

### B を採る場合にやること（小さい）

- `MiniRoll`：音符0個なら `null` の代わりに**句の表記を1行**返す（あふれは省略）。歌詞も無ければ「まだ空」。
- カードの `label`：メロで title も text も空なら、句の表記を使う。
- どちらも表示だけ＝保存の形は不変（`content.lyric` は既にある）。テストは NetaList／MiniRoll の既存テストに1本ずつ足す。
- **空メロの尺の手当て（`sectionContext.ts:81,88`）はこの裁定と独立に要る**＝スライス5でやる。

## 5. 追記（同日）＝案E が出て、それで決着

上の4案をオーナーに提示（実機CSSのモックで見え比べ＝下の「見え方の材料」）したところ、
**「Bかなあ、いやでも歌詞が入ったり空でなくなったら作る形が望ましそう」** という反応。
これは D（共有の1枚が産む）ではなく**遅延生成**＝第5の案なので、材料を作って比べ直した。

### 案E＝空のうちは実体を作らない（遅延生成）

- 枠は**通しで読む面の中の下書き**（クライアント state・id 無し）。**句を確定した瞬間にメロを作って同時に配置**する。
  書きかけで離れたら下書きは消える＝**空のメロは1件も保存されない**。
- **D との違い**＝D は機械が黙って産む（原則7と衝突）。E は**人が句を書いたことが合図**＝衝突しない。
- **B と競合しない**＝E で消えるのは「合図したが何も書いていない」1枚だけ。**句があって音符が無いメロは E でも必ず生まれる**
  （それが詞先の主役）＝そのカードを読めるようにする B の表示直しは**E でも要る**。
  ＝選択肢は「B か E か」ではなく「**B だけ**」か「**B＋E**」か。
- **制約（実コードで確認）**＝配置は `compose_edge.child_id TEXT NOT NULL REFERENCES neta(id)`（`apps/api/src/db.ts:38`）
  ＝**実体の無い枠は曲に置けない**。ゆえに E は「作成＋配置を1操作」にしかならない。
  引き換え＝**「枠だけ先に並べて構成を眺める」使い方は無くなる**（並べるには何か書く）。
- **いま決める利得**＝通しで読む面も「空メロを置く」操作も**まだ1行も実装されていない**（同日 grep で確認）＝作り直しゼロ。
  さらに**尺の手当ての bit 一致の地雷が構造で消える**＝遅延生成では「音符0個かつ句を持つ」ネタしか生まれないので、
  手当てを `content.lyric` を持つネタに限れば既存の音符0個50件（配置6件・全部 bass＝句なし）は1件も動かない（design §31-10 スライス5）。

### 決着（2026-07-30 オーナー裁定）

> **「なにか書いたらメロが生まれるようにして」**

＝**(い-c) 遅延生成を採用**（＋カードに句を出す表示直し＝上の B は E に内包されて必要）。A・C・D は却下。
要点は design §31-9（決め・却下理由・制約）と §31-10 スライス5（やること・不要になった作業・bit 一致の縛り）へ昇格済み。
