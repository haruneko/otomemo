## 1. 一行要約

ドラム→ベース→ギター/アンサンブル→ピアノの順で「レシピ（掴み＋つまみ＋seed）→ resolve →**演奏の生成**」の縦を通す。
**レシピは生成器**＝ドラムは骨を「描く」（任意＝空ならおまかせ骨・裁定#1）・ベース/コードは「指す」（音符は全部生成物）＝io-map。**ノリは生成物の一面**で、その持ち場は **B1（2026-08-19 裁定済み）＝演奏レイヤー・値は phrase_maker・スコアには焼かない・既定ON非破壊**（詳細§2 B1）。
**フィル等の位置と性格はセクションの合図（cues）**＝案C（2026-08-21 裁定済み）＝レシピは「弾き方」だけ持つ。実装はカスケード S0（型と規則の凍結）→S1（セクション fill 合図）→S2（境界 land）を M0〜M2 に相乗りさせる。
残りのブロッカーは M2 以降を止めるもの。**次の一手は M0＝契約凍結**（スキーマ・resolve 署名（ctx.cues 込み）・RNG ソルト表・feel 層拡張の追補・cues 型と merge 規則）。

## 2. ブロッカー一覧（優先度順）

### B1【裁定済み 2026-08-19・オーナー耳＋コンセプト整合】ノリ（グルーヴ）は演奏レイヤー・値は phrase_maker・スコアには焼かない
- **決着**：グルーヴ（もたり・前ノリ）は otomemo のコンセプト上そもそも**演奏の性質**＝design.md「フィール層分離（2026-07-11・notes 常時ストレート／performative タイミングは非破壊の feel 層）」の管轄。よって**「resolve でノートの start に ms を焼く（＝スコアに持つ）」はコンセプト違反で選択肢から除外**（当初の四択のうち①は無効）。
  - **採る音＝phrase_maker の値**（`timing.py` の `SYS_OFFSET_MS`：snare +14／ghost +8／kick +3／chh・ohh −9／ride −6ms＋ガウス揺れ sd 3.5）。otomemo 既定 `HUMANIZE_PROFILES`（snare +4／hihat +1）より深いノリ＝オーナー耳で GO。
  - **持ち場＝演奏側のデータ**：レシピが「声部別オフセット＋揺れ幅」を**演奏側パラメータとして**抱え、鳴らす瞬間に feel（演奏）レイヤーが**非破壊で**当てる。**resolve が吐くノート／skeleton（キック線）はストレートのまま**（ベースの kickLock も素の格子位置を読む）。
  - **既定 ON**（そうしないと「同じ家族の音」が聴こえない）・ただし **OFF／クオンタイズで素に戻せる**（非破壊）。**揺れ（sd 3.5）も込みで採る**（"良い"の一部）。
- **これで二重掛け問題は実質消える**：当て所が演奏レイヤー一箇所に定まるので、スコア側＋演奏側で二回掛かる経路が生まれない（design 596 の宙吊り＝「rhythm への feel UI は二重掛け審査未了」は、この一本化で解ける見込み）。
- **位置づけの現行化（2026-08-20 io-map）**：B1 はレシピの主目的でなく「生成物の一面（ノリ）」の持ち場の裁定。レシピ本体は生成器＝ハット/ゴースト/フィル/強弱まで演奏全部を生成する（掴み→生成物の対応は io-map の表が正準）。
- **M0 への含意（契約）**：①resolve 出力（ノート・skeleton）は**ストレート**。②ノリは**レシピ由来のパラメータ**として演奏レイヤーへ渡す＝既存 feel 層の語彙を「レシピ駆動の声部別（ghost/クローズ・オープンハット/ride/tom…）」へ**拡張**する。③この一本化を design.md「フィール層分離」の追補として正準化してから M1。
- **残る小論点（2026-08-20 裁定・オーナー）**：
  - (a) **併存＝レシピが勝つ**。基本の演奏アレンジは**既定ON**、レシピが自分の声部別ノリの権威（全体 `HUMANIZE_PROFILES` は非レシピ音のフォールバック）。**加えて「演奏の仕方」を指示できる＝ノリは固定値でなく directable なつまみ**（`recipe.knobs` に演奏方向スロットを切る・実装はM2、M0は枠だけ）。
  - (b) **ノリを当てて出す**。プレビューで流れるのに MIDI に乗らないのは詐欺＝MIDI 書き出しは再生と同じく演奏を適用して出す（内部スコア/ノートは素のまま・書き出しは render 行為）。将来「素で書き出す」トグルは backlog の nicety（今は作らない）。
  - (c) 用語は**提案でいく・問題あれば直す**（暫定＝レシピ側の刻みの粗さ＝「**刻み**」、演奏側のタイミング＝「**ノリ／グルーヴ**」）。

  - **残り（未実装）**：① **物理フィルを実際に鳴らす結線**（`fillNotes`＝絶対qb/GM番号 を web の実レンダ〈Tone.js／MIDI 書き出し〉へ流す）。② **フィルの呼び方＝kind 選択**（どの型をいつ出すか）＝**最小にとどめ固定しない**（利用の中で決まる＝硬化させない）。位置はセクション cue・弾き方はレシピ。③ その他のつまみ蒸留（ゴースト＝レーン分割・押し引き・ハット開閉勾配・熱量）＋小節単位の別案（io-map 裁定#7）＋build/break の楽器別解決（カスケード S3）。

- **Done**：物理フィルが**アプリ本体で実際に鳴る**（cue から呼べる＋cue 無し自動フォールバック・4/4）／他つまみが効く。ゴールデン回帰でスナップショット固定（**耳合格ゲートは置かない**＝下記受け入れ）。
- **受け入れ（2026-08-21 修正・旧A/Bゲートを撤回）**：**忠実度はデータ一致で証明済み＝耳での A/B は不要**（オーナー指摘）。**「辞書より良いか」は今の段階で立てられる評価軸でない**（生成結果は辞書の一エントリのようなもの・優劣は実際の利用の中でしか出ない）。よって受け入れは**「実際の作曲で使えること」**＝物理フィルがアプリで鳴り cue から呼べることを実機/機械で確認するに留める。質・家族性は使用の中で自然に判る＝**抽象 A/B ゲートを置かない**。機械＝ゴールデン回帰（seed＋tempo＋cues 固定）＋bit 一致。
- **契約テスト**：M1 の①〜⑥継続＋フィル小節の骨キック扱い（B2(1)）の裁定結果を仕様化＋（B3 可決なら）テーブル読み込みの決定性。
- **撤退基準（修正）**：フィル移植は忠実（データ一致）＝「家族に聞こえない」型の撤退条件は**無効**。撤退があるとすれば技術的破綻のみ（結線が既存を壊す等）＝その時は既定 grid に留めて M3 へ（レシピは楽器非依存＝後続は死なない）。
- **止めるブロッカー**：B2(1)・B3・B5（M2 冒頭で実音材料→オーナー裁定）。

### M3：ベース
- **Scope**：**掴みは「指す」**＝コード進行（ctx.chords・slashBass 込み）＋役割/スタイル＋ドラムレシピの skeleton（io-map）＝**音符は全部生成物**（「描く口」は将来＝io-map 裁定#2・§7 先送り）。resolve が ctx.chords を消費する最初の楽器（署名は M0 で据え済み）。skeleton（キック線）を読んでルートをキックにロック＝既存 kickLock（design 297）と同型。ドラムレシピ不在時＝既存経路＋仮骨フォールバック可（io-map 裁定#3＝こだわらない）。cue への応答（fill＝該当小節を fill セルへ・land＝bar0 ルート強打）はカスケード §3-1 の表どおり。
- **Done**：ドラムレシピの skeleton を読んで縦が噛み合う（結合をアンサンブルまで先送りしない）。
- **受け入れ**：耳＝ドラム＋ベース 2 声で家族判定。機械＝ゴールデン＋「skeleton 変更→ベース追従」テスト。
- **撤退基準**：M2 と同じ 2 周ルール。既存 gen_bass 据置で凍結可。
- **止めるブロッカー**：なし。

### M4：ギター/アンサンブル
