# phrase_maker の伴奏知識を otomemo に取り込む計画（一案）

以下はすべて「案」であって決定ではない。裁定は §8 の項目を潰しながら各アークの頭で下ろす。

## 0. 目的とスコープ

otomemo の伴奏・アレンジが弱い。phrase_maker（Python 試作・ML なし・ルール/物理で伴奏生成）が獲得した音楽の知識を otomemo に取り込み、**伴奏のバリエーションを増やす**（質の向上はおまけ）。phrase_maker は開発を止めてアーカイブするが、**リポジトリは残す**（いつでも読める）。凍結の際は**未 push コミットを push してから**（gap-fixes に手元だけの分がある＝ローカルが飛ぶと耳合格版の最終形が消える）。

この計画のスコープ＝「どう取り込むか」の段取り・契約・撤退基準の案を出すこと。実装は otomemo 側で進める。

## 1. 大枠の方針（案）

- **翻訳でなく作り直し**。Python を 1 行ずつ移さない。experiments 約 5.7 万行は `gesture_p1〜p14` 等の"作り直しの履歴"で、コード解釈が 4 系統コピー・入力契約が 2 系統（GAP-AUDIT）と構造的に運びにくい。運ぶのは**音楽の知識**（ルール・物理・イディオム・調整値）で、コード自体は参考。
- **単位＝レシピ**。伴奏＝コードが変わっても同じ雰囲気で弾き直す「弾き方」。完成音は保存せず、レシピ（骨＋つまみ＋seed）を保存。otomemo の「コード進行は音を出さない抽象、実音化は resolve 時に毎回」と同じ向き。
- **楽器順＝ドラム → ベース → ギター/アンサンブル → ピアノ（最後）**。安定度（ドラム・ベースは耳 GO 済み、ピアノは決着したて）と規模（ピアノ ~2 万行、他の 6〜9 倍）に合致。
- **蒸留は各アークで都度**。リポが残るので前倒しで全部抜かない。その楽器を作るとき、最良版を読んで知識・調整値・データを取り出す。

## 2. phrase_maker の読み方（蒸留のとき）

中身は**転記せずポインタで持つ**（転記した瞬間から劣化する）。読む場所さえ分かれば蒸留時に正確な値が取れる。

- **最良版はコードで都度確認**：`ensemble.py` / `core/parts.py` のロード先で分かる（例：ピアノは comp と lead で別版＝思い込みで固定しない）。同名モジュールが中身違いで並存する（GAP-AUDIT の G13/G14）ので、蒸留時に耳合格版を特定する。**docs と実装が食い違ったら実装が正**。
- **調整値・実行時データの在り処**：タイミング補正は `drums/gen2/src/timing.py`、最良版と経緯は `HANDOFF-NEXT.md`、既知の穴は `GAP-AUDIT.md`、bodyfill が読むドラマー別テーブルは `data/quarantine/GMD`（出所は同梱 `PROVENANCE.md`）。値そのものはここに書かず、作るときに読む。
- **却下（負の知識）は必要に応じて**。辞書フィル＝わざとらしい、テンポ比例でなく絶対 ms、grammar 表への堕落禁止 等が HANDOFF 群に散在。専用ドキュメントは作らず、袋小路にはまりそうな時に見に行く。
- **耳の見本が要るとき**は phrase_maker でその場でレンダして比べる（リポが残るので焼き置きは不要）。

## 3. 検証（案：耳で合格、機械で回帰）

- **合格判定＝耳**。「同じ家族の音か」＋「自分では作らん感じが残っているか」。判定は `docs/research/` に記録。Python 版と同一出力は目指さない（作り直しだから）。
- **回帰＝機械**。耳合格した瞬間の出力をスナップショットで固め、以後はそこと突き合わせる。ゴールデンは Python でなく「自分の過去の合格出力」。**固定条件は seed だけでなく tempo も含める**（タイミング補正が絶対 ms なら tick 換算が tempo 依存になり、tempo を変えると出力が変わるため）。
- **音源をそろえて A/B**：phrase_maker は fluidsynth＋FluidR3Mono、otomemo は Tone.js。別音源だと「生成の差」と「音源の差」が混じるので、比較は MIDI レベルでそろえて otomemo 側の音源で鳴らす。

## 4. レシピの中身（契約の案・後で覆ると全楽器に響くので先に当てる）

**初日に固定したいのは形の 3 点**（フィールド名まではアーク 0 で確定＝ここでは決め打たない）。当てる前に、受け入れ側 otomemo に既にある形（既存 rhythm content・rng・feel 層）と突き合わせる（§8・§6）。

1. **解決関数の署名**：`resolve(recipe, ctx)`、`ctx = { meter, tempo, bars, key?, chords?, feel?, sectionRole? }`。ドラムは `chords` を無視するが引数の形には最初から入れる（ベース・ピアノで署名を壊さない）。分数コードの低音（slashBass）も型に含める。
2. **互換ルール**：フィールドは足すだけ・未知フィールドは保存時に保持・省略＝既定（既存 relative bass / followChords の additive 前例どおり）。
3. **RNG は役割別サブストリーム**（kick/ghost/fill… を seed から分ける）。新つまみ＝新サブストリーム＝既存レシピの音に触らない。後付け不可（付けた瞬間に全音が変わる）なので初日。既存 `rng.ts`（mulberry32・同一 seed 同一出力）とどう折り合うかはアーク 0 の設計事項。

補足（決め打ちでない）：
- スキーマの姿は例として `{ v, instrument, bone:{cellsPerBar,cells[]}, knobs（省略可）, fills[], seed, engine:{version} }` くらいの粒度。骨は**拍子非依存**に「1 小節あたりのマス数＋マス列」で持つ（`bars = total_beats//4` の 4/4 ハードコードで 6/8 が無音になった phrase_maker の G1/G3 を踏まない）。アーク 0/1 は 4/4 限定と明記する。
- **戻り値は 2 枚重ね**：(a) 既存 rhythm content 形に落ちる実音、(b) 機械可読の骨（kick/snare の拍位置＝skeleton）。(b) は後のベース（ルートをキックにロック）・ギター/ピアノ（隙間刺し）が読む横断の接点。
- **タイミング・微小な揺れは otomemo の feel 層と領分がかぶる**（§8 の裁定待ち）。裁定が出るまで resolve で焼き込まない。
- **engineVersion をレシピに刻む**：エンジン更新で既存レシピの音は変わり得る。ただし黙って変えず、更新時に告知し、気に入らなければ別案で振り直す。旧レゾルバの永久保守は約束しない。

## 5. family の扱い（案・保留だった論点）

- レシピは「ネタとして同じ棚に並ぶ・保存と UI の扱いが同じ」まで。**内部構造は揃えない**（関数境界 `進行+つまみ+seed → イベント列` だけ揃える）。
- 既存 chord_pattern は「型をコードに当てて解決する」方式。レシピを内部構造まで合わせると、phrase_maker の獲得物（物理が生成する）を捨ててテンプレ・スタンパーの焼き直しに堕ちる（phrase_maker がピアノで 2 度失敗した所）。この整理なら「ドラムはコードに解決しない」も自然に収まる。
- **新 kind は増やさない**を第一候補：新 kind 追加は kinds/theme/レーン/MiniRoll/notesForContent… 12〜13 箇所連鎖（design.md 410）。ドラムレシピは rhythm kind の新 content 形が自然。ただし content 拡張か新 kind かはアーク 0 の裁定項目に残す。

## 6. アークと完了・受け入れ・撤退（案）

### アーク 0：レシピを端から端まで通す（最簡ドラム）
- **スコープを絞る**：証明に要るのは骨＋seed＋別案だけ。ノリ/ゴースト/熱量/フィルはスキーマに枠だけ切って既定スタブ＝アーク 1 の仕事。ここを溶かすと判断が機能圧で歪む。
- **完了**：① 骨を描く → rhythm kind のネタとして保存 → 解決で実音化 → セクションで再生、が端から端で通る。② 同じ resolve が apps/api（/gen/section・MIDI 書き出し）からも呼べる（＝アーク 0 の一番の存在意義）。③ 契約テスト：置いた音が必ず鳴る／同一 (recipe, ctx, version) → 同一イベント列／未指定既定＝既存 rhythm ネタと bit 一致。④ 机上確認：スキーマ・互換ルール・skeleton・ピアノ要件（保持/タイ/ペダル/小節跨ぎ）と、**既存 rhythm content の実形（generate.ts）と design.md 記載のずれ**を確認し、どちらに寄せるか裁定して design に載せる。
- **受け入れ**：耳は「壊れていないか」レベル（骨どおり鳴るか・ループ境界）。家族判定はまだ問わない。
- **撤退**：レシピが既存モデルに収まらないと判明したら新 kind 案に切り替えて仕切り直し。

### アーク 1：ドラム本実装
- **完了**：6 項目が効く／フィル（bodyfill 系の物理生成＋着地固定＋別案差し替え）／4/4 で成立。ゴースト・押し・ハット開閉・逆算フィルを調整値付きで蒸留し TS 化。
- **受け入れ**：固定バッテリー（進行 3 種 × テンポ 3 種 × seed 数個）を phrase_maker のその場レンダ（otomemo 音源）と並べて聴く。「同じ家族か」＋「手癖脱出が残るか」。記録は `docs/research/`。
- **撤退**：2 周作り直して家族に聞こえないなら、原因を「定数の移し漏れ／理解漏れ」に切り分けて 3 周目。それでもダメなら既存 gen_drums 据置＋レシピは骨・フィル旗だけの薄い形で凍結しベースへ（レシピは楽器非依存なので後続は死なない）。
- **既知の未達**：三連フィル（bodyfill の 0.25 格子に三連スロット無し・実フィルの 35% が三連）。直すか既知の限界とするか spec に書く。

### アーク 2 以降：ベース／ギター・アンサンブル／ピアノ
- 完了に必ず「skeleton（キック線）を読んで縦が噛み合う」を含める（結合をアンサンブルまで先送りしない）。ベース＝ルートをキックにロック（既存 kickLock と同型）。
- **ピアノは移植でなく半分新規 R&D**（fingersim は初合格・反復中）。工数見積りは別枠。難所は進行解決でなく「多声 × 両手 × 保持 × ペダル × 小節跨ぎ」。

## 7. プラン B（撤退先・捨てない）

作り直しが難航したときの逃げ道＝Python をサーバーで仮住まいさせる（8/13 時点の旧案）。特にピアノで価値がある。**判断時点＝ピアノのアーク頭で工数を見積り直し、そこで作り直し続行か仮住まいか決める**。アーク 1 の撤退基準（2 周ルール）ともつなぐ。

## 8. まだ決める裁定項目（spec を書く前に）

- **【最重要】feel 層との重なり**：otomemo には「スイング・微小タイミングは非破壊の feel 層」という確定済み正典（design.md「フィール層分離・2026-07-11」＋ music-core に部位別 humanizeProfile 実装）がある。phrase_maker の声部別タイミング（絶対 ms）は同じ領分。resolve で実音に焼くか・feel 層を拡張するか（**二重掛け防止**）。アーク 0 の契約に響くので早い。
- **生成の置き場**：現状の分業どおり apps/api を推す（クライアント生成は otomemo の常時オンライン前提と逆行するので追わない）。ここも一応の案。
- **フィルの矛盾 2 つ**：(1) フィル小節に骨のキックがあったら＝骨停止か・骨保持＋フィル追加か。(2) セクション最終小節のフィルは着地がセクション外＝次セクション頭に鳴らす/鳴らさない/着地省略のどれか。
- **「レシピは足すだけ」の二義**：(a) スキーマ進化が additive、(b) 生成が指定を消さない。両方採るなら両方明記。(b) は「熱量＝静か」でも置いたキックは鳴るまで具体化。
- **GMD 由来テーブルを持ち込むなら出所表記の置き場**（CC BY 4.0＝商用可だが要クレジット）。そもそも持ち込むかも含めて。
- **既存 gen_drums との終着**：レシピが型ライブラリを将来吸収するか併存か。
- **用語の書き分け**：レシピの「ノリ」＝刻みの粗さ vs 既存 feel 層の「ノリ」＝タイミングの揺れ。別物なので design で書き分け。
- **熱量 × sectionRole**：frame.section の role→ノブのプリセット（energy あり）と、レシピの熱量の関係。
- **別案の後戻り**：seed 振り直しで前案は消える。seed 履歴を持つか「戻れない」と明記するか。
