## 全体構成（#1・暫定確定）
- 常時起動の箱 K8-Plus = サーバー：データ（DB＋ファイル）、非同期ワーカー（投げて→進めて→受け取る）、情報収集の常駐、API。
- クライアント = ブラウザ／PWA：スマホ（出先）・PC（家）から同じサーバーを見る。
- 到達（決定 2026-06-21・`docs/deploy.md`）：**Tailscale tailnet 限定**。WSL2(mirrored)で Tailscale IF(100.x)が見えるので api を **その IP にバインド**(`CM_HOST`)＝LAN/ネットに出さず自分の端末だけ到達。アプリ側パスワード無し(ネット層が境界)。LAN直は `CM_HOST=0.0.0.0`。
- 端のローカル橋渡し：ABILITY 登録など、Web の外の薄い助っ人（家／EVO-X2 側）。

## AIの実行先（#1・方針確定／2026-06-24 是正＝MCP＋Claudeクライアント）
- **会話・司令塔**（何を・どんな雰囲気で・どのツールを呼ぶか） → **Claude クライアントそのもの**（Claude Code CLI を `claude -p --resume --output-format stream-json` で・Max認証）。**プロンプト組み立て・判別ルーティング・エージェントループは自作しない**＝Claude が記憶・多ターン・ツール選択をネイティブに担う。
- **作曲ドメイン能力** → **creative-manager MCP（TS・api 内 `apps/api/src/mcp.ts`）**：ネタ/合成の読取・**ルールエンジンによる生成(gen_*)**・当てはまり判定(analyze_fit)・書込(候補返し＋明示commit＝承認が効く)。どの MCP クライアントからでも叩ける宣言的な面。**音楽的妥当性の真実源はここ**（requirements #92/#151＝AIは引く/選ぶ/直す、根拠なきものは作らない）。
- **会話の場** → web アプリ内の**薄いチャットラッパー**：Claude セッションを中継し `tool_use`/`tool_result` を既存の視覚部品（ピアノロール/再生/選択カード）として描くビュー層（脳なし）。
- **画面が直接使う口も同じ格で置く（2026-07-29 追記・オーナー未レビュー）**：会話を通さず画面が使うもの（歌詞の読み・高低・モーラ、当てはまりの印、仮歌）は、api の普通の口（HTTP）から使える。**中身は1つだけ持ち、入口を2つにする**（MCP＝会話から／HTTP＝画面から）。理由＝作詞の推敲は会話ではなく画面を開いた時点で出ていてほしいもので、会話を挟むと体験原則6（摩擦・待ち時間ゼロ）に反する。現状は歌詞系の口が MCP にしか無く、画面は9語だけの内蔵辞書で代用している。
- **日本語の読み取り（読み・アクセント・句の切れ目）→ K8-Plus の Python（pyopenjtalk・`apps/audio/accent.py`）**（同・オーナー未レビュー）。api が必要なときに起動して結果をもらう（常駐しない）。**呼び出しは1句ずつではなく、まとめて一度に渡す**（実測：1句ごとに呼ぶと40句で5.8秒／まとめて渡せば40句149ミリ秒。1回あたりのほとんどが Python の起動と辞書の読み込み。`docs/research/2026-07-29-lyric-assist-design-settled.md` §4）。
- mp3 解析・埋め込み（意味検索） → **K8-Plus（ローカル、軽い）**／DAW(ABILITY) → **EVO-X2（家側。必要なら補助で手元 LLM）**。
- **是正の経緯**：旧実装は worker(Python) が `claude -p` を**ステートレス単発JSON API**として使い、intentごとに手組みプロンプト→判別ユニオンを返す**ルーター**だった（＝worker が脳をホスト＝「LLM差し替え可能」設計だが Claude の会話力を捨て「会話が返らない」）。→ **脳は作らず Claude クライアントに任せ、ドメインは MCP に集約**へ転換。worker は AI プロンプトを持たない（決定: design #100）。
- 前提：未発表物を他人から見える所に置かない。Claude 等の外部利用は可（tailnet 境界）。

## データの持ち方（#2・確定＝実装済）
- すべては「ネタ」。ネタは入れ子にできる（くっつけて新しいネタになる）。
- 最小単位のネタ：メロディ／コード／リズム／歌詞／その他。
  - **歌詞の持ち方（2026-07-29 追記・オーナー未レビュー）**：歌詞には2つの姿がある。(1) **人が書いたそのままの文章（漢字仮名交じり）＝これが元**。(2) **そこから導かれるかな（仮歌用）と、音符への割付**。(2) は保存してよいが、(1) と人の手直しから作り直せるものとして扱う。かな書きは歌詞の書き方ではなく、鳴らすために導かれる姿（requirements「歌詞を書く」）。曲の中に位置を持つ歌詞は**独立した実体にせず、ネタの中の層**として持つ（`Note.syllable` は音符に載る仮歌用の写しであって歌詞の本体ではない）。**ただし「歌詞のネタが無くなる」という意味ではない**（2026-07-29 監査で補足）：曲もセクションも無い思いつきは今までどおり `kind:"lyric"` のネタとして置ける＝次項。
  - **人の手直しが機械の読み取りより上（同）**：機械が読み・高低・句の切れ目を取り違えたときに人が直したものを保存し、機械が読み直しても消さない。作詞で機械が出すのは**間違いに気づくための材料**であって良し悪しの裁きではない（点数を付けない）。＝上の「音楽的妥当性の真実源は MCP」は音符の話であり、日本語の読みには伸ばさない。
  - **どこにも属さない歌詞がある（同）**：曲もセクションもまだ無い思いつきは、素材のまま置ける（今のネタ帳と同じ）。曲の中に位置を持つ歌詞と、置いてあるだけの歌詞は別物として扱う。
- 組み合わせると大きいネタになる：コード（複数）→ コード進行、メロ＋コード＋リズム → 断片、…→ 曲。
- 「曲」もネタの延長（いちばん大きい組み合わせ）。ただし曲は箱として独立して持つ（段階・次の一手などプロジェクト情報を載せるため）。
- **プロジェクト＝曲(箱)の上位の器**（作業中の一曲 or 組曲）。1プロジェクトに曲は 1..N（組曲）。プロジェクトは曲ツリーに加えて、取り込んだファイル(asset)と AI会話セッション(chat thread)も束ねる＝「一箇所に集まって辿れる」器（requirements「一曲（または組曲）の器にまとめる」）。実体は `prj:` 名前空間タグ（design「複数プロジェクト」）。階層＝Project ⊃ Song(1..N) ⊃ section ⊃ leaf。**ただし「leaf は必ず section の下にある」という意味ではない**（2026-07-29 追記・オーナー未レビュー）。詞が先に書かれた場所にはまだメロもセクションも無いことがある。その歌詞の置き場は**案(い)＝人が合図して空のメロを置き、そこに書く、で確定（2026-07-30 オーナー裁定・requirements「作詞まわりの未決」1）**＝歌詞は常にメロの層にあり、曲・セクションは歌詞を持たない。その代わり既存メロディなどからのコピー機能を充実させる。**空のメロを保存する瞬間は「人が句を書いて確定したとき」＝(い-c) 遅延生成で確定（2026-07-30 オーナー裁定）**＝空のうちは実体を作らない（下の「黙って実体を作らない」の受け＝書く行為そのものが合図）。詳細＝design §31-9。
- **黙って実体を作らない（2026-07-29 追記・オーナー未レビュー＝体験原則7の受け）**：曲・セクション・メロを、人の合図なしにデータとして作らない。既存の中身を機械が書き換える場合（例＝歌詞を流し込むと音符が自動で割れる＝`apps/api/src/lyric.ts`）が、これに触れるかどうかは design で裁定する。
- 資産ファイル（歌詞テキスト／MIDI／mp3／画像）は「ソース」。可能なら分解して、メロ／コード進行／リズム等のネタを取り出し、元ソースに紐づける。
  - 注：MIDI/ABILITY は分解しやすい（既に記号）。mp3 はキー/BPM/雰囲気（＋できればコード推定）どまりで、メロの完全復元は狙わない（要件メモの方針と整合）。

## 技術選定（#3・確定）
- メインのバックエンド＋フロント：**TypeScript**。フロントは **React（PWA）**。
- 推論・解析・MIDIワーカー：**Python**（ジョブキュー越しに隔離。日常触る面はTS、Pythonは滅多に触らない安定サービスに追いやる）。
- API/Webサーバー：TS（Node。フレームワークは Fastify 等、細部はあとで）。
- DB：**SQLite（＋sqlite-vec）**。1ファイルで永続＝バックアップ簡単。WALで TS API と Python ワーカーから利用（またはワーカーはAPI経由）。規模（数千〜数万件）的にベクトル検索はブルートフォースで十分。検索精度は埋め込みの作り方が本丸（#6）。
- 非同期ジョブ：SQLite上のジョブ表＋**api(TS)内のコンシューマ**＋スケジューラ（Redis等の追加インフラ無し）。※旧 Python ワーカーは 2026-07-05 撤去＝生成/研究/取込は api が消化。
- 音：**Tone.js**（中核：テンポ/小節/スケジューリング/シンセ）＋ smplr/SoundFont（音色）＋ **@tonejs/midi**（MIDI入出力＝ABILITY書き出しも担う）。
- **仮歌（歌わせる）＝VOICEVOX の歌声エンジン**（2026-07-29 追記・オーナー未レビュー。実装は 2026-07-15 から稼働）。api が音符とかなを渡して wav を作り、資産として残す（`apps/api/src/sing.ts`）。**独立したプロセス**で、api が必要になった時点で起動する（既定 127.0.0.1:50121・`CM_VOICEVOX_DIR`/`CM_VOICEVOX_PORT`/`CM_VOICEVOX_URL` で差し替え）。**systemd には登録していない**＝箱を再起動した直後の1回目だけ立ち上げ待ちが入る。常駐にするかは未決（下記）。
- 楽譜表示：**VexFlow / OpenSheetMusicDisplay**（"できれば"が現実的。楽譜"入力"は別途重い）。
- 配置（実態 2026-06-23・アーキ是正S2/S4後）：K8-Plus の **WSL2(mirrored) 上で tsx/uv 起動**（Docker 不使用）。**常駐は2プロセス**（＋dev の vite）：api(:8787 単一オリジン＝web も配信／**音楽ドメインTS＝`/music`**／**creative-manager MCP の宿主**／**会話＝`claude -p` セッションを中継する薄いラッパー endpoint→web に SSE**／**ジョブ消化＝生成(決定的 `/gen/section`)・継続調査(`research-runner.ts`＝`claude -p` 一発)・MIDI取込(`midi-import.ts`＝@tonejs/midi)**)／cm-search(:8788 意味検索・Python＝`apps/worker/` の venv で動く)。**常駐しない Python とプロセスが別に2つある（2026-07-29 訂正・オーナー未レビュー）**：(a) **`apps/audio/` の Python**（専用 venv `apps/audio/.venv`。日本語の読み取り＝`accent.py`／mp3 解析＝`analyze.py`。api が必要なときに spawn して結果をもらう＝`apps/api/src/accent.ts`・`audio-analyze.ts`）、(b) **歌声エンジン**（上記・api が spawn）。＝旧記述の「**2プロセス**」「cm-search＝**残る唯一のPython**」は実態と違っていたので直した。systemd で自動起動するのは cm-api / cm-search / cm-backup.timer の3つだけで、(a)(b) は含まれない（`deploy/systemd/`）。なお `apps/worker/` ディレクトリは残っており、そこが今の cm-search の住所（`cm-search.service` の WorkingDirectory）＝撤去されたのはジョブ消化の役目であってディレクトリではない。**cm-worker(旧ジョブワーカー)は撤去済(2026-07-05・worker脑撤去完了)**＝claude も job 消化も api(TS)へ。cm-music-mcp(:8790) も S2 で廃止。外は Tailscale serve/IP で tailnet 限定。**自動起動＝systemd 導入済（2026-07-07）**：`deploy/systemd/install.sh` で cm-api/cm-search/cm-backup.timer を `--user` enable＋linger 設定（再起動・ログアウトでも生存。cm-worker ユニットは撤去に伴い剪定済＝backlog D8/D9 参照）。手動起動（`pnpm --filter ./apps/api start` 等）は開発時のみ。

## 解決済み（旧「未決・要調査」）

- 歌詞のモーラ分析（#13）→ **かな書きの範囲でのみ実装済み**（web `lyrics.ts` / api `lyric.ts` の `splitMora`。旧 worker `split_mora` は撤去済）。**漢字仮名交じりには対応していない**＝漢字1字を1音として数える（実測：「雨の日は」を4＝正しくは5）。歌詞の本体が漢字仮名交じりだと決まったため（requirements「歌詞を書く」）、**ここは未決へ差し戻す**（下記「未決・要調査」／2026-07-29 訂正・オーナー未レビュー）。

## 未決・要調査（2026-07-29 復活・⚠ オーナー未レビュー）

L5 は「未決は『未決・要調査』に置く」と書いているのに、その節が無くなっていた（「解決済み」に置き換わっていた）ので作り直す。

- **漢字仮名交じりから、読み・かな・モーラを起こす経路**。仕組みは `apps/audio/accent.py`（pyopenjtalk）側にあるが、表記からかなを返す形になっていない（今はローマ字の音素しか返さない）。画面から届く口も無い。
- **詞先の歌詞をどこが持つか**（requirements「作詞まわりの未決」1）。**現在は案(い)（空のメロを人が置いて書く）を仮置き**。階層の記述はこれを先に決めない。
- **人が直した読み・高低・句の切れ目をどこに置くか**。置き場が今はどこにも無い。
- **歌声エンジンを常駐にするか**。要件「いつ開いても使える状態」との兼ね合い。今は箱の再起動後の1回目だけ立ち上げ待ちが入る。
- **読み取りの呼び出しをまとめる形**。Python 側はまとめ受けに対応済みで、api 側が使っていないだけ（`apps/api/src/accent.ts`）。常駐させるほどの必要はない（まとめれば足りることを実測済み）。
