# 演奏レシピの持ち場 — 作曲プロセスの高度分解から決める（一案）

## 0. 問い

きっかけ＝オーナーの気づき：**ドラムのフィルはパターン単体では位置が決まらない**。位置は編曲の都合（曲の構造・セクション境界・次に何が来るか＝サビ前の8小節目 等）で決まる。だから「フィルマーカーをドラムレシピ（トラックの掴み）に保存する」（[入出力対応表](2026-08-20-phrasemaker-recipe-io-map.md) 裁定#6）は破綻の芽を含む。これはドラムに限らない（ベースの駆け上がり・コードのビルドも同じ）。では「演奏の詳細はセクションが持ち、トラックはリズムパターンくらい」に倒すべきか？——倒すと**セクションが神オブジェクト化**（全楽器の演奏詳細を抱える）する懸念がある。この綱引きに一つの解を出す。

順序＝(1) 作曲プロセスを高度で分解 →(2) その分解を土台に持ち場を決める。

## 1. 作曲プロセスの分解（決定 × 高度 × 頻度）

「高度」＝曲全体／セクション／トラック／音符・演奏の4段。「頻度」＝その決定がいつ・何回下されるか。右列＝otomemo に既にある住所（実 doc/実装で裏取り）。

| 決定 | 高度 | 頻度・タイミング | otomemo の現住所 |
|---|---|---|---|
| フォーム（セクション列・A→B→サビ…） | 曲全体 | 曲で1回（後から改訂あり） | song の children 順・suggest_form（提案のみ） |
| キー計画・転調 | 曲全体 | 曲で1回 | keyPlan / suggest_key_plan |
| テンポ・拍子 | 曲全体 | 曲で1回（途中変更は例外） | frame |
| エネルギー曲線（山谷・落ちサビ→ラスサビ） | 曲全体 | 曲で1回・改訂あり | suggest_energy_plan（提案のみ・Δ=前セクション比） |
| 編成（どの楽器がいるか） | 曲全体 | 曲で1回 | レーン（トラック）の存在そのもの |
| セクションの役割（verse/chorus…） | セクション | セクション作成時に1回 | `role:` タグ（prev/next は song の並びから導出＝保存しない） |
| コード進行 | セクション | セクションごと | コードレーン（section の子） |
| レイヤー抜き差し（このセクションで誰が弾くか） | セクション | セクションごと | layerAdd/Drop（energy plan の提案）＋レーンへの配置 |
| セクションのエネルギー水準 | セクション | セクションごと | frame.section.energy（提案止まり） |
| **境界イベント＝フィル・ビルド・ブレイク・キメ・受け渡し** | **セクション（＋曲の並び）** | **セクションごと・「次に何が来るか」に依存** | 現状は genDrums/genBass の fill ノブ（bars-2 固定）＝**トラック生成の内部に埋没** |
| 楽器の弾き方の語彙（8ビートルート・オクターブ奏法・コンピング型・骨格子） | トラック | 曲で1回〜セクション役割ごと | style 型ID・レシピの骨（bone）＋つまみ |
| その奏者のノリ（声部別オフセット・揺れ） | トラック | 曲で1回（奏者の癖） | content.feel / recipe.groove（M0契約） |
| 実音・ボイシング・微小タイミング・フィルの実際の音 | 音符・演奏 | resolve/再生のたび（決定的・seed） | resolve ＋ feel 層（非破壊適用） |

### 編曲都合のものの帰属（この表の芯）

フィル・駆け上がり・ビルド・ブレイク・キメ・アンサンブルの受け渡しは、実は**1つの決定ではなく3つの決定の束**：

- **(a) どこで**（着地小節＝サビ前の8小節目）＝**セクション境界の高度**。次のセクションが何かを知らないと決められない＝セクション単体でも決まらず「セクション＋曲の並び」で決まる。
- **(b) どんな性格で**（強さ・狙い＝派手/控えめ・上昇/下降）＝**セクション寄り**（エネルギー設計の一部）。
- **(c) どう弾くか**（タム回しの語彙・打撃経済の物理・駆け上がりの音使い）＝**トラック（奏者）の高度**。

phrase_maker はこの分離を既にやっていた：`Chart.fill_marks`（着地小節＋強さ＝(a)(b)）は **Chart＝「全パートが読む共有オブジェクト」の属性**で、フィルの中身（(c)）は bodyfill（打撃経済DP）が生成する。フィル位置はドラムパート内のデータではなかった。

タイミングの含意：実務では境界イベントは**セクションが並んでから**決まる（「ここがサビ前」と分かって初めて8小節目にフィルを置く）。フォームを改訂（Bメロ挿入・サビ繰り返し追加）したらフィル位置は**自動で動くべき**もの＝トラックのデータに焼くと改訂のたびに腐る。

## 2. 持ち場の3案

| 案 | 中身 | メリット | デメリット |
|---|---|---|---|
| **A. トラックのみ**（現裁定#6） | フィルマーカー等をレシピに保存 | ネタが自己完結・ライブラリ単独試聴が成立・セクションのスキーマ不変 | 位置がレシピの小節番号に焼かれる＝**長さや文脈が違うセクションで再利用すると位置が腐る**／nextRole を知れない／同じ編曲情報を全トラックに重複記入＝ズレる（ドラムだけフィルしてベースが棒立ち）／フォーム改訂に追従しない |
| **B. セクションのみ** | セクションが全トラックの演奏詳細（フィルの中身まで）を持つ | 編曲情報が一箇所・アンサンブル同期が構造で保証 | **神オブジェクト化**＝楽器別スキーマがセクションに増殖／レシピネタが骨抜き＝ライブラリで再利用する単位が消える／「content は人が仕上げる単位」（design 統一原理）に反する／楽器を1つ足すたびセクションのスキーマが動く |
| **C. 分担（推奨）** | トラック＝**弾き方の語彙**（骨・つまみ・groove・フィルの弾き方）。セクション＝**薄い指揮**＝編曲キュー（位置＋性格のみ・楽器非依存）。resolve(recipe, ctx) が合成（ctx にキューが乗る） | 位置は編曲側で1回だけ決まり全トラックが同期／レシピは文脈非依存で再利用可能／セクションは数フィールドのまま | resolve の ctx が1項目増える／「キューにどう応えるか」の設計が要る（→§4） |

## 3. フィル位置問題の解（案Cの具体形）

- **セクションが持つのは「合図」だけ**：`cues: [{bar, kind: "fill"|"build"|"break"|"kime", intensity?, aim?}]` 程度の1配列。bar はセクション相対。
- **セクション末フィルの着地がセクション外に出る問題**（[移植計画](2026-08-19-phrasemaker-port-plan.md) §8 の未決「着地が次セクション頭」）は、この高度なら自然に解ける：着地＝次セクション頭は **song の並びから導出**（prevRole/nextRole を保存せず導出する既存前例と同型）。トラック高度では原理的に解けない（次を知らない）。
- **合図が無いとき＝自動シーム**：phrase_maker の auto seams（fill_marks が None なら小節境界から自動配置）と、現行 genDrums fill の「bars-2 既定」がそのまま前例。ライブラリでのレシピ単独試聴もこれで成立（裁定#3「レシピ不在時は仮骨」と同じ型の防御）。

## 4. セクション神化の回避＝責務の線引き

**セクションが持ってよいもの**（薄い指揮）：
- 楽器非依存・小節粒度・数個の合図（cues 1配列）＋既にある role・energy。それだけ。

**セクションが持ってはいけないもの**：
- 楽器別の音符・楽器別のスキーマ・レシピ本体・フィルの中身。楽器が増えてもセクションのスキーマは1バイトも動かないこと＝神化していない判定基準。

**トラックの自律**：
- 合図は**命令でなく合図**（バンドで首を振って「次サビ！」と伝えるのと同じ）。各奏者＝レシピが**自分の語彙で解釈**する：ドラムは bodyfill・ベースは駆け上がり（FL-*）・コードはクレッシェンド/上行ボイシング。合図に乗らない自由もレシピ側のつまみ（例 `respondToCues` 既定ON）。
- 「置いた意図は生成が消さない」原則との整合：合図は音を**足す/変える方向**にだけ働き、骨で置いた音は消さない。

**合成点＝resolve**：
- `resolve(recipe, ctx)` の ctx（[M0契約](2026-08-20-phrasemaker-M0-contract.md)＝`{meter, tempo, bars, key?, chords?, sectionRole?, slashBass?}`）に `cues?` を1項目足すだけ（additive・sectionRole と同じ席）。実音はレシピ（語彙）×ctx（指揮）の合成として毎回生成＝どちらにも完成音は住まない。

**物理的置き場**：
- section ネタの content に additive フィールド（content は `z.unknown()` 素通し＝DB スキーマ変更不要・新 kind 不要）。resolve 呼び出し時に ctx.cues として注入。

**情報の流れの対称性**（設計を覚えやすくする整理）：
- **skeleton＝下から上**（ドラムの骨→ベース/コードが読む・ボトムアップの噛み合い）。
- **cues＝上から下**（セクション→全トラックが読む・トップダウンの指揮）。
- どちらも「薄い横断契約」であってデータの塊ではない。この2本で縦（アンサンブル）と横（構成）が噛む。

## 5. 全楽器で成立するか

成立する。ドラムのフィル＝ベースの駆け上がり＝コードのビルドは**同じ (a)(b)(c) 分解**に乗る：位置と性格は共通（同じ小節で盛り上がる）・弾き方だけ楽器ごと。1つの cue を各楽器が自分の語彙で解決する形は「1回描けばバンド全員が噛む」（skeleton の設計思想）の指揮版。

実装側の傍証：現行 genDrums fill も genBass fill も「**末尾の1つ手前の小節（bars-2）**」という同じ位置規則を**別々にハードコード**している（design.md WP-D1/WP-B1）。同じ知識の重複＝その知識がトラックの外（上の高度）にある証拠。

例外の芽＝**キメ**だけは位置＋「どの縦を打つか」（リズム型）まで指揮が要る。cue にリズム格子を1本持たせる拡張で吸収できる（additive・後段）。初期は fill/build/break の3種でも成立。

## 6. 既存前例との整合

- **セクション共有 feel**（design.md 306）＝`POST /gen/section` が同一 feel を全生成器へ**配る**が、**保存は各トラックの content.feel**。＝「セクションは配り役・データは薄く・実体はトラック」という案Cと同じ形が既に本番にある。
- **frame.section**（role/energy/prevRole/nextRole）＝セクション文脈をトラック生成へ渡す既存チャンネル。ctx.sectionRole は M0 契約に既に載っている＝cues は**同じ席に座るだけ**。
- **phrase_maker**＝fill_marks は Chart（共有譜面）の属性・auto seams はセクション長（fill_section_bars）と大境界（cyc_bars）から導出＝**本家も位置は編曲情報として持っていた**。案Cは移植元の構造とも一致する。

## 7. 裁定#6 の見直し（このdocの帰結）

- 旧：フィルマーカーは**掴み＝レシピ保存対象**（「この範囲にフィル」の構成意図を残す）。
- 新提案：**位置と性格（どこ・どれくらい）はセクションの cue へ**。レシピに残るのは「フィルの弾き方」（語彙・応答つまみ・フィル量の既定）だけ。
- #6 の狙いだった「構成意図を保存する」は生きる＝**保存する場所がセクションに変わるだけ**。むしろ意図の寿命が正しくなる（フォーム改訂に追従・レシピ再利用で腐らない）。
- M0 契約への影響＝ctx に `cues?` を足す（additive）・Recipe v1 の `fills?: Fill[]` 枠は「弾き方の既定」の意味に読み替え（フィールド名はアーク0で確定）。

## 8. オーナー裁定（2026-08-21 決着＝案C採用・6点すべて採用）

**案C（分担）で確定**：セクション＝楽器非依存の薄い合図（位置＋性格）／トラック＝弾き方の語彙／resolve が合成。神化回避＝「楽器が増えてもセクションのスキーマが1バイトも動かない」。以下6点すべて採用：

1. #6改訂＝フィルの位置と強さはセクションの合図へ移す
2. 合図の語彙＝fill/build/break（キメは後段）で開始
3. 置き場＝section ネタ content に additive フィールド
4. セクション末フィルの着地音＝次セクション頭に鳴らす
5. 合図なしの単独試聴＝末尾に自動フィルで代用する
6. 応答つまみ（合図に乗る/乗らない）を初期から持つか
