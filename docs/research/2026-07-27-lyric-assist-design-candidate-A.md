# 作詞補助ツール 白紙設計案A（独立導出）

- 日付: 2026-07-27
- 位置づけ: 要求文書（`2026-07-26-lyric-assist-requirements-draft.md`）のみを入力とした独立導出。他の設計案・アプリコードは非開示。1つの提案＝材料。物差しはオーナー。

---

## 1. この設計の芯

**「穴の見える歌詞全体を常に開いたまま、選んだ穴を、意味の側からでも音の側からでも埋めていける道具」。**

導出の根拠：

- C-5「穴を埋める作業を中心に据える」＋ C-8「現状の歌詞全体が穴も含めて見えること」＋ D-3「ほぼ空の状態でも成立する場」。この3つを重ねると、**ホーム画面＝歌詞全体の一覧（穴つき）**が自然に出る。推敲のときだけ開く俯瞰ではなく、曲の最初から最後までここに居る。
- B-9「次にどの穴を埋めるかを選ぶ段階」が独立のユースケースとして挙がっている。つまりこの道具の作業ループは「全体を見る → 穴を選ぶ → 穴の中で作業する → 全体に戻る」の反復であり、画面構成もこのループに一致させるのが素直だと判断した。
- C-1 の往復（曲先/詞先）は「曲全体のモード」ではなく「穴ごとの、その瞬間の入り方」として実現する。詞から入るか音から入るかは穴ごとに違ってよく、道具はどちらも同じ扱いで受ける。

## 2. 画面/機能の構成

画面は実質2枚＋表示切替1つ。スマホ基準（C-2）なので枚数を絞った。

| 画面/機能 | 役割 |
|---|---|
| (0) 曲一覧 | 入口。曲を選ぶだけの薄い画面。 |
| (1) 歌詞全体画面（ホーム） | 現状の歌詞全体を、穴の所在・粒度・どちら側が欠けているかも含めて縦に一覧する。曲を開いたら常にここ。穴を選んで (2) へ。 |
| (1a) 推敲表示（(1) の表示切替） | 同じ歌詞全体の上に、音韻の注記とイントネーションの注記を重ねる切替。別画面にはしない。 |
| (2) 穴の作業画面 | 選んだ1つの穴に集中する画面。前後の固定情報（詞・メロ）を見せた上で、直接入力・条件を付けた候補探し・メロ側の作業を行う。 |
| (2a) 候補探し（(2) 内の機能） | 意味・音数・アクセント・語尾などの条件を任意の組合せで与え、条件を満たす言い方/旋律の候補一覧を得る。 |

デスクトップは**同じ2枚を左右2ペインに並べる**（左＝歌詞全体、右＝作業画面）。C-2 が「画面の構成が2つになることは許容」としているのはここで使う。機能差は付けない。仕上げはDAWで行う（C-2 の理由）ので、この道具にデスクトップ専用の重い工程は置かない。

### データの見せ方（構造の要点）

- 1曲 ＝ **セクションの並び**（A/Bメロ等。名前と順序を持つ。C-12）。
- 各セクションの中は、**詞のレーンとメロのレーンの2本**が並走する。この2レーン構造が C-14（音が無い詞と詞が無い音は別物）の実現手段。
- **穴は保存されるモノではなく、レーンの空白から導出される状態**。詞レーンだけ空なら「詞が無い穴」、メロレーンだけ空なら「メロが無い穴」、両方空なら「双方空白の穴」。粒度は空白の連続範囲そのもので決まるので、語1個〜曲全体の斑まで連続的に扱える（C-5）。詳細は F-2。

## 3. F-1〜F-5への回答

### F-1. 現状の歌詞全体（C-8）をどう見せるか

**縦スクロール1本の、読める歌詞としての一覧**にする。セクション見出しの下に行（句）が並び、行ごとに詞レーンとメロレーンの状態が見える。

- **詞は普通のテキストとして読める**ことを最優先にする。理由：推敲の4点のうち「意味」「感情遷移」は道具が手助けしない（C-7）＝人間が読んで確かめる。ならば全体画面は第一に「通しで読める歌詞」でなければならず、注記や記号で読み流しを妨げてはいけない。
- **メロの有無は行ごとの細い帯**で示す。帯が実線＝メロあり、帯なし（または点線）＝メロ未定。スマホで五線やピアノロールを常時出すのは読み流しを壊すので、全体画面ではメロは「有無と長さ」まで。中身は作業画面で見る。
- **穴は伏せ字の枠**で本文中に示す。メロがある詞の穴は、メロから音数が決まるので**音数ぶんの枠（例：○○○○○）**として出す。これで D-1「サビは最後の一言だけ無い、という水準で穴の所在と粒度が分かる」を満たす。メロが無い詞の穴は音数が決まらないので、長さ未定の空欄として区別して出す（F-4参照）。
- **ほぼ空でも成立する**（D-3）：セクション骨組みだけ宣言して全部が穴、でもこの画面は成り立つ。セクションすら未定なら「未整理」の1区画から始め、モチーフ一節（B-7）はそこに置く。
- 推敲表示（1a）はこの画面の表示切替：音韻（母音の並び・行末の対応の強調）とイントネーション（アクセントとメロの向きが衝突する箇所の印）を重ねる。C-7 で補助を求められているのはこの2点だけなので、意味・感情のための注記は作らない。警告は印であって修正の強制ではない（E-2）。

### F-2. 穴の粒度（C-12）をどう構造として持つか

**「セクション＋分割点」だけを構造として持ち、穴そのものは構造として持たない（導出する）**案を採る。

- 構造として保存するのは：(i) セクションの並び、(ii) セクション内に人間が任意に打てる**分割点**（半分・クォーター・4パート割り等はこれで表現。C-12・B-6）、(iii) 詞レーンとメロレーンの中身。
- **穴＝レーン上の空白の連続範囲**として計算で出す。穴の端は「埋まっている内容の端」か「セクション/分割点の境界」。
- 穴の**範囲の長さ**の決まり方：
  - 詞の穴でメロがある → メロの音符数から音数が決まる（範囲も長さも自動で確定）。
  - メロの穴で詞がある → 詞の音数から音の枠がおよそ決まる（B-5「詞からメロはある程度決まる」）。
  - 双方空白 → セクション/分割点の区画がそのまま穴。必要なら区画に小節数などの目安長を付けられる。
- 検討して捨てた対案は本文6章に書くが、要点だけ：穴を第一級のオブジェクト（人間が作成・削除する管理単位）にする案は捨てた。穴とは「無いこと」であって、管理台帳を人間に持たせると「穴を登録する」という余計な仕事が増える。埋めれば消え、消せば現れる、が最も嘘がない。ただし双方空白の区間だけは「無いこと」自体が区切りを持てないので、分割点という最小限の宣言で補う。

### F-3. 意味の側からの入口（C-13）をどんな入り方にするか

作業画面の候補探し（2a）を、**どの項目から埋めてもよい単一の条件フォーム**にする。項目は例えば：

- **言いたいこと**（語または短い言い換え。例「通り過ぎる」）
- **音数**（メロがあれば自動で入る。手で上書き可）
- **アクセントの形**（メロがあれば旋律の上下から候補が自動で入る。手で指定も可）
- **語尾・韻の条件**（行末の母音、他の行との韻の対応など。任意）

すべて任意入力で、**順序も必須項目も無い**。「通り過ぎる、3文字、このアクセント」（C-13）は「言いたいこと＋音数＋アクセント」を埋めた状態であり、逆に音数だけ入れて語を眺める入り方もできる。**意味の入口と音の入口を別画面にしない**ことで、絞り込みの順を構造に焼き付けない（E-1・C-4）ことを画面の形そのもので保証する。

曲全体の背景（主題・風景）はこのフォームに持ち込まない。C-13 が「優先度が低い（チャットがそのために作られている）」としているため、背景はこの道具の外に置く。

### F-4. 「まだ音が無い詞」と「まだ詞が無い音」（C-14）をどう見せ分けるか

2レーン構造をそのまま見せ分けに使う。

- **まだ音が無い詞**：本文は普通のテキストとして読める。その行のメロ帯が無い（点線）。→「読めるが、まだ歌えない」見た目。
- **まだ詞が無い音**：メロ帯は実線であり、詞レーンには**メロ由来の音数ぶんの伏せ字枠**が出る。→「歌えるが、まだ何も言っていない」見た目。B-11「メロだけ置く」はこの状態をそのまま保存すること。仮の句を強制しない（D-7 は未定なので作り込まない。詞レーンは普通のテキスト入力なので、置きたければ置ける、以上の対応はしない）。
- **双方空白**：帯もテキストも無い区画としてどちらとも違う見た目になる。
- 穴を選ぶ場面（B-9）でも、各穴に「詞が無い／メロが無い／双方無い」の別を明記する。同じ「穴」で一緒くたにしない。

### F-5. 収束側で候補を出すとき、どこまで出してどこから人間の手番にするか

**機械の受け持ち＝条件を満たす候補の列挙と、条件適合の根拠表示まで。人間の受け持ち＝選ぶ・直す・置く。**

- 前後が固定された穴（B-1〜B-5）では、音数・アクセント・前後との接続（音韻）という**硬い条件で絞った候補一覧**を出す。並び順は条件適合の度合いによるが、これは「どれだけ枠に嵌っているか」の表示であって優劣の判定ではない（E-2）。D-5 の言う通り、収束側は数え上げに近く機械の趣味が混入しにくいので、列挙に徹する。
- **候補が1件でも、機械は自動では置かない**。一意なら一意と分かる形で1件だけ出し、置く操作（タップ）は人間に残す。C-11 の本体は「選ぶ行為を人間に残す」ことなので、複数出すことを義務にはしないが、置く手番は絶対に渡さない。
- **候補は置く前に編集できる**。候補を叩き台に語尾だけ変える、といった仕上げが人間の側でできること（E-3「候補までが機械、仕上げは人間」）。
- 置いたあとはガードレール（音韻・イントネーションの印）が働くが、警告であって差し戻しではない。
- 発散側（B-7・B-8）では、機械は**求められたときだけ**セクション規模の下書きを複数の変奏として出す。人間は丸ごと採る・一部だけ採る・捨てるを選べる。列挙（収束側）と下書き（発散側）で機械の性格が違うことを画面上も分けて示し、発散側の出力を「正解」めいた一意の顔で出さない。なお E-6 により、両端固定の小さな穴に限っては（元の裁定の対象外なので）二段DP的な数え上げ手法の採用を実装時に再検討してよい。

## 4. 曲先/詞先の往復（C-1）をどう実現するか

**往復を「モード」にしない。穴ごとの入り方にする。**

- 歌詞全体画面のどの穴からも作業画面に入れて、作業画面では常に「詞側を埋める」「メロ側を埋める」の両方が開いている。メロがある穴では詞を当てる（曲先方向）、詞がある穴ではメロを付ける（詞先方向）、双方空白ならどちらから置いてもよい。
- 曲やセクションに「いま曲先/詞先」という状態を持たせない。持たせると往復のたびに切替操作が要り、「どちらかが主」の構造（C-1違反）に育つ。
- 往復の粒度はセクションに限られない（C-1）が、これは F-2 の構造で自動的に満たされる：穴はレーンの空白から任意の粒度で導出されるので、語1個の詞当て（曲先の最小）も、一句ぶんのメロ付け（詞先の最小）も、同じ作業画面で起きる。
- Aメロにメロ→詞当て→2番作詞→サビ作詞→その詞からメロ、という進行（A節の例）は、この設計では「全体画面で次の穴を選ぶ」の反復として自然に表現される。進行の順を道具が指図しない。

メロの表現について1点だけ設計判断を書く：この道具の中のメロは、**音数（音符数）とリズムと音高の上下が分かる軽い表現**（帯＋簡易な音高表示＋再生）に留める。理由は C-2＝仕上げはDAWで行うため。詞当てに必要なのは音数とアクセント照合であり、それにはこの水準で足りる。清書級の楽譜編集をこの道具に持ち込まない。

## 5. 収束と発散の両方をどう支援するか（C-6, C-10, C-11）

同じ「穴を選ぶ→作業画面」の動線の上で、**穴の固定度に応じて機械の出し方だけが変わる**構成にする。入口を分けない（C-10「どちらか一方に絞る前提を置かない」）。

- **収束側**（前後固定・B-1〜B-5）：候補探しフォームに前後の条件が自動で入り、機械は条件を満たす候補を列挙する（F-5）。人間は選ぶ・直す・置く。
- **中間**（双方空白・B-6）：どちらのレーンから置くかを人間が選び、片方を置いた瞬間にもう片方は収束側の穴に変わる。中間を特別扱いする機能は作らず、「片側を置くと収束側に変わる」性質に任せる。
- **発散側**（B-7・B-8）：固定端がほとんど無いので列挙は成立しない。機械は求められたときだけ複数の下書き（変奏）を出し、人間が採る・一部採る・捨てる。モチーフ一節しか無い初期状態（B-7）でも全体画面は成立し（D-3）、そこから広げる作業も同じ動線に乗る。
- どちらの側でも**最終選択は人間**（C-11）。機械が置く・機械が確定する操作は存在しない。

## 6. 検討したが採らなかった案

1. **チャットを主画面にする案** — 意味の側からの入口（C-13）は対話が向くように一瞬見える。捨てた理由：C-8/D-3 が要求するのは「常に見えている歌詞全体」であり、チャットは状態を流れの中に埋めてしまう。また背景・主題の相談は既にチャットの守備範囲だと要求文書自身が述べており（C-13）、重複する。
2. **セクションカード式（1画面1セクション）のナビゲーション** — スマホでは作りやすいが、歌詞全体が一望できず C-8 に反する。穴はセクション境界と無関係な粒度で開く（C-1・C-5）ので、セクションを画面の単位にすると構造が実態より粗くなる。
3. **穴を第一級オブジェクトとして人間に登録・管理させる案** — 穴に メモや優先度を付けられる利点はあるが、「穴を登録する」作業が発生し、埋めたのに台帳が残る類の不整合も生む。穴＝無いことの導出、に寄せた（F-2）。双方空白の区間のためだけに分割点という最小限の宣言を残した。
4. **意味からの入口と音からの入口を別画面にする案** — 入口を分けると、どちらを先に開くかという順序が動線に生まれ、E-1（順を構造に固定しない）を画面の形で破る。単一フォームの任意項目に統合した（F-3）。
5. **候補が一意のとき自動で埋める案** — C-11 は「一意に収束すること自体は禁止しない」と言うが、守るべきは選ぶ行為＝自作感。置く操作を機械に渡すと、一意でない場面でも「機械が置いてくれる」期待が育つ。一意でも人間がタップ、で統一した。
6. **スマホ版とデスクトップ版で機能を変える案**（例：推敲はデスクトップのみ） — C-2 の原点は出先の細切れ時間であり、推敲的な読み返しも出先で起こりうると考え、機能差は付けず配置だけ変えることにした。デスクトップ専用の重い工程は「仕上げはDAW」という C-2 の理由により、そもそもこの道具に置かない。

## 7. この設計案の弱点・自信のない部分

- **メロの軽い表現の水準が未検証**。音数・リズム・音高の上下で詞当てに足りると判断したが、アクセント照合にどこまでの音高精度が要るか、またスマホでのメロ入力（下書きの受け取り以外に手で置けるべきか）は詰め切れていない。DAWとの受け渡しの形も要求文書からは導出できず、開いた問いとして残る。
- **音符と音数（モーラ）の対応の曖昧さを塗り込めている**。1音符に複数モーラ、複数音符に1モーラ（メリスマ）がありうるが、「メロから音数が決まる」と単純化した。伏せ字枠の音数表示はここが崩れると信頼を失う。
- **推敲表示の情報量**。音韻とイントネーションの注記を歌詞全体に重ねると、行数が多い曲ではうるさくなる恐れがある。切替式にはしたが、重ね方の実際は試作で確かめるしかない。
- **末尾の穴（B-4）の扱い**。片端しか固定されていない穴は、収束（列挙）と発散（下書き）の中間で、候補の出し方がどちらに寄るべきか設計しきれていない。「固定端が減るほど列挙から下書きに寄る」と連続的に考えているが、境界の引き方は実装時の検討事項。
- **分割点の手間**。双方空白の穴のためだけに人間が分割点を打つ設計は、B-6 のような場面で小さな登録作業を強いる。穴を導出に寄せた代償であり、実際の使用でこの手間が気になるかは分からない。
- **D-7（仮の詞）を作り込まなかった判断**。「入れられるなら嬉しい程度」を「普通のテキストとして入れられる、以上の支援なし」と解釈したが、仮の詞と本番の詞を区別したくなる場面が後から出る可能性はある。
