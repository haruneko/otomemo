**何が問題か** 改訂案は自分の根拠を3か所で上に置いているが、そこに現物が無い。

**何が起きるか** design.md だけが先に更新され、上位が空のまま残る。次に読む人（＝次のセッションのあなた自身）が「requirements に書いてある」と信じて確かめずに乗る。この道具の設計はまさにそれで一度事故っている（#13d の「既存 chat verb だと書いてあったが実装時から誤り」）。存在しない番号（体験原則7）を根拠に「曲が持つ／機械が黙って作らない」を決めているのは、根拠の捏造と同じ形になる。

**どう直すか** 順序どおり、requirements に「歌詞を書く」節を、architecture に該当追記を**先に**書き、そのうえで design を差分適用する。それが同じ回でできないなら、design 側の引用を実在するもの（確定コンセプト文書のパス＋見出し番号）に差し替える。番号のある原則を引くときは、その番号を目視で確認してから書く。

## 2. コンセプトの未確定1（仮歌はどこまで自動でできるか）を、聞かずに設計が決めている

**何が問題か** オーナーは「メロディに対して歌詞を適用すると、符割りに基づいて仮歌用の歌詞が入ること」が**最も正しい**と言い、そのうえで「だけどこれはできないんでは？」と保留した。確定コンセプトはこれを未確定1に置き、「決めるとこの道具の中心の往復の手数が決まる」と書いている。改訂案は 2-5 の決定L2で「この規則は**人が『合わせる』を押したときだけ**走る」と決め切り、§12（オーナーに聞く）にこの項目が無い。

**何が起きるか** オーナーが「最も正しい」と言った姿（詞を当てたら仮歌が入る）が、確認なしに「ボタンを1つ押す形」に置き換わる。さらに、字余りの句で仮歌を鳴らしたとき何が鳴るのかが改訂案のどこにも書かれていない——§6-2 は「句の範囲にある音符に頭から1対1」なので、余ったモーラは音符が無く**黙って歌われない**。出先で書き足して鳴らして確かめる、というこの道具の中心の場面が、書かれないまま実装に落ちる。

**どう直すか** §12 の先頭に立てる。「詞を書き足したあと、仮歌はどこまで自動で鳴るか（写しだけ／音符も合わせる／人が押す）」と、「字余りのまま鳴らしたとき、余った分をどう扱うか（歌わない／最後の音符に詰める／鳴らさず知らせる）」の2つ。決めると何が決まるかも書く（＝書き直して鳴らすまでの手数と、機械が音符に触ってよい場面）。決まるまでは決定L2を「当面こうする」と明記して、決めた形として書かない。

## 3. 「軽微なら変化の適用はされたい」を、実装がゼロだからという理由で消している

**何が問題か** オーナーの発言「いやメロがわかれるのは良くて（…）**いや軽微なら変化の適用はされたい**」に対し、確定コンセプトはこれを未確定2として残している。改訂案は §10-8 の末尾で「**伝播はしない（「軽微な直しが複製先に及ぶか」は未決＝作らない）**」と一行で処理し、§12 にはこの問いが無い。§11「触らないもの」にも入っていない。

**何が起きるか** オーナーが希望として口に出したことが、「未決だから作らない」と書かれた瞬間に、聞かれないまま消える。しかも改訂案はこの直前で置き場をメロの中に移している＝複製が起きる頻度は上がる方向なので、影響は前より大きい。これは進行役が「直前に起きた事故」と呼んだ形（実装が無い→上流を縮める）と同じ形をしている。

**どう直すか** §10-8 は「複製の来歴を残す」だけに留め、「伝播はしない」という決めは書かない。代わりに §12 に「元のメロを直したとき、複製した先にどこまで及ぶか（何も及ばない／知らせるだけ／条件付きで及ぶ）」を立て、決めると何が決まるか（1番と2番が黙って別物になるのか、細く繋がったままか＝比較の面が何を見せる場所になるか）を書く。

## 4. 1番と2番の土台にしている「既存の安全弁」が、実コードではそう動かない

**何が問題か** #13e §2 が「共有されたメロの句を直そうとしたときは既存の安全弁（`useCowGuard`＝配置2以上で『全部に効かす／この曲だけ変える』を1度だけ聞く）が**そのまま受ける**＝同じメロに複数の歌詞案を並べて持つ形は作らない」と書いている。実コードを読むと3点食い違う。

- `apps/web/src/useCowGuard.ts`：`parentId` が無い（＝ネタ帳から直接メロを開いた）ときは**ガードが完全に無効**（「parentId 未指定＝ガード完全無効」とコメントにも明記）。改訂案は §9 で「ネタ帳から直接開いた場合」を正面から扱っているのに、その経路には安全弁が無い。共有されているメロに詞を書いても何も聞かれず、置いてある全部に効く。
- 「この曲だけ変える」が呼ぶのは `api.vary`＝**分家**（`variant_of` が残る浅い分け方。`apps/api/src/core.ts:121` の注記どおり子は共有）。確定コンセプトが選んだのは**複製**（`copyNeta`＝中身ごと丸ごと・系譜なし）。安全弁を通ると、確定した作り方と違うものができる。
- `placementsOf`（`core.ts:267`）が数えるのは**そのメロ自身の配置数**。1番と2番が「同じセクションを曲に2回置く」形（このアプリの既定の作り方）なら、メロの配置数は1のままで**発火しない**。§2 が言う「同じメロネタを2箇所に置けば歌詞ごと同じものが2回出る」がまさにこの状態で、そこに安全弁は無い。

加えて、この形はオーナーの Q1「同じメロのまま詞だけ違うを実際にやるか＝**やることもある**」に答えていない（複製すれば「同じメロ」ではなくなる／複製しなければ詞は1つ）。

**何が起きるか** 「複製で作る・コピーと比較を強くする」の運用が、設計上は既存機能に寄りかかっているのに、実際には受け皿が無い。1番の詞を書いたら2番にも同じ詞が出る状態で、直そうとしても止める仕組みが働かず、どこかの時点で片方が消える。

**どう直すか** §2 のこの段落を書き直す。(a) 2番を作る手順を実際の操作で書く（曲フォームの「複製する」＝配置1つを `copyNeta` した別物に差し替える。`FormStrip.tsx:238` に既にある）。(b) 安全弁については「今のガードは親から潜ったときだけ・分ける形は分家」という実態を書き、詞を持つメロに対して何が要るか（ネタ帳から開いた経路も対象にするのか、分ける形を複製に変えるのか）を**直す対象**として §10 に立てる。(c) Q1 への答え（同じメロのまま詞だけ違う、をこの設計でどうやるか）を §12 に立てるか、できないと明記する。

## 5. 曲（song）に content を持たせる決めが、design の既存の決めと正面から衝突していて、触る節の一覧にも入っていない

**何が問題か** #13e §2 が `song.content.lyric = { phrases: [...] }` を新設する。一方 design.md **247行**は「合成(section/song)：**content でなく `compose_edge`（子＋position）で表す**」と決めており、191行も container を「中身を持たない親」と書いている。改訂案の「1. 触る節の一覧（それ以外は触らない）」に247行は入っていない。

**何が起きるか** 同じ文書の中に「曲は中身を持たない」と「曲は歌詞を持つ」が並ぶ。実装側も 247 に従って書かれていて、`useNetaEditor.ts` の `savePatch()` は container のとき `{key,mode,tempo,meter}` しか返さない（＝content を書かない）。改訂案は §10-1 でこれを「専用の書き込みにする」と一行で流しているが、根っこは実装の穴ではなく**設計の決めの衝突**なので、直す先が違う。

**どう直すか** 247行を触る節に加え、「曲は配置で表す。ただし歌詞（メロの無い区間の句）だけは曲が持つ」という例外を明記する（191行の container 例外と同じ書き方）。そのうえで §10-1 の実装対応を、その例外の帰結として書く。

## 7. 句の「範囲」を必ず人が決める設計になっているが、決めなかったときが書かれていない

**何が問題か** §3 の表2は範囲を「**人**（「ここに書く」と開いた場所）」が書くものとし、§7 は「範囲は**音符からは導かない**」と念を押している。ところが、範囲を指定せずに詞だけ書いたときどうなるかが、改訂案のどこにも無い（§12 にも無い）。

**何が起きるか** コンセプトの「出先の細切れ時間でどこからでも書き足せる」「穴は最小1単語から」に対して、書くたびに範囲を決める手数が挟まる。スマホ幅で「まず範囲を決めてから1単語書く」は、この道具が一番やらせたい動作の入口を重くする。逆に実装側が黙って既定（メロの全体など）を当てれば、それは「音符から導かない」という決めを破る。

**どう直すか** 既定を明記する。たとえば「メロを開いて詞を書き始めたら、範囲の既定はそのメロの全体。人が切れば分かれる」。既定を機械が決めることの是非がオーナー裁定に触るなら §12 に立て、決めると何が決まるか（1単語を書くまでの手数と、字余り／メロが途中の言い分けが最初から効くかどうか）を書く。

## 8. 発散の助けが設計に一行も無く、歌詞生成が収束専用として固定される

**何が問題か** 確定コンセプトの「すること」に「**発散の助けと収束の助けの両方を出す**（双方あるのが良い）」がある。改訂案 2-3 は `gen_lyric` の制約を「句の範囲（小節数）と、そこにあるメロの音数・読みの高低」と書き直しており、これは全部**枠が決まってから埋める側**＝収束だけ。§11 は「触らない」、§12 にも発散の問いは無い。オーナーが挙げた具体例（「ここに『通り過ぎる』という言葉で、3文字、このアクセント」というパズル）は §3 の表8番「予定」の置き場としては入っているが、そこから何を出すかは無い。

**何が起きるか** 歌詞生成の入口が「枠に嵌るものを出す」と設計に書かれ、以後それが正典になる。コンセプトが確定した「双方あるのが良い」の片方が、最初から作らない扱いになる。

**どう直すか** 2-3 に「これは絞る側の入口。広げる側（何を出すか）は未定」と明記し、§12 に「作詞での発散として何を出してほしいか（語の候補／韻／予定に嵌る言い方／別の言い回し）」を立てる。決めると何が決まるか＝機械が出す候補の種類と、出してよい場面。

## 9. 「句を書けるのは melody だけ」が、表示の都合を入力の可否にしている

**何が問題か** §2 の最後に「**句を書けるのは melody だけ**。counter（ハモ）・riff は対象外＝**通しの面に歌詞が二重に出ない**」とある。理由が「通しの面に二重に出ると困る」＝出す側の都合。オーナーはハモに詞を書きたいかを聞かれておらず、発言も無い。

**何が起きるか** ハモ（コーラス）に詞を付けたい場面が来たとき、データの置き場が無い。表示の都合で入口を塞ぐのは、コンセプトの「どこからでも書き足せる」と逆を向く。

**どう直すか** 「今回はメロだけを対象にする（ハモは後で足せるようにデータの形は同じにしておく）」という**範囲の限定**として書き、理由を表示側に求めない。ハモに詞を書きたいかは §12 に立てる（決めると、通しの面に何行出るかと、仮歌で何声鳴らすかが決まる）。

## 10. オーナーが口にした「空のメロディを作る方が無難」に、設計が一言も触れていない

**何が問題か** やり取りでオーナーは「メロがないと歌詞が書けないなら底にメロを置くか曲が歌詞を持つべき」と両案を出し、その後「**つまり空のメロディを作る方のが無難な気がするな、その代わりコピーとかを充実させるとか**」と、片方に寄った言い方をしている。確定コンセプトは逆（メロの無い区間は曲が持つ／空のメロを勝手に置かない）で決着しており、改訂案はそれに従っているが、§2 の「旧懸念とその答え」5点にも §12 にもこの発言は出てこない。

**何が起きるか** 曲に新しい持ちもの（`song.content.lyric`）を足し、通しの併合（§8）と出会いの操作（§12-1・2）という枝を丸ごと生やす決定が、オーナーが逆向きに寄った発言に一度も触れないまま進む。あとで「空のメロでよかったのでは」となったとき、§8 と §12-1/2 がまるごと消える。

**どう直すか** §12 に「メロの無い区間の詞は、曲が持つ形でよいか（人が『ここにメロを置く』と合図して空のメロに書く形ではなく）」を1つ立て、決めると何が決まるかを書く＝曲が歌詞を持つかどうかで、§8 の通しの併合と §12-1/2（出会い・並べ替えでの置き去り）が要るか要らないかが丸ごと決まる。触れずに進めるより、1問で潰したほうが安い。

- `docs/architecture.md` の最終更新は 2026-07-18 で、2026-07-29 の追記はありません（全43行）。
- 体験原則は `requirements.md:24-30` の**6つまで**で、7番は存在しません。
- 引用として書かれた要件文も原文にありません。「2番は複製で作る」は無く、`requirements.md:156` は「分家と複製は別の操作」としか書いていません。「最後に選ぶのは人間」も原文は `requirements.md:168`「最終の良し悪しは人が耳で決める」です。

**改訂案のどこか**　#1 の表が「触る節の一覧（行番号つき・**それ以外は触らない**）」と宣言し、14行すべてが design.md 内。上位2つの改訂は差分に含まれていません。「補足」では requirements 未決1 の更新を「進行役の判断」に委ねていますが、そもそも requirements にその未決1 も歌詞の節もありません。

## 2. 「共有されたメロの句は既存の安全弁が受ける」——その安全弁は、コンセプトが主役に据えた入口では動かない

**何が問題か**　#13e §2 は「共有されたメロの句を直そうとしたときは既存の安全弁（`useCowGuard`＝配置2以上で『全部に効かす／この曲だけ変える』を1度だけ聞く）が**そのまま受ける**」と書いています。実物：

- `useCowGuard.ts:29` `useRef(opts.parentId ? null : false)`（parentId 無し＝最初から「共有でない」扱い）
- `useCowGuard.ts:70` `if (!opts.parentId || …) return { action: "save" };`（何も聞かずに原本へ書く）
- `App.tsx:770` `parentId={navStack.length ? navStack[…].id : undefined}`＝**曲/セクションから潜ったときだけ**付く。ネタ帳から直接メロを開くと undefined。
- `NetaDialog.tsx:36-37` に「placementCount>=2 なら小バッジを常時表示（**parentId 無し＝トップ開きの3択ガード欠如を補う緩和策**）」と、コード自身が穴を自認するコメントがあります。バッジであってガードではありません。

一方コンセプトは「**メロを単体で開いたときも詞が書ける**」を明記し、#13e §2 もそれを「置き場の直接の帰結」として売りにしています。

**何が起きるか**　2箇所に置いた同じメロをネタ帳から開いて2番の詞を書くと、**確認が一度も出ないまま1番の詞が書き換わります**。改訂案が置き場をメロに決めたことで、この経路が「たまに通る道」から「詞を書くときの正面玄関」に格上げされるので、事故の頻度も上がります。

なお §2 の同じ段落は「1番2番＝複製（要件『2番は複製で作る』）」と言いながら、続けて「同じメロネタを2箇所に置けば歌詞ごと同じものが2回出る／別の詞にしたければメロごと複製する」と、既定を**共有配置**として書いています。コンセプトの「複製でよくね？」とは逆向きで、この食い違いがそのまま上の穴に直結しています。

**どう直すか**　§2 の「そのまま受ける」を撤回し、§10（実装が追いついていない箇所）に「トップ開きでは共有メロへの書き込みにガードが無い（`useCowGuard.ts:70`）」を欠陥として立てる。そのうえで、既定が共有配置なのか複製なのかを §2 で1つに決める（複製が既定なら、複製の手順を先に用意しないと詞を書けない曲が出ます）。

## 3. 漢字を1字1モーラで数えている実装がもう1本ある。直す対象に入っていない

## 4. メリスマから「ー」を外す決定が、それを読んでいる2箇所を壊す。直す対象に無い

**何が問題か**　#13e §6-4 は「メリスマ（余った音符）は `syllable` に『ー』を書かない…**仮歌へ渡す直前だけ**『ー』に直す」と決めています。「ー」を読んでいる実物：

- `apps/api/src/sing.ts:143` `const isMelisma = n.syllable === "ー" || n.syllable === "ｰ";` → `lyric: isMelisma ? "" : (n.syllable?.trim() ? n.syllable : mora)`。**syllable が空だと `mora`（既定「ラ」）で歌います**。
- `apps/web/src/components/PianoRoll.tsx:398` も同じ判定で音符の見た目を変えています。

§10 の直す対象にも、段階 LS4 にも、この2箇所はありません。「渡す直前」がどの関数かも書かれていません（仮歌は web の `useVocal` 経由と api の `POST /sing` の2経路あります）。

**何が起きるか**　余った音符が母音の続きでなく「ラ」で歌われ、画面のメリスマ表示も消えます。仮歌で確かめるのがこの道具の芯なので、いちばん目立つ形の後退です。

**あわせて**　§6-4 が挙げている理由（「`pron` の長音も『ー』なので、埋め草と混ざると『字余りN／あとN音』の数えが狂う」）は §7 の数え方と噛み合っていません。§7 は句のモーラ数と句の範囲の音符数を突き合わせる決めで、`syllable` の文字列は一切数えていません。さらに実測すると `pron` は長音を**必ず**「ー」で返します（今日→`キョー`／ああ→`アー`／そう→`ソー`）。つまり「ー」は埋め草でなくても普通に出るので、「埋め草だけを『ー』でなくす」では区別できません。

**どう直すか**　§10 に `sing.ts:143` と `PianoRoll.tsx:398` を直す対象として足し、変換をどの関数の中でやるかを1点に決めて書く。§6-4 の理由も、実際に効く理由（あるいは §12-3 の「っ」「ー」に音符を立てるかの裁定待ち）に書き換える。

## 5. §9 が求める「音符を変えずに読みを音符へ写す」処理が、どこにも無い

**何が問題か**　#13e §9 は「句の範囲にある音符の `syllable` は、句の読みから機械が写し直してよい——**音符の数・位置・高さは変えない**」と決めています。実物で `syllable` を書く純関数は `flowLyric` だけで（`apps/api/src/lyric.ts:37-63` と `apps/web/src/lyrics.ts:34-65`・同じものが2本）、42-55行が**必ず**音符数＝モーラ数になるまで音符を割ります。音符を変えずに写す処理は存在しません。
