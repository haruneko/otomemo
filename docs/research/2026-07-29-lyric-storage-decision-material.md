## 1. 前提（確定していること・4案の定義）

**確定済み（オーナー原文が根拠）**
- 「セクションではなく仮歌を入れるメロディにほしい。Sectionに歌詞ってなんか違和感がある」＝**仮歌を入れる先はメロディ・セクションには歌詞を置かない**。
- 歌詞の正データは漢字仮名交じりの普通の文章（かな書きは仮歌のための姿）。

**未確定＝この文書の問い**：メロがまだ無い場所（詞先）の歌詞をどこが持つか。案は4つ。

| 案 | 中身 |
|---|---|
| **(あ) 曲が持つ** | 曲（song ネタ）の content に句を持つ（メロの無い区間ぶんだけ）。メロが後から来たら、そのとき句をメロへ移す |
| **(い) 空のメロを置いて書く** | 人が「ここにメロを置く」と合図して音符0個のメロネタを作って配置し、その中に句を書く。オーナーが「空のメロディを作る方のが無難な気がするな、その代わりコピーとかを充実させるとか」と言ったほう |
| **(い-a) (い)＋一覧から隠す** | (い) に加えて、空のメロはネタ帳（一覧）からは非アクティブとして見えなくする（オーナー発案） |
| **(い-b) 共有の空メロ1つ** | プレースホルダー用の空メロは1つだけ共有しておき、何かが入った瞬間に新しいメロディを産む（オーナー発案） |

**時系列の注意**：過去の裁定「ゴミが増えるのは嫌なので暗黙の操作はあまり増やさないでほしい」「実体を明確に作る合図なければ作られたくない」（2026-07-27・モチーフからの曲の自動作成と仮セクションの実体化への裁定）は、**「空のメロディを作る方のが無難」の発言より前**。(い-a)(い-b) はさらにその後にオーナー自身が出した案。

## 3. 本体＝4案 × 6軸の表

### 軸1. メリット（この案でしか得られないもの）

| 案 | メリット |
|---|---|
| (あ) | **実体を1つも作らない**＝ネタ帳にも尺計算にも影響ゼロ。詞を書くのに「メロを置く」という別の操作を経ない＝詞先の1手目が最短。「詞もメロも無い区間」はデータ0のまま。空メロの見た目問題（(い-a)(い-b) が対処しようとしているもの）がそもそも発生しない |
| (い) | **保存先が常にメロ1種類**＝通しの面は配置ツリー（getComposition）を辿るだけで全句が時間順に取れ、「曲持ちの句を別枠で併合する仕組み」が丸ごと消える。「詞とメロが出会ったとき句を移す」操作も消える（空メロに音符を足すだけ）。design 247「container は中身を持たない」に例外を書かずに済む。**オーナーの最後の傾き（「無難な気がするな」）と一致** |
| (い-a) | (い) の全メリット＋ネタ帳の見た目問題（オーナー「見た目には微妙ね」）への答えを持つ。隠す仕組みは scope（project/library タブ）という前例の上に作れる |
| (い-b) | (い) の全メリット＋**空メロの実体が増えない（常に1個）**＝ゴミ最小。「置く」操作の手数も最小（毎回作らず、既にある1個を置くだけ） |

### 軸2. デメリット（この案を選ぶと必ず払うもの）

| 案 | デメリット |
|---|---|
| (あ) | 曲が content を持つ**例外**を design 191・247 の決めに書き足す（container 原則の一貫性を1箇所崩す）。曲の歌詞専用の書き込み口を新設する（自動保存が container の content を返さないため＝`useNetaEditor.ts:347`）。通しの面に「配置由来の句＋曲持ちの句」の併合が要る＝スライス5が最も重い。「メロが来たら句を移す」操作の設計が要る。新しい問いが1つ増える（曲の構成を並べ替えたとき、メロの無い歌詞は付いてくるか） |
| (い) | 音符0個のメロが**曲の尺を1小節と誤って数えさせる**（`sectionContext.ts:81,88`）＝3小節ぶんの詞を書く場所に置いた空メロが1小節扱い→手当てが必須（例：bars ヒントを尊重）。詞を書く前に「メロを置く」1手が必ず挟まる。**詞だけ書いてメロを書かなかった空メロは音符0のままネタ帳に溜まる**（オーナー自身が「見た目には微妙ね」と指摘済み） |
| (い-a) | (い) の全デメリット（見た目を除く）＋隠す仕組みの新設コスト（scope enum は閉じている＝値を足すと配置時の library→project 自動コピー分岐にも波及。タグでやるなら一覧絞りの実装を別に書く）。**「見えないゴミ」を作る**＝隠れた空メロを後から見つける・掃除する手段が別に要る。いつ非アクティブになり、いつ戻るかの規則も決める必要がある |
| (い-b) | 「何かが入った瞬間に新しいメロを産む」＝**機械が合図なしに実体を作る**振る舞いそのもの。共有された1個への書き込み事故の防止が必須＝`useCowGuard.ts:70` の穴（ネタ帳から直接開くと確認なしで原本へ書く）を先に塞がないと、プレースホルダー原本に音符が入り**全部の置き場所が一斉に変わる**。「産む」処理を全保存経路（600ms自動保存・set_lyric・流し込み）に仕込む＝(い) 系で最も実装が重い。産まれたメロの命名・整理という新しい仕事も発生する |

### 軸5. 後から乗り換えられるか（実データの移行可能性）

どの案でも**句のデータの形は同一**で、違いは「句がどのネタの content に入っているか」だけ。content は素通しの JSON（`schemas.ts:16`）＝DB スキーマ変更なし。曲は1回読めば全構成が取れる（`getComposition`）ので、移行は機械的な一括変換で書ける。

| 乗り換え | 評価 |
|---|---|
| (い)→(あ) | **安い**。空メロの句を親曲の content へ移し（メロの拍→曲の拍に換算）、空メロの配置と実体を消す。音符が入ったメロの句は動かさない |
| (あ)→(い) | **安い**。曲持ちの句ごとに空メロを作って配置し、句を移す。逆向きと同じ規模 |
| (い)↔(い-a) | **ほぼゼロ**。データ同一・表示の絞りだけ |
| (い-b)→他 | **安い**。産まれた後のメロは普通のメロ。運用中のプレースホルダー配置を実体化するだけ |
| (あ)↔(い) 共通の注意 | 乗り換えが高くなる唯一の分岐＝**通しの面（スライス5）を作った後**。併合の実装が2系統／1系統で違うため、スライス5だけは作り直しに近くなる |

**＝この裁定は「今すぐ完璧に決める」必要が無い**。データはいつでも移せる。高いのはスライス5のコードだけなので、**スライス5に着手する前までに決まっていればよい**。

## 4. 推し（提案・物差しはオーナー）

**提案＝(い) を素のまま（(い-a)(い-b) は保留）で仮置きして進める。**
理由：①オーナーの最後の傾き（「空のメロディを作る方のが無難」）と一致し、「実体は人の合図で作る」の裁定にも沿う。②design の「container は中身を持たない」を守り、併合・出会いの操作が丸ごと消える＝作るものが最小。③乗り換えが安い（§軸5）ので、使ってみて (あ) が良ければ後で移れる。④(い-a)(い-b) は見た目への対処であり、**実物で空メロが実際に何個溜まるかを見てから**決めるほうが判断材料が濃い——溜まらなければ何も作らずに済む。

## 5. 今すぐ決める必要があるか

**無い。ただし期限はある。**
- **スライス1〜4（メロに詞を書く・読み・印・言い分け・手直し）は置き場に依存しない**＝今すぐ着手できる（引き継ぎ書 第7章と一致することを裏取り済み）。
- **必ず詰まるのはスライス5（通しで読む面）の着手時**。ここだけは (あ)＝2系統併合／(い)＝1系統で実装が分かれ、作った後の乗り換えが高い。
- (い) 系を仮置きするなら、空メロの尺の手当て（`sectionContext.ts:81,88`）はスライス5より前＝「空メロを置く」機能を作る時点で要る。
- よって聞き方は2択が可能：**今この1問だけ決める**（後続の (い-a)(い-b) は実物を見てから）か、**スライス1〜4を先に進めて、実物を触ってからスライス5の前に決める**か。どちらでもデータは困らない。

## 6. オーナーに見せる用の短いラベル（スマホ幅・そのまま選択肢に使える形）

- **(あ) 曲が歌詞を持つ** — メロ無し区間の詞は曲に保存。メロが来たら移す。実体を作らない
- **(い) 空のメロを置いて書く** — 人が合図して空メロを置き、詞はそこへ。保存先は常にメロ
- **(い-a) 空メロを一覧から隠す** — (い)＋空のメロはネタ帳で非アクティブ表示にする
- **(い-b) 共有の空メロを使い回す** — 空メロは1つだけ。書いた瞬間に新しいメロが生まれる
