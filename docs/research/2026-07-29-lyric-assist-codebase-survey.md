# 歌詞データの現状の棚卸し（実コード実測・2026-07-29）

## 0. 結論を先に

**「歌詞」という保存物は、実装上どこにも存在しない。** 保存されているのは2つの別物で、互いに繋がっていない。

1. **音符に貼り付いた1文字のかな**（`Note.syllable`）＝メロネタの `content.notes[i].syllable`。実データ4件。中身は**仮歌用の発音表記**であって歌詞ではない（実測: 「思いわめぐりい」「だろお」＝助詞「は」が「わ」・「う」が「お」）。
2. **`kind:"lyric"` ネタの `text` 列**＝ただの自由文テキスト。**メロとも音符とも一切結線していない**（compose_edge も relation_edge も張られない）。実データ8件、全部QAの捨てデータ（`qa歌詞-1783808367720-3120` 等）、`content` は8件すべて NULL。

**漢字仮名交じりの正データを置く場所は、DBにもコードにも無い。** design.md がそれを1回決めて（797-798行）、実装されないまま、別の裁定（1647行）が上書きしている。2層化は「欄を1つ足す」ではなく、**存在しない層を新設し、既存の1層の意味を「歌詞」から「割付の結果」へ定義し直す**作業になる。

## 1. `Note.syllable` の全経路

### 1-1 定義（1か所）

`packages/music-core/src/index.ts:9-15`


### 1-4 【実測・重大】アクセント抽出がかなを食っている

`apps/api/src/accent.ts:76-81`:

```ts

  const kana = syllables.join("");     // ← 音符上のかなを連結
  const r = await extractAccents(kana); // ← それを pyopenjtalk に渡す
  return mapAccents(syllables, r);
```

＝事実資料§2が「かな書きだと読みを取り違える」と書いた誤読を、**アプリが常時踏んでいる**。実測（`apps/audio/.venv/bin/python apps/audio/accent.py`、今日再実行）:

| 入力 | hl（0=低/1=高） | アクセント句 |
|---|---|---|
| `にわへ` | `[1,1,0]` | 2句（1+2）に割れる |
| `庭へ` | `[0,1,1]` | 1句（正） |
| `あめのひは` | `[0,1,1,1,0]` | 2句 |
| `雨の日は` | `[1,0,0,0,1]` | 2句（雨＝頭高・正） |

現行アプリで音符に載っているのはかなだけなので、`analyze_lyric_fit` の赤黄も `computeLyricHits` の色も**この誤った高低の上に乗っている**。2層化の本命の効き所はここ。

なお `mapAccents`（`accent.ts:59-70`）はモーラ総数が音符数と合わなければ `null` を返し、`mcp.ts:996-1001` が黙って内蔵ヒューリスティックへ落ちる（`accentSource` に出るだけ）。表記から読みを起こすようになると総数の一致条件が変わるので、ここは必ず触ることになる。

### 1-5 accent.py の出力はローマ字＝かなが取れない

`apps/audio/accent.py:95` `"moras": ["".join(m["phones"]) …]` ＝ `["ni","wa","e"]`。**表記→かなモーラ列を返す経路はリポジトリ内に無い。**

モックv8はこれを `docs/research/2026-07-28-lyric-assist-v8/frontend.py` で解決している（`pyopenjtalk.run_frontend` → 形態素ごとの `{string, read, pron, mora_size}`）。今日再実行して動作確認済み:

```
庭へ      → [{string:"庭", read:"ニワ", pron:"ニワ", mora_size:2}, {string:"へ", read:"ヘ", pron:"エ", mora_size:1}]
雨の日は  → 雨/アメ/2, の/ノ/1, 日/ヒ/1, は/ハ→pron:"ワ"/1
沈みゆくこの体 → 沈み/シズミ/3, ゆく/ユク/2, この/コノ/2, 体/カラダ/3
```

**`read`（書いてある読み）と `pron`（歌う発音）が別物である**ことに注意（は→ワ、へ→エ）。既存の実データの syllable は `pron` 側の系列（「思いわ」「だろお」）。＝2層化では表記から**2種類のかな**が出る。どちらを音符に載せるかは未裁定の論点として残る（オーナー裁定「かながきは仮歌のためにある」から素直に読むと `pron` 側）。

このスクリプトは調査用ディレクトリにあるだけで、**`apps/audio/` にも api にも配線されていない**。

### 2-2 UI

`apps/web/src/components/KindEditorBody.tsx:331-341` — 歌詞ネタのエディタは**ただの textarea 1枚**（`p.text`）＋その下にモーラ数パネル。

### 2-3 【実測・重大】モーラ数パネルが漢字で嘘をつく

`moraLines`（`apps/web/src/lyrics.ts:25-27`）→ `splitMora`（`:8-23`）は**かな専用**（コメント `:5` 「※かな前提。漢字交じりは各字1カウント」）。実測:

## 3. `flowLyric` — 既存の割付を守る引数は無い

**同じ関数が2本ある**（片方を直すと片方が腐る）:

- `apps/api/src/lyric.ts:37-63`
- `apps/web/src/lyrics.ts:34-65`（コメント以外ロジック同一）

やること:
1. モーラ数 > 音符数 → 一番長い音符を半分に割る（下限16分＝`MORA_FLOOR = 0.25`・`lyric.ts:33`）を貪欲に繰り返す（`:42-55`）
2. **`work.map((n,i) => ({...n, syllable: i<M ? moras[i] : "ー"}))`（`lyric.ts:57`）＝全音符の syllable を頭から無条件に上書き**
3. 割り切れず余ったモーラは最後の音符へ全部連結（`:58-61`）

**保護引数は無い。** 第3引数は `floor`（分割下限）だけ。呼び側4つ（`mcp.ts:953`・`generate.ts:762`・`PianoRoll.tsx:280`・テスト）すべてが全notes上書き。＝事実資料§6「既存 syllable を保護する引数が無い」の裏取り、確認。

「後から足せない作りにしてはいけない」（裁定2）に対しては、`flowLyric` の**引数を足すこと自体は容易**（純関数・呼び側4つ）。難しいのは保護の単位で、現状は「音符の配列位置」しか識別子が無いため「この語の割付は動かすな」が表現できない。＝**割付の手直しを後から足すには、音符とモーラを結ぶ識別子（またはモーラ側の索引）が要る**。これは今から `Note` に置き場を作っておくか否かの判断で、後付けだとデータ移行が発生する。

## 5. `docs/design.md` が歌詞について約束していること（行番号つき原文）

### 5-1 #13 の裁定（現行の正典・2層化と正面衝突する）

> **1647**: `- **データモデル決定（2026-07-15・オーナー裁定）＝歌詞は独立エンティティにしない**。歌詞は `Note.syllable` としてメロに埋め込み（現行どおり）が正典。根拠＝**譜割り一体論**：日本語は1音1モーラ原則ゆえ歌詞が変わればメリスマ分割等で音符列自体が変わる＝「同じ音符列に別歌詞」は成立しない。**同じ音・違う歌詞は別のメロディネタ**（copy_neta／分岐スタック realized_from の一種）として扱う。歌詞先行の下書きは knowledge/テキストネタで書き溜め、メロと出会った時点で流し込み＝埋め込みに変換。`

> **1658**: `- **入力源**：本スライスは `syllable`（かな・モーラ片）とピッチ/オンセット列で完結。`

### 5-3 読み方（衝突の整理）

- **797-798 は今回のオーナー裁定1と同じ方向**（表記＋読み・読みが音数の正準）。ただし単位が「行」で、語↔モーラの対応は 799 で明示的に「将来」へ送られている。**モックv8の `spans`（語区間↔モーラ区間）はこの「将来」の実現物**。

- **1658**（プロソディの入力源は syllable で完結）は**破棄が必要**。アクセントの正しさが表記依存である以上、入力源に表記が要る（§1-4 の実測）。

## 6. 2層にするとき、どのファイルの何が変わるか

「正データ＝漢字仮名交じりの文章／導出＝かな・割付」にした場合。**新設が要るものと、既存が壊れるものを分けて挙げる。**

### 6-1 まず上位を直す（コードより先）

## 6. `run_frontend` の実測と、accent.py に足す妥当性

`pyopenjtalk.run_frontend("駆け抜けた通り過ぎる街の灯")`：

```
駆け抜け[read=カケヌケ|pron=カケヌケ|acc4|mora_size4|chain_flag-1]
た      [read=タ      |pron=タ      |acc0|1|+1]
通り過ぎる[read=トオリスギル|pron=トーリスギル|acc5|6|0]
街      [read=マチ    |pron=マチ    |acc2|2|0]
の      [read=ノ      |pron=ノ      |acc0|1|+1]
灯      [read=ヒ      |pron=ヒ      |acc1|1|0]
```

確かめた性質（49語×約20文で実測）：

1. **`sum(mora_size)` と `accent.py` の `mora_total` は一致する**（試した全ケース。唯一「ーあ」という先頭長音だけの退化例で 2 vs 1 に割れた）。→ **形態素の区切りとモーラ列を、mora_size の積み上げで確実に対応づけられる。**
2. **`chain_flag` の切れ目（0 or -1 が新しい句頭、+1 が前へ結合）が `accent.py` の `phrases` 境界と一致する**。「庭へ」→ へ が +1 → 1句3モーラ、`accent.py` phrases も `[{3, kernel:3}]`。
3. **`read` と `pron` は別物**。`read` は仮名遣いに沿った読み（ハ→ハ、トオリスギル）、`pron` は実際の音（**ハ→ワ**、**トーリスギル**、ヴェール→**ベール**、ちいさな→**チーサナ**）。仮歌に流すなら `pron`、ふりがなとして人に見せるなら `read` が自然。**どちらを正とするかはオーナーに聞く必要がある**（両方持つのも可）。
4. **`pron` にはアクセント記号「’」が混じる**（`です`→`デス’`、`聞こえ`→`キ’コエ`）。かなとして使うなら除去が要る。
5. 各形態素の `acc` は**結合前の値**で、`accent.py` の `kernel`（結合後のアクセント句の型）とは違う。「庭」acc=0 に対し「庭へ」の kernel=3。**表示・判定には `accent.py` の kernel を使い、`acc` は使わない。**
6. 記号（、。！…）は `mora_size=0` の形態素として出る＝除外して連結すればよい。

**費用**：同一プロセス内で `extract()` が 0.15ms/回、`run_frontend()` が **0.02ms/回**（各200回計測）。**`accent.py` の中に足しても実測で計れないほど安い。** ＝**この経路を accent.py に足す形は妥当**（別スクリプト・別 spawn にする理由が無い）。

## 7. TS と Python のモーラ分割は食い違うか（実測）

`packages/music-core/src/prosody.ts:46 analyzeMoras` の結果と Python の `mora_size` を、形態素単位で突き合わせた。

- **実用範囲では一致する**：49語（拗音・促音・撥音・長音・無声化・数字・アルファベット・句読点を含む）で **read 不一致 0 / pron 不一致 0**。「きゃっと=3」「ゆっくり=4」「感嘆=4」「トゥインクル」「ディズニー」「ヴェール=3」「コーヒー=4」「ですます（無声化）」すべて一致。
- **食い違う例が3つ見つかった**：
  - `クァルテット` — Python 6モーラ（`ku,a,ru,te,cl,to`＝クァを2つに割る）／TS 5モーラ（クァを1つに結合）。
  - `ワァ` — `read=ワァ` なら TS 1モーラ・Python 2モーラ。ただし **`pron=ワア` を使えば一致する**。
  - `ーあ`（先頭が長音）— Python の中でも `mora_size` 合計 2 と full-context 1 が割れる退化例。
- ＝**`read` ではなく `pron` を TS に渡せば食い違いはほぼ消える**（クァ系の外来音を除く）。逆に言えば **TS 側の分割を正とせず、Python が返したモーラの区切りをそのまま持ち回るのが安全**。

## 8. 所要時間の実測（歌詞を打つたびに走らせて耐えるか）

Node から `extractAccents` を実際に叩いた値（WSL2・同機）：

| やり方 | 実測 |
|---|---|
| 1句 1回（×10回） | **最短 125ms / 中央 143ms / 最長 149ms** |
| 40句を順番に spawn | **5,799ms**（1句あたり 145ms） |
| 40句を並列8で spawn | **1,591ms** |
| **40句を stdin で1回の spawn にまとめる** | **149ms**（3回とも149〜150ms） |

`python -c "import pyopenjtalk"` だけで 130ms。**145ms のうち約144ms は Python 起動と辞書ロードで、解析は 0.15ms。**

読み取れること：

- **1句を打ち終えるたびに1回なら現状のままで耐える**（145ms＝入力の途切れに紛れる）。ただし打鍵ごとに走らせるのは無理（145ms×連打）。
- **通しの面（歌詞全体）を出すのに1句ずつ spawn するのは破綻する**（40句で5.8秒）。**stdin 一括にすれば 149ms＝1回ぶんと同じ**。`accent.py:105-107` はすでに一括対応済みで、`apps/api/src/accent.ts:45` が使っていないだけ。**ここは足す必要がある。**
- 常駐プロセスにすれば 0.2ms まで下がるが、上の数字を見る限り**一括 spawn で足りる**。

## 9. 2層（漢字仮名交じり＝正データ／かな＝仮歌と割付用）にしたとき足す必要があるもの

### 9-1 Python 側（`apps/audio/accent.py`）

いま返していないものを足す。1回の呼び出しで、1つの句について：

## 3. 曲・セクション・句に相当するデータ

### 3-1 今あるもの

`api.getComposition(id)`（`api.ts:392`）が返すのは、この形だけ（`api.ts:528-531`）：

```
CompositionNode = { neta: Neta, children: { position:number, ord:number, node: CompositionNode }[] }
```

- `position` は**拍**。小節ではない（`sectionContext.ts:103` に「×BPB は誤り」という是正の記録）。
- 曲 → セクション → パート（メロ・コード・ベース…）の3階層。`sectionLanes.ts:13-24` がその対応表。
- 1階層ぶんの中身は再帰で全部入って返る（`apps/api/src/core.ts:280-290`）。**曲を1回読めば、全セクション・全メロの音符まで一度に取れる。**

### 3-2 モックの「句」に対応する実体は、無い

| モックが持っているもの | 今のデータ | 導けるか |
|---|---|---|
| 曲 | kind:"song" のネタ | そのまま |
| セクション（名前・小節範囲） | kind:"section" のネタ＋曲の下での position | **導ける。**開始小節＝`position ÷ 1小節の拍数 + 1`（`FormStrip.tsx:420`）。名前＝title、役割＝`role:`タグ |
| **句**（2小節くらいの区切り・表記・音符・読み） | **無い** | **導けない。**メロは1つのネタに音符が一続きで入っているだけで、どこが句の切れ目かという情報がどこにも無い |
| 句の**表記**（漢字仮名交じり） | **無い** | 音符には `syllable`（かな1モーラ）しか無い。型の定義が `packages/music-core/src/index.ts:9-15` で、フィールドは pitch/start/dur/vel/syllable の5つだけ |
| 句の**読み・高低** | **無い** | 上の2-2のとおり、web からは pyopenjtalk に届かない |
| 「メロが無い」「詞が無い」の区別 | 部分的 | 音符が無い＝メロが無い、`syllable` が無い＝詞が無い、は音符単位では分かる。ただし「詞は書いたがメロがまだ」は表現できない（詞の置き場が音符しか無いため）。**オーナー裁定3「字余りとメロ未定を分ける」は、今のデータでは原理的に分けられない。** |

**句の切れ目に一番近いものが1つだけある**：kind:"skeleton"（骨格）のネタが `phrases: [{endBeat, cadence}]` を持つ（`useNetaEditor.ts:153`、保存は `useNetaEditor.ts:339`）。ただしこれは骨格ネタの中の話で、メロネタとは別ネタ・別レーン（`sectionLanes.ts:16`）。**メロの句を骨格から借りる設計は、骨格ネタが存在する曲でしか成立しない。**

### 3-3 気をつける点（実コードから）

- `formStrip.ts:77-89` に「同じセクションを2回置いたとき、2個目の中身は空で返る」という注記がある。一方 `apps/api/src/core.ts:280-290` の実装は、経路ごとに循環を見るだけなので2個目も展開されるように読める（`core.ts:276-279` に「昔は空だった、直した」と書いてある）。**日付は formStrip 側（7/16）が core 側の修正（7/4）より新しい**ので、どちらが実態か実データで確かめる必要がある。**1番と2番が同じセクションを共有している曲では、通しの面が「2番の中身が空」になるかどうかがここで決まる**ので、着手前に確かめること。
- 同じセクションを1番と2番で使い回すのが既定（`FormStrip.tsx` の「共有N」バッジ・×N畳み）。**「同じメロに違う歌詞」は、今のデータの持ち方だと「同じネタを共有している」＝歌詞まで共有されることになる。**別々の歌詞を持たせるには分家（`api.ts:181` `vary`）を作ることになり、分家すると「同じメロ」という繋がりは `variant_of` のリンクにだけ残る。欠陥9（1番と2番を突き合わせる）はここに絡む。

## 4. 状態管理と保存

### 4-1 保存の作法（「編集画面は onChange で自動保存」の実体）

`useNetaEditor.ts:434-520` が本体。

- 画面上の値をぜんぶ1つのJSON文字列にまとめ（`useNetaEditor.ts:494`）、**それが変わったら600ミリ秒後に自動でサーバへ送る**（`useNetaEditor.ts:497-509`）。明示の「保存」ボタンは無い（`useNetaEditor.ts:435-436` に廃止の記録）。
- 画面を離れるとき・タブを閉じるときに未送信ぶんを送る（`useNetaEditor.ts:511-520`）。`keepalive` を付けてリロード中でも落ちないようにしてある（`api.ts:170-171`）。
- 「保存済／保存中／未保存」の3状態を持ってヘッダに出す（`useNetaEditor.ts:438`・`NetaDialog.tsx:60`）。
- **落とし穴**：初回レンダは送らない（`useNetaEditor.ts:498-500`）。ここを踏み外すと、開いただけで全ネタが更新扱いになる。
- 共有されているネタを編集するときは「全部に効かせるか／この曲だけ変えるか」を1度だけ聞く仕組み（`useNetaEditor.ts:445-447`・`useCowGuard.ts`）。**通しの面から句を直接編集するなら、この確認をどう通すかを決める必要がある**（今は編集画面が1つのネタを開いている前提で組まれている）。

### 4-2 保存の経路は1本ではない

- 編集画面本体＝上の自動保存。
- セクションの設定（小節数・レーンの表示）＝`SectionEditor.tsx:131-140` の `writeSelf` で、投げっぱなし（返事を待たない）。
- 曲フォームの並べ替え・役割の付与＝`FormStrip.tsx:257` で `api.updateNeta` を直接呼ぶ。
- 骨格の机＝自前の500ミリ秒待ち保存（`SkeletonDesk.tsx:55`）。

**＝新画面は自分の保存を自分で持つのが今の流儀。**共通の保存置き場は無い。

### 4-3 端末に残る状態

- 選んでいるプロジェクト（`App.tsx:38,170-173`）、チャットのセッションid、トレイを見た時刻（`App.tsx:340`）。localStorage 直書き。
- **モックv8の「表示するパーツの選択」を覚えるなら、ここと同じ流儀（localStorage）になる。**サーバに持つ仕組みは無い。

## 6. 分からないこと（オーナーに聞く／実データで確かめる）

1. **同じセクションを1番と2番で使い回している曲で、通しの面に2番の中身が出るか。**`formStrip.ts:77-89` の注記と `core.ts:280-290` の実装が食い違う。実データで確かめないと断定できない。
2. 1番と2番で歌詞だけ違うとき、今のデータでは「セクションを分家する」しか手が無く、分家すると「同じメロ」という繋がりはリンクにしか残らない。**この扱いをどうするかは設計の判断で、まだ決まっていない。**
3. 通しの面から句を直接編集するとき、共有ネタの「全部に効かす／この曲だけ変える」確認（`useCowGuard.ts`）をどう見せるか。今の仕組みは「編集画面が1ネタを開いている」前提。
