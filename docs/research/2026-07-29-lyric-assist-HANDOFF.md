### 1-1. 作り方・使う場面について

- 曲先（メロが先）と詞先（詞が先）は1曲の中で往復する。往復の粒度について——
  > 往復はSection単位なんて言ったっけ？ **どこでも開くのが正しい**
- 穴（未完成の箇所）は最小1単語から、大きければ曲全体が斑。粒度は 曲 > セクション > パート > 句 > 語 と入れ子で、詞側とメロ側が独立に欠ける。詞もメロも両方とも空白の区間が普通にある。曲の初期状態が「モチーフ一節しかない」こともある。
- 詞の途中の欠落の例＝`xxxxx yyyyy zzzzzz wwwww` と4区切りにできる歌詞で、z だけ無い／z の後ろ半分が無い／z の中の単語1個が無い。
- 書くのは通しではない。ただし推敲は必ず通しでする。推敲で見ているのは (i) 意味が通らなくならないこと (ii) 聞き手の感情遷移 (iii) 音韻の通しでの確認 (iv) イントネーションの確認。
  > 音韻のチェックとかする以上、**現状の歌詞全体はみえるべき**だと思うよ
- 「曲全体を見る」のは曲単位の別の話で、ここで論じているのは「歌詞全体を見る」話（オーナーによる語の使い分けの訂正）。
- メロ側・詞側の**両方に困っている**（どちらか一方に苦心が偏ってはいない）。
- 仮の句（プレースホルダの歌詞）はあまり使わない。やるとしても「メロだけ置く」形。可能なら仮歌用の無意味語を入れられてもよい（あれば嬉しい程度・必須ではない）。
- 同じメロに複数の歌詞案を並行保持することはほぼしない。
- 絞り込みの順は「意味を前提にそこから音」が典型。ただし——
  > **固定ではない、これは固定してはいけない**
- 意味側からの入口の具体例＝「**ここに『通り過ぎる』という言葉で、3文字、このアクセント**」というパズル。
- 原点はスマホ・出先の細切れ時間。自宅の机でも使う。
  > **デスクトップパソコンをことさらに意識せずスマホベースでどっちも。なぜなら仕上げはDAWとか別のもの使うから**
- 言葉づかいについて——
  > **強い言葉はいらない。イメージを誤るので**
  > **恒等の意味はわからん。内輪語になってない？？**

### 1-5. データの持ち方の議論（原文・時系列）

> 歌詞エディタと曲エディタで根本的にデータの持ち方が衝突するってことかな？ 設計思想で最も正しい持ち方を考えると、**メロディに対して歌詞を適用すると、符割りに基づいて仮歌用の歌詞が入ること**、だけどこれはできないんでは？ 次善策としては**メロディに歌詞とシラブルを入力させてしまう**。これは実務上は非常に強力かつ現状にフィットする。どちらがいいですかね、**メロと歌詞は不可分かなとは思うけど**、メロディの繰り返し構造を持つためにメロディを再利用するユースケースと衝突します。トレードオフないしはメロディに対する歌詞の流し込みで技術的な解決の必要な話に見えます。

> 多くの場合は歌詞を流し込む形がきれいかなと思うんだけど、メロディが違ってしまう場合があるんだよね。**そもそもの言い回しによって符割りで対応できなくて音符を減らす増やすするパターンがありえて、このパターンはメロディが派生する。この場合は歌詞と仮歌シラブルとメロディは不可分[の方が]面倒ない。** そうなるとこのパターンの場合歌詞エディタは曲につくが正データはメロディにある。流し込みなら曲データに歌詞がある。うーん、**これ双方から操作したいな、データの持ち方はともかく操作としてはメロディからも曲からも歌詞は修正したい。** 正データがどこか、**メロのないところに歌詞があるからそれは曲にしか持てないか。** ちょっと面倒ですねこれ。もともとの実装計画だと曲に歌詞がありその位置のメロディに流し込める？

> **いやメロがわかれるのは良くて、一番と二番の同じパーツでもアレンジが違うことはあるからセクションすら別になっても変ではない。過剰に分派が生まれるのを避けなくても良い。**
> **ネタとしてのメロディは歌詞が組み合わさったものと素のままのメロディは別？？** 元のメロディ変えたからと仮歌込みのメロディの修正は手でやりたい？？ **いや軽微なら変化の適用はされたい。**
> 正データというか**歌詞エディタで全体を見るのは曲全体にやるのは確定**、んじゃそれを構成する正データがどこがいいか？ **メロがないと歌詞が書けないなら底にメロを置くか曲が歌詞を持つべき。**
> **ここは設計の正念場で簡単に決められないよ**

> **アレンジは基本少しずつ違うもんだよ？ 割とボクは分派ベースに頭が偏ってる。つまり空のメロディを作る方のが無難な気がするな、その代わりコピーとかを充実させるとか。** 議論は出揃ってきたから頭きれいなOpusにまとめてもらう？

### 4-1. 最優先＝歌詞の正データをどこに持つか

**オーナーの発言はこう動いています（全部原文）。**

- 「メロのないところに歌詞があるからそれは曲にしか持てないか」（自問）
- 「底にメロを置くか曲が歌詞を持つべき」（両案併記）
- 「空のメロディを作る方のが無難な気がするな、その代わりコピーとかを充実させるとか」
- 「セクションではなく仮歌を入れるメロディにほしい。Sectionに歌詞ってなんか違和感がある」
- 「ただ、プレイスホルダー用の空メロディができるのは見た目には微妙ね。ネタ帳からは非アクティブで見えなくする？？ プレイスホルダーのシングルトン的空メロディはなにかが入った瞬間新しいメロディを産むとか？？」

**確定しているのは「仮歌を入れる先はメロディ」「セクションには置かない」の2点まで。** 残っているのは**メロがまだ無い場所（詞先）の歌詞をどこが持つか**で、案は現在3つあります。

- 案(あ) **曲（song ネタ）が持つ**。メロが後から来たら、そのときメロへ移す。
- 案(い) **人が「ここにメロを置く」と合図して、空のメロを置き、そこに書く**（＝オーナーが「無難」と言ったほう）。
- 案(い)の見た目の問題に対して、オーナーから新しく2つの案が出ています。
  - **(い-a) 空のメロはネタ帳（一覧）からは非アクティブとして見えなくする。**
  - **(い-b) プレースホルダー用の空メロは1つだけ共有しておき、何かが入った瞬間に新しいメロディを産む。**

**これを決めると何が決まるか。**

- 詞先で書いた歌詞の保存先が決まる（曲の中／人が置いた空のメロの中）。
- **通しの面が「複数のネタの句を時間順に並べて併合する仕組み」を必要とするかどうかが決まる。** 案(あ)なら要る。案(い)なら、詞はすべてメロの中にあるので併合の枝が丸ごと消える。
- **詞とメロが後から出会ったときの操作**が決まる（歌詞が曲からメロへ移るのか、置いた空のメロにそのまま音符が入るのか、人が何を合図するのか）。
- 案(あ)を選ぶと、続けて「曲の構成を並べ替えたとき、まだメロの無い歌詞は付いてくるか、その場に残るか」を決める必要が出る。案(い)なら詞はメロと一緒に動くのでこの問いが消える。
- 案(い)を選ぶと、続けて (い-a)(い-b) のどちらを作るかを決める必要が出る。(い-b) は「空メロが1つだけ存在して、何か入ると新しいメロを産む」という振る舞いなので、実体を作る合図の扱い（オーナー裁定「実体を明確に作る合図なければ作られたくない」）とどう折り合うかが同時に決まる。
- **縦スライス5（曲持ちの句と通しで読む面／後述）を丸ごと作るか落とすかが決まる。**

**この判断に効く実測（コードで確認済み）。**

- **音符が0個のネタは、尺の計算で1小節として数えられる**（`apps/web/src/sectionContext.ts:81` と `:88`＝音符が無ければ `ctx.BPB` を返す）。空のメロを置くと、その位置の曲の長さの計算がその分ずれる。案(い)を採るならここに手当てが要る。
- **曲（song / section）は「中身を持たない親」として設計されている**（`docs/design.md:191`、`:247`「合成(section/song)：content でなく `compose_edge`（子＋position）で表す」）。実装も同じで、自動保存は container のとき `{key,mode,tempo,meter}` しか返さない（`apps/web/src/useNetaEditor.ts:347`）。案(あ)を採るなら、この決めに例外を書き足すことになる。
- **メロの自動保存は content をキー決め打ちで作り直す**（`apps/web/src/useNetaEditor.ts:334`）。メロの中に歌詞を置くと、音符を1つ動かした数秒後に消える。これは直せる欠陥（同じ理由で `feel` が落ちていた前例が同ファイルにある）。
- **DB スキーマの変更・移行は不要**（`content` は素通しの JSON・`apps/api/src/schemas.ts:17` が `z.unknown()`）。どの案でも同じ。

### 4-2. 仮歌はどこまで自動でできるか（＋字余りのまま鳴らしたら）

オーナーは「メロディに対して歌詞を適用すると、符割りに基づいて仮歌用の歌詞が入ること」が最も正しいと言い、同時に「だけどこれはできないんでは？」と保留しています。設計の改訂案では当面「人が『合わせる』を押したときだけ音符が変わる」としています（「当面の形であって決めた形ではない」と明記）。

**決めると**：詞を書き直してから仮歌で確かめるまでに人の手作業がどれだけ残るか＝この道具の中心の往復の手数が決まる。あわせて、字余りのまま鳴らしたとき余ったモーラをどうするか（歌わない／最後の音符に詰める／鳴らさず知らせる）が決まる。

### 4-3. 元のメロを直したとき、複製した先にどこまで及ぶか

「いやメロがわかれるのは良くて」と「いや軽微なら変化の適用はされたい」が同居していて、「軽微」の線引きが未裁定。

**決めると**：複製した1番と2番が黙って別々のものになるのか、細く繋がったままなのかが決まり、「コピーと比較を強くする」の中身（比較の面が何を見せる場所になるか）が決まる。

### 4-4. 「同じメロのまま詞だけ違う」をどうやるか

Q1 の答えは「やることもある」。いまの設計案の答えは「複製する」だけで、複製すると「同じメロ」という繋がりは残りません。

**決めると**：2番を作る操作の手数と、1番2番の繋がりがデータに残るかが決まる。あわせて、共有されたメロに詞を書こうとしたとき何を聞くべきかが決まる（→ 5-6 の実測を参照）。

### 4-5. 1番と2番の差を見る面を、最初に作る範囲に含めるか

「ほしい。優先度は高いかはわからない」。

**決めると**：複製で進める作り方（「代わりにコピーとか比較とかを強くすればいい」が前提）が成り立つかを、いつ確かめられるかが決まる。

### 4-6. 作詞の発散として何を出してほしいか

「双方あるのが良い」までは確定。何を出すか（語の候補／韻／「3文字・このアクセント」に嵌る言い方／別の言い回し）は語られていない。

### 4-7. 通しの推敲の面に何が見えるか（意味・感情遷移のために何を出すか）

推敲で見るのは4点だが、機械が踏み込まない意味と感情遷移を人が確かめるために面に何を出すか（人が書いたメモを通しの面に出すのは踏み込みか）が未定。

**決めると**：4点のうち画面が受け持つ範囲と、人が頭の中でやる範囲の線が決まる。

### 4-8. ハモ（counter）に詞を書きたいか

設計案は今回メロだけを対象にしている（データの形は同じにして後から足せるようにする、という範囲の限定）。

**決めると**：通しの面に何行出るかと、仮歌で何声鳴らすかが決まる。

### 4-9. 句の範囲の既定

設計案は「メロを開いて書き始めたら、範囲の既定はそのメロの全体。人が切れば分かれる」で進める案。

**決めると**：下書きと曲に同じ言葉が二重にあるときの付き合い方が決まる。

### 4-13. 設計案が当面決めているが、オーナーの明示裁定が無いもの

### 5-1. 歌詞という保存物は存在しない

### 5-4. 画面から日本語の読みに届く経路が1つも無い

- 画面が叩ける `/music/:op` は35個あり、**歌詞系はゼロ**（`apps/api/src/http.ts:201-385`）。読み取りに繋がっているのは MCP のツール2つだけ（`apps/api/src/mcp.ts:998`・`:1282`）。
- そのため**いま PianoRoll に出ている赤黄は、9語だけの内蔵辞書で動いています**（`packages/music-core/src/prosody.ts:185-195`・`apps/web/src/lyricFit.ts:31` はブラウザ内で同期計算＝サーバも Python も呼ばない）。9語のうち核を持つのは「はし=1／そら=1／ゆめ=2」の3語だけで、**それ以外の語を含む歌詞では読みの下がり目が生じず、一番効く印（読みが下がる所をメロが上がって裏切る）が出ません。**
- `/music/:op` は switch 全体を1つの try/catch で包み、**投げられたものを全部 400 に落とします**（`http.ts:381`）。読み取り失敗を「入力が変」と区別したいなら、新しい case の中で自分で 502 を返す必要があります。

### 5-5. Python 側の実測

- `apps/audio/accent.py:95` は**ローマ字の音素しか返しません**（`["ni","wa","e"]`）。表記からかなを返す経路はリポジトリに1つも無い。
- `pyopenjtalk.run_frontend` は語ごとに `{表層, read, pron, mora_size, 品詞}` を返す。実測：「庭へ」→ 庭/ニワ/ニワ/2＋へ/ヘ/**エ**/1。`read` と `pron` は助詞で必ず割れる。`pron` にはアクセント記号「’」が混ざる（靴→`ク’ツ`）＝除去が要る。`pron` は長音を必ず「ー」で返す（今日→キョー）。
- `run_frontend` の `mora_size` 合計と `accent.py` の `mora_total` は試した全ケースで一致。追加費用は **0.02ms/回**（同一プロセス内・200回計測）。
- **所要時間**：1句1回＝125〜149ms（中央143ms）／40句を順番に起動＝**5,799ms**／並列8で1,591ms／**40句を標準入力でまとめて1回＝149ms**。145ms のうち約144ms は Python の起動と辞書の読み込みで、解析は0.15ms。`accent.py:105-107` は一括受けに対応済みで、`apps/api/src/accent.ts:45` が使っていないだけ。
- ＝**通しの面を1句ずつ呼ぶと破綻します。まとめて渡せば1回ぶんと同じ。**

### 5-6. 1番2番・複製まわり

- **複製の来歴が残らない**：`copyNeta`（`apps/api/src/core.ts:88-117`）は元ネタへの繋がりを一切記録しない（`vary` の `variant_of` とは非対称）。
- **共有されたメロへの書き込みに確認が出ない経路がある**：`apps/web/src/useCowGuard.ts:70` は `parentId` が無いと何も聞かずに原本へ書く。`parentId` は曲/セクションから潜ったときだけ付く（`apps/web/src/App.tsx:770`）。ネタ帳から直接メロを開くと確認が出ない（`apps/web/src/components/NetaDialog.tsx:36-37` にバッジで補っている旨のコメントがある）。
- 「この曲だけ変える」が呼ぶのは**分家**（`vary`＝子は共有）で、確定した作り方（複製）とは別物。
