## 3. 音符に写した歌詞をどこに置くかが書かれていない。保存すれば結論の売りが崩れ、その場計算なら工事が3つ増える

### 作業が回るか

## 1. 1番と2番に別の詞を持たせる操作が、今の分家では作れない（結論の売りが成立しない）

**何が問題か**：「同じセクションを2回置いて分家すれば詞だけ別になる」は、コードの実装と食い違う。

**結論案のどこか**：§3「同じセクションを2回置いている状態で2番の詞を書くと、1文字目で『全部に効かす／この曲だけ変える（分家）／やめる』が出る…これがオーナーの言う『メロは同じで詞が違う』形そのもので、**追加実装ゼロで手に入る**」／§5-(2)「2番を作る操作を、分家（vary）に寄せる」。

**何が起きるか**：`apps/web/src/useCowGuard.ts` の分家処理は、こう書かれている。

```ts
const edges = pcomp?.children.filter((c) => c.node.neta.id === neta.id) ?? [];
for (const e of edges) {
  await api.removeChild(opts.parentId, neta.id, e.position);
  await api.placeChild(opts.parentId, branch.id, e.position, e.ord);
}
```

＝**その親の下にある「そのセクションの全部の配置」を、1つの同じ分家へ差し替える**。1番と2番が同じ曲の中の2配置なら、「この曲だけ変える」を選んでも 1番も2番も同じ新セクションを指す。詞は結局1つのまま。「全部に効かす」を選んでも当然1つ。**どちらを選んでも1番と2番で違う詞にはならない。** 実データ `68_Aメロ` は `68_SONG` の position 0.0 と 12.0（実測）＝この経路に必ず入る。

「配置ごとに別の詞」を得るには配置を1つずつ指す仕組みが要る＝結論案が§2で落とした「配置ごと」案の中身そのもの。追加実装はゼロではなく、落としたはずの案を作ることになる。

**どう直すか**：(a) 分家を「配置1つだけ差し替え」に直す（`useCowGuard.ts` の for を「今いる配置1本だけ」に限定し、通しの面から配置の位置を渡す）か、(b) 1番/2番の作り分けは分家でなく**セクションを複製して置き直す**（＝オーナーの「コピーを充実させる」）と認め、§3と§5-(2)を書き直す。どちらにせよ「追加実装ゼロ」は撤回。

## 3. 同じメロに2つの詞を同時に置けない（写しの置き場がネタ1個ぶんしか無い）

**何が問題か**：詞をセクションに置いても、音符へ写した読みはメロネタ1つの中に1組しか入らない。

**結論案のどこか**：§3「音符に写した歌詞（`Note.syllable`）…仮歌に歌わせる・音符の中に文字を出す・アクセントの色を出す、その3つの出口のための写し。**句の範囲に重なる音符では句の読みが正**」。

**何が起きるか**：`Note.syllable` は `packages/music-core/src/index.ts:9-15` のとおり音符1つに文字列1本。書き先はメロネタの `content.notes`。仮歌は `/neta/:id/sing`（`apps/api/src/http.ts:721-737`）と `apps/api/src/sing.ts:141-148` が**そのネタの音符に載っている文字**を送る。赤黄も `apps/web/src/lyricFit.ts:31` が同じ音符を見る。

つまり「メロは同じ・詞だけ違う」状態を作れたとしても、

- 1番の詞を写した瞬間に2番の写しが消える（同じ音符だから）
- 仮歌は1番か2番のどちらか一方でしか鳴らない
- 音符の中の文字・赤黄も片方だけ

＝**結論が定義した3つの出口が、結論が守りたかった状態でだけ機能しない。**

しかもこれはセクションを跨がなくても起きる。実データ `検収-Aメロ-20260714` は、**1つのセクションの中に同じメロネタ `f01d9ba2` を position 0.0 と 64.0 の2回**置いている（実測）。ここに前半と後半で別の句を書けば、同じ音符に2組の読みが要求される。

**どう直すか**：写しを保存しない（画面を出すときだけ組み立てて、仮歌の呼び出しにも詞を引数で渡す）と決めるか、写しの置き場を「メロネタ＋どの配置か」の組にすると決める。前者なら `sing.ts` と `/neta/:id/sing` の入口を「音符＋詞」を受ける形に変える工事が§4に足りない。どちらにせよ§3の1行規則では足りない。

## 4. 白紙の曲では1語も書けない（曲案を落とした理由が、そのまま自分に当たる）

**何が問題か**：セクションが1つも無い状態で、詞の置き場が無い。

**結論案のどこか**：§2「曲に置くと、この詞には置き場が無い…**育てている途中は詞が書けない**」を曲案の落とす理由にしている。§3「メロが無い場所の歌詞＝句だけ置く」。

**何が起きるか**：句はセクションの中にしか存在できないので、思いついた1行を書くには先に「曲を作る→セクションを作る→（拍範囲を決める）」が要る。裁定5「実体を明確に作る合図なければ作られたくない」・裁定4「暗黙の操作はあまり増やさないでほしい」があるので、勝手に作るのは禁じ手。＝**スマホの細切れ時間に思いついた1行を置く**という原点の入口が、セクション作成の手数で塞がる。v6の欠陥11（白紙の曲で「並びに入れる」の行き先が無い）も未解決のまま。

曲案を「育てている途中は書けない」で落とした基準を1段下ろすと、そっくり同じ形でセクション案に当たる。結論はこの対称性に触れていない。

**どう直すか**：白紙の曲で最初の1行を書く動線を具体的に書く（例：通しの面に「まだセクションに入れていない詞」の置き場を作り、あとでセクションへ移す）。それをセクション案の一部として認めるなら、置き場は「セクション」一本ではなくなるので§1の言い方も直す。

## 5. 句が範囲（拍）を自分で持つ、が詞先で成り立たない

**何が問題か**：まだメロが無い段階で「セクションの頭から何拍目・何拍ぶん」を決めさせることになる。

**結論案のどこか**：§1「句が自分の範囲（セクションの頭から何拍目・何拍ぶん）と…表記を持つ」／§3「『メロなし』『字余りN』『あとN音』は、句が自分で持っている範囲と、その範囲に重なる音符の被り方から出す（**範囲を音符から導かない、が必須条件**）」。

**何が起きるか**：

- **詞先のとき**：メロが無いのに拍を決めないと句が置けない。オーナーが詞側で使う物差しは「3文字、このアクセント」＝**音数**であって拍ではない。道具の側が先に音楽的な決定を強いる。裁定6「予定は…オプショナルで必須にしない」とも噛み合わない。範囲を空にできる作りにするなら、§3の状態表示（メロなし／字余り／あとN音）は全部出せなくなる＝結論の裏付けが崩れる。
- **弱起**：`PianoRoll.tsx:122-137` は負の拍（弱起）を扱う。実測で**歌詞のある実メロ「みなそこイントロ」の先頭は -0.5拍**（104件中この1件だけだが、まさに詞が入っている1件）。「セクションの頭から何拍目」では、この曲の1文字目を指せない。
- **あとでメロが変わったとき**：範囲を音符から導かないと決めた以上、符割りが変わっても範囲は自動で追随しない。発言(b)の「音符を減らす増やす」は日常なので、**そのたびに全部の句の範囲を人が引き直す**ことになる。

**どう直すか**：範囲を「任意（空でよい）」と決め、空のときに何が出て何が出ないかを§3に書く。弱起のために負の拍を許すと明記する。「範囲を音符から導かない」は必須条件のままでよいが、**メロが変わったときに範囲がずれたことを見せる**（自動で直さない）仕組みを§4に足す。

## 6. 「語1つの穴」が表せない

**何が問題か**：句が「表記1本」なので、句の中の一部だけが無い状態に置き場が無い。

**結論案のどこか**：§1「句が…**漢字仮名交じりの表記**を持つ」。

**何が起きるか**：オーナーの言う欠け方は `xxxxx yyyyy zzzzzz wwwww` の「z だけ無い／z の後ろ半分が無い／z の中の単語1個が無い」。句＝表記1本だと、真ん中の1語だけ無い状態は「文字列の途中に何か目印を書く」しかなく、その目印は読み取り（pyopenjtalk）に食わせた瞬間に読みを壊す。裁定2の「しっかりよくハマってるのか、そもそも歌詞がないメロがないのか」＝**嵌り具合を出す**ための材料が、句より細かい粒度で作れない。

**どう直すか**：句の中を「決まっている語」と「まだ決まっていない枠（音数・アクセントの条件だけ持つ）」の並びにするか、句をもっと細かく切れることにする。どちらにせよ§1の「表記を持つ」1行では足りないので、そこを書き足す。

## 7. 一方向の写しで、既存のかな入力が黙って消える

**何が問題か**：「既存の口を1つも殺さずに済む」が、実際には「上書きで静かに失う」。

**結論案のどこか**：§3「流し込みの向き＝一方向…**音符から歌詞へ戻す向きは作らない**」「これで既存のかな入力口（`set_lyric`・ピアノロールの流し込み欄・詞モード・詞先メロ）を**1つも殺さずに済む**」。

**何が起きるか**：詞モード（`PianoRoll.tsx:224-261`）で音符に手で打ったかなは、その音符に句が重なった瞬間に句の読みで上書きされる。戻す向きが無いので、打った内容はどこにも残らない。`flowLyric`（`apps/api/src/lyric.ts:57`・`apps/web/src/lyrics.ts:58`）は**全音符を頭から無条件に上書き**する実装で、保護する引数が無い。＝「殺していない」のではなく「消えるまで気づかない」。要件の「データを失わない」に正面から当たる。

**どう直すか**：句が重なっている範囲では音符のかなを直接打てないようにする（口を閉じる＝殺すと明記する）か、手で打った値を「手で直した」として残す置き場を作る（裁定1の後半と同じ置き場でよい）。§3の「1つも殺さずに済む」は撤回。

## 8. 通しの推敲が、実データでは成立しない

**何が問題か**：詞がセクションにあり、通しの面が曲を辿る以上、曲に入っていないセクションの詞は通しに出ない。

**結論案のどこか**：§6-2「曲に入っていないセクションに詞を書きたいか」を**問いのまま**残して結論を出している。

**何が起きるか**：実測でセクション22件のうち曲に入っているのは3件（結論案の数字は正しい）。逆に言うと**19件は通しの面に出ない**。歌詞のある実メロ4件のうち、通しに出せるのは Cメロ一回目・二回目の2件だけ。「推敲は必ず通しでする」は確定事項なので、**確定事項が実データの半分で成り立たない状態**を、未回答の問いに預けたまま結論にしている。

**どう直すか**：この問いは結論の前に答える（＝オーナーに先に聞く）。§6の5問のうち、これと6-1は「結論を出す前提」であって「出したあとの確認」ではない。

## 9. 「メロ単体では詞欄を出さない」の代償が、唯一でも小さくもない

**何が問題か**：この制限が当たるのは例外ではなく、実データの歌詞の半分。

**結論案のどこか**：§3「**メロをネタ帳から単体で開いたときは、詞の欄を出さない**…これはメロ案なら起きなかった制限で、セクション案が払う**唯一の代償**」／§6-3。

**何が起きるか**：実測で歌詞（音符のかな）を持つメロ4件のうち、`68_melody` は**親が1つも無い**、`みなそこイントロ` の親セクション `組み合わせテスト` は**どの曲にも入っていない**。＝4件中2件は「単体で開くしかないメロ」。この2件では詞の正データに一切触れない。オーナーの「往復はどこでも開くのが正しい」と、曲に置いていないメロに仮歌を当てる今の作り方に、そのまま当たる。さらに上の1〜3・7と合わせると代償は「唯一」ではない。

**どう直すか**：「単体で開いたメロにも詞を書け、そのメロがあとでセクションに入ったときに句へ引き継ぐ」道を作るか、代償の大きさを実測（4件中2件）どおりに書き直す。

## 10. 結論の効き方を決める前提が、未回答のまま（しかも発言は逆を向いている）

**何が問題か**：結論を支える場面が「起きるかどうか分からない」と自分で書いている。

**結論案のどこか**：§6-1「1番と2番で『同じメロのまま詞だけ違う』を実際にやるか。**これだけが結論の効き方を変える**…実データはCメロ1/2が別物で、n=1」。

**何が起きるか**：結論の柱（§1の「一番大事な点」、§2-(a)、§5-(1)）は全部この場面のためのもの。ところがオーナーの発言(d)は「**アレンジは基本少しずつ違う**」＝この場面は典型ではないと言っている。実データも別物（n=1で反例側）。**典型でない場面のために選んだ、と読める構図**になっている。しかも上の1と3で、その場面自体が今の仕組みでは作れない。

**どう直すか**：6-1を先に聞く。聞かずに進めるなら、柱を「同じメロのまま詞だけ違う」に置かず、§2の他の理由（曲に入っていないセクションに詞がある／自動保存が壊さない／音符ゼロでも置ける）だけで結論を立て直す。この3つは実測に支えられていて、1〜3の指摘を受けても崩れない。

## 11. 「先に直す6つ」に抜けている3つ

**何が問題か**：先に直さないと通しの面から句を書けないものが表に無い。

**結論案のどこか**：§4「先に直す必要があるのは次の6つ」。

**何が起きるか**：

- **配置を指す手段が無い**：`getComposition`（`apps/api/src/core.ts:280-290`）が返すのは `{neta, children:[{position, ord, node}]}` だけで、配置そのものの識別子は無い。1と3を解くなら「どの配置か」を画面から渡す必要があり、この形のままでは渡せない。
- **曲に入っていないセクションでは共有の確認が効かない**：`useCowGuard` は `parentId` 未指定なら**ガード完全無効**（同ファイル冒頭の注記どおり）。§4-6 の「通しの面は必ず曲を親として開く」を採ると、曲に入っていない19件のセクションを開いたときに親が無い＝確認なしで原本に書く。
- **新画面を足すときの必須3箇所**：`App.tsx` の画面分岐（`:718-803`）・`closeTop()`（`:101-121`）・`anyOpen`（`:126-128`）。棚卸しに「ここを踏み外すと戻るでアプリを抜ける・過去に2回バグった」と記録がある。通しの面は新画面なので必ず当たる。

**どう直すか**：§4の表に3行足す。

---

**この結論で進んでよいか＝直してから。** 一番の理由：置き場を「セクション」にすること自体は実測（歌詞のある実メロの親セクションが曲に入っていない・コンテナの content は自動保存で壊れない・音符ゼロでも置ける）で支えられていて残せるが、**結論が「一番大事な点」として掲げた分家の話は、コードを読むと成立しない**（分家は同じ親の全配置をまとめて差し替える／写しの置き場がメロネタ1個ぶんしか無い）し、それを裏付けるはずの実データ（Cメロ1と2が伴奏を共有している）も実測では複製だった。この2本を撤回して理由を組み直さないと、正しい置き場を間違った理由で選んだことになり、次の設計判断（1番と2番の作り分け・仮歌の鳴らし方）がそこから連鎖して外れる。
