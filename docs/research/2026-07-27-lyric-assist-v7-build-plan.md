# モックv7 制作計画

## 1. v7で何を直し、何を足すか

### 出発点の整理
v6は「状態の網羅図」としては閉じているが、**書く道具としての操作が欠けている**。欠陥1〜13の大半は「操作の不在」で、これは個別の描き漏れではなく「編集画面＝句に固定・候補は眺めるだけ」という骨組みから来ている。よってv7は「19件を1つずつ塗る」のでなく、骨組みを直して大半を一括で消す。

### 必ず足すもの（事実に直結）

- **自分の言葉を書き入れる欄**（欠陥1）。編集画面の最上位に置く。候補より上。根拠＝「作る努力の部分を人間から奪うと自作感がなくなる」「最後に選ぶのは人間」。候補は下からのシートのままでよいが、主役は入力欄。
- **通しの面での直接入力の拡張**（欠陥1の裏面）。裁定1の原文は「その場で打てたら最善」であり、v6は「語1つ程度」に先回りで妥協していた。v7では**通しの面の詞テキストは全てその場で打てる**姿を描く。複雑になるのは候補・断片・意味欄であって、文字を打つこと自体ではない。複雑さの判定はオーナーがモックを見てする（裁定1の枠内）。
- **候補を句に入れる操作＋入れた後の取り消し**（欠陥3・8）。「入れる」→入った直後の絵→「戻す」まで1連の絵で描く。※裁定2との関係は§3参照。
- **編集画面が開く単位を「句固定」から「範囲」へ**（欠陥12）。根拠＝「どこでも開くのが正しい」「穴は1語から曲全体まで」「パート（Bメロ4分割の3つ目）」。詳細は§2。
- **両方埋まった句を開いた絵**（欠陥2）。推敲は必ず通しでする以上、埋まった句を開いて直すのが最頻の作業のはず。書き換え・消す・同じメロを使う他の句の参照（事実表示）を入れる。
- **メロ側の候補一覧**（欠陥4）。「メロ側・詞側の両方に困っている」ので詞側だけ2案まで描いてメロ側が白紙なのは非対称。矩形表記の断片候補＋事実バッジ（音数・読みの高低との関係）。ただし既決（Orpheus型二段DP不採用）に沿い、「アクセント厳密一致のメロを作る」と読める見せ方はしない。一致度は候補に付く事実であって保証ではない。
- **音韻タブの選択状態の絵**（欠陥5）。推敲4点の(iii)。見せ方は枚2と同作法（文字の時間揃え＋付け足しの印）で、中身は母音・韻の対応。具体の記法は設計裁量で1案描き、目視裁定に回す。
- **新しい断片を放り込む操作**（欠陥7）。「まだ並びに入れていないもの」に「＋断片を置く」の入口。初期状態が「モチーフ一節しかない」ことがある以上、置き場に入れる手が要る。
- **白紙の曲での「並びに入れる」の行き先**（欠陥11）。裁定4・5に従い、暗黙にセクションを作らず「どこに置くか／新しくセクションを作る」の明示確認を挟む絵。
- **メロ未定の場所にアクセント条件を置く欄**（欠陥10）。予定の記入フォームに「読みの高低（任意）」を足し、候補依頼の条件に「使いたい語（任意）」を足す。根拠＝「ここに『通り過ぎる』という言葉で、3文字、このアクセント」のパズルの原文そのもの。裁定6（すべて任意）の形式は守る。
- **赤黄の印の規則の定義**（欠陥19）。§5とセットで、v7では印を手置きせず規則から導出する。提案する規則＝「同一アクセント句内の隣接モーラ対で、読みの高低の変化（H→L / L→H）とメロの上下が逆＝赤」。読みが平らな対（H→H・L→L）は**判定対象外＝印なし**。これで「平らな区間に閾値が要る」問題は「平らなら黙る」で消える。閾値ベースの「大きく動いたから注意」は導入しない（印なし＝指摘なし、の作法を濁すため）。黄の扱いは§3の裁定待ちへ。
- **表示の不整合の修正**（欠陥14〜18）。小節番号は前奏を勘定に入れて通す（外部DAWと突き合わせる座標だから）。枚7のカードの数え漏れは、数字をデータから機械算出することで構造的に直す。孤立の例はデータ参照制にして実在対象を指す。意味欄は**人だけが書く**と決めて出所問題を消す（「意味に踏み込むと破綻」の原文により、機械はこの欄に書かない。自動が書くのは音の枠欄だけ＝出所明記は現状維持）。間奏2の音数予定は前奏と揃えて「歌なし」にし、予定の例は大サビ（仮）へ移す（裁定3＝設計者裁量）。
- **意味メモを通しの面に出す**（欠陥13の半分）。編集画面の「意味（言いたいこと）」と予定の「メモ」を同一のデータに統一し、通しの面の該当位置に薄く出す。推敲(i)(ii)は人間が歌詞そのものを読んでやる作業なので、機械の注記層は作らない。

### 足さないもの（理由つき）

- **感情遷移の機械表示**。原文「意味、感情遷移は踏み込むと破綻」。通しの面で歌詞が読めること自体が推敲(i)(ii)の場であり、専用レイヤーは作らない。
- **曲の背景・風景を詰める面**。原文「チャットでやるでいい」「優先度は高くない」。遷移図の「チャット（相談）」の橋で足りる。発散の入口を画面として肥大させない。
- **複数歌詞案の並行保持（案スロット）**。原文「ほぼしない」。両埋まり句の編集は上書き＋戻すで表す。
- **仮歌用の無意味語の生成**。原文「あれば嬉しい程度・必須ではない」。v7の主題（場の完成）に含めない。
- **1番と2番を並べる専用画面**（欠陥9の大半）。並べたいという発言は事実に無い。足すのは「同じメロを使う句」の事実表示（裁定2「状況が書かれたい」の範囲）まで。それ以上が要るかは**オーナーに聞く**。
- **点数・順位・下書き/確定ラベル**。既裁定どおり出さない。

## 2. 画面の構成

### 結論＝2つの場は維持。ただし2枚目の定義を変える

- **場1「歌詞全体画面（通しの面）」**：維持。「推敲は必ず通しでする」「現状の歌詞全体はみえるべき」に直結する場。役割を1段広げ、詞テキストの直接入力をここで受ける（裁定1の最善形）。
- **場2「句の編集画面」→「範囲の編集画面」に改める**：開く単位を語・句・複数句・パート・セクション・区間の任意範囲にする。「どこでも開くのが正しい」「穴は1語から曲全体まで」に対し、v6の2小節固定は真っ向から反している（8小節の空きセクションを4回開かされる）。スマホ幅で範囲を選ぶ操作は「句をタップ＝その句／句を長押し→端をのばす＝範囲」程度の1案を描き、複雑さの判定は裁定1の枠でオーナーに委ねる。

3枚目の場（比較画面・発散画面など）は**作らない**。場を増やす根拠になる発言が無く、スマホ基準では場の数がそのまま迷いになる。

## 3. 裁定の仕分け

### 待たずに決めてよい（設計裁量・事実から一意）
- 小節番号の通し方、間奏2の整合、孤立例の指し先（欠陥14・16・18）
- 意味欄＝人だけが書く／メモとの統一（原文「踏み込むと破綻」から従う）
- 赤の印の規則（§1の逆行定義。論理的にほぼ一意）
- イントネーション表示の様式（折れ線）＝明示裁定が無い領域だがv6様式を継続。様式変更の提案はしない
- 前奏・間奏の表記（裁定3で裁量とされた）

### オーナーの裁定を待つ（v7に両案または1案を描いて仰ぐ）
1. **裁定7（既存の未裁定）**：候補の並べ方2案。v7でも両案並置を維持。
2. **黄の印の意味**：案A＝「読みが変化する箇所でメロが平ら（変化が出ない）＝黄」／案B＝黄は高低には使わず音数系（字余り等）に限定し、高低は赤のみ。推しは案B（印を減らす方向。「印なし＝指摘なし」が濁らない）。
3. **範囲選択の操作の複雑さ**：裁定1の「行き過ぎたら妥協」の判定はオーナーにしかできない。
4. **発散の助けの形**：原文「双方あるのが良い」に対し、v7では「条件を減らした候補依頼（意味だけ・音数だけ）」＋既存の相談を描く。これで発散側と呼べるかの判定を仰ぐ。
5. **音韻タブの記法**：1案描いて目視裁定。
6. **1番2番の突き合わせ**：事実表示より先が要るか聞く。

### 裁定に触れる可能性のある提案（黙って上書きしない）
- **「候補を句に入れる」操作の追加**は、v6が裁定2から導いた「『確定にする』の操作は置かない」という注記に形の上で触れる。ただし裁定2の原文が否定したのは「下書き/確定の**色分け＝状態情報**」であり、テキストを句に置く操作そのものではない。v7では状態ラベルを一切作らず「入れる／戻す」だけを置く＝裁定2の趣旨（状態管理はしない、状況は嵌り具合で見せる）は維持する、という整理で提案する。裁定2の再確認事項としてオーナーに明示する。
- **裁定9（実PianoRoll断片の常設）の適用範囲**：裁定は句の編集画面に対して下された。範囲がセクション級のとき全小節の実表記断片は350pxに入らない。「広い範囲では句ごとに縮小表記＋選択中の句だけ実表記」という適用案を描き、裁定9の拡張として確認を仰ぐ。

## 4. 作業の分け方

過去の失敗（同一句の複数枚出現による回帰・レンダせず納品・SVG手書きの座標破壊）を**構造で**防ぐ。分担は「枚ごと」ではなく「データ層と絵の層を分離した工程順」にする。

### 工程0（先行・1体・同期実行）＝データと骨組み
- サンプル曲・短曲3つの全データ（セクション・小節範囲・句・音符・歌詞・予定・ストック）を**HTML内の単一のJSオブジェクト**に定義。句はidを持ち、全ての枚はidで参照する。**同じ句のデータを2度書くことを構文的に不可能にする**＝回帰の根絶。
- 全ダミー歌詞を `apps/audio/.venv/bin/python accent.py` に通し、HL列とアクセント句切れをデータに焼く（記憶で書かない）。
- 赤黄の印は§1の規則をJS関数1つで実装し、**全枚がこの1関数から印を導く**。手置き禁止。
- 描画（矩形・空き枠・高低線・時間揃え文字）はv6のJS方式を引き継ぎ定数を1か所に閉じる。CSS・電話枠・凡例もここで確定。
- 成果物：スケルトンHTML（枠と共通部だけ）＋機械検証スクリプト（§5）。

### 工程1（並行3体）＝枚の制作
- **B：通しの面**（枚1・枚2・音韻新枚・枚3＋インセット）
- **C：範囲の編集画面**（枚4・5・6＋両埋まり新枚＋広い範囲新枚）
- **D：足し込み＋遷移図**（枚7・8）

各エージェントに**渡すもの**：オーナー発言と裁定の抜粋（v7-facts.mdの§2・§3。経緯・設計論は渡さない）／担当枚の仕様（本計画から起こした差分指示）／工程0のスケルトンとデータモジュール（読み取り専用）／v6該当枚の**スクショのみ**（到達点の見た目参考）／レンダ手順。

**渡さないもの**：`docs/research/` の他ドキュメント／v6のHTML全文（desc文に設計論が染みているため）／他エージェントの担当枚。

**縛り**：新しい歌詞文字列・句データの追加は自作禁止＝工程0担当へSendMessageで依頼し、accent検証済みデータとして受け取る。CSS追加は枚接頭辞つきクラスに限定。**納品前に自分の枚をレンダしてスクショをReadで目視すること**を完了条件に明記する。

### 工程2（統合・1体または親）＝突き合わせ
- フラグメントをマージし、全枚を一括レンダ。
- §5の機械検証を全部走らせる。
- 全スクショを目視。
- **欠陥19件との対照表**（各欠陥→v7のどの枚のどの要素で解消したか／意図して足さなかったか）を作って報告に添える。ここで「絵に無いものが残っていないか」を最終確認する。

## 5. 検証の手順

### スクリプトで測るもの
1. **アクセント照合**：データ内の全歌詞を accent.py に通し、HL列・アクセント句切れがデータの値と一致することを機械照合。人にも他モデルにも聞かない（事実6の教訓どおり）。
2. **印の導出照合**：印がすべて規則関数の出力と一致すること（手置きが混入していないこと）。
3. **小節の連続性**：前奏を含めて小節番号が1から通り、セクション・句の範囲に重なり・欠番が無いこと（欠陥14の再発防止）。
4. **枚間の数値整合**：枚7カードの「詞の空きn」等がデータからの算出値と一致すること（欠陥15）。参照idが全て実在すること（欠陥16）。
5. **レイアウト実測**（ヘッドレスブラウザでレンダ後に計測）：
   - モーラ区画のx位置・幅が対応する音符矩形と1px以内で一致（裁定11の縦揃え）
   - 音符矩形が親要素からはみ出て切れていないこと（過去の overflow 事故の再発検知）
   - 352px幅で横スクロールが発生しないこと
   - 高低線のy座標が2値ちょうどであること（振幅潰れの検知）
6. **状態網羅**：対応表の全状態ID・全裁定番号が本文に登場すること。

### 目でしか確かめられないもの
- 各枚が「何の絵か」一目で読めるか（情報の密度・ghostの薄さ・文字のはみ出し）
- 入力欄→入れる→戻すの一連が操作として想像できるか
- 広い範囲の編集画面がスマホ幅で作業に耐える見た目か（裁定1・裁定9の判定材料として成立しているか）
- 音韻タブ・発散の絵が、裁定を仰ぐに足る具体性か

目視は工程1（各自の枚）と工程2（全体）の二重にし、「レンダせず出す」を工程の完了条件で塞ぐ。
