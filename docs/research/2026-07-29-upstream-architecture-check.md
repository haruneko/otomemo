## 1. 衝突している箇所

### 衝突A. 歌詞の置き場所（L23・L26）

> **L23**: `- 最小単位のネタ：メロディ／コード／リズム／歌詞／その他。`
> **L26**: `階層＝Project ⊃ Song(1..N) ⊃ section ⊃ leaf。`

コンセプトは「歌詞はメロに付く」「メロの無い区間の歌詞は曲が持つ（未決1・未裁定）」「曲もセクションも無い思いつきはメモ」と言っている。ところが L23＋L26 を素直に読むと、歌詞は他の素材と同じ一枚の板で、必ずセクションの下にぶら下がる。**メロの中に歌詞が入る形も、曲が直接歌詞を持つ形も、この2行からは読めない。**

実装でもそうなっている：セクションに置ける種別は表で決まっていて、歌詞を含む並びは1つも無い（`apps/web/src/sectionLanes.ts:13-24`）。歌詞ネタ8件はすべて曲ともメロとも繋がっていない孤児（棚卸し(data)§2-4）。＝L23 の「歌詞」は、置き場所を持たないまま名前だけ載っている。

ここを直さないと、未決1（メロの無い場所の歌詞をどこが持つか）をどちらに裁定しても、アーキの階層に載らない。

### 衝突B. 「歌詞のモーラ分析は解決済み」（L43）

> **L43**: `- 歌詞のモーラ分析（#13）→ 実装済み（web クライアント側＝歌詞流し込み。旧 worker `split_mora` は撤去済）。`

コンセプトで「歌詞の正データは漢字仮名交じりの普通の文章」が確定した。**その瞬間、この「実装済み」は成り立たなくなる。** 実装されているのはかな専用の数え方で、漢字が入ると1字を1音として数える（実測：「雨の日は」を4と表示・正しくは5／「沈みゆく この体」を7・正しくは10／棚卸し(data)§2-3）。解決済みの欄に置いたままにできない。

### 衝突C. 機械の手助けが会話からしか届かない（L15・L16）

> **L15**: `**作曲ドメイン能力** → **creative-manager MCP（TS・api 内 `apps/api/src/mcp.ts`）**：…**音楽的妥当性の真実源はここ**`
> **L16**: `**会話の場** → web アプリ内の**薄いチャットラッパー**：…（脳なし）`

コンセプトは「出先の細切れ時間でスマホから開いて、通しで音韻とイントネーションを確かめる」。これは会話ではなく、画面を開いた時点で出ていてほしいもの。ところが L15＋L16 を素直に読むと、ドメインの中身は MCP に集め、画面は会話の結果を描くだけの層になる。**画面が読みと高低を得るには会話を挟むことになり、体験原則6（摩擦・待ち時間ゼロは前提）に反する。**

実装も同じ形で詰まっている：日本語の読み取り（pyopenjtalk）に届く経路は MCP のツール2つだけ（`apps/api/src/mcp.ts:998, 1282`）。画面が叩ける `/music/:op` は35個あるが歌詞系はゼロ（`apps/api/src/http.ts:201-385`）。その結果、いま画面に出ている赤黄は9語だけの内蔵辞書から作られていて、一番効く印（読みが下がる所をメロが上がって裏切る）を原理的に一度も出せない（棚卸し(accent)§5・実測）。

### 衝突D. 機械の読みと、人の手直しの上下（L15）

> **L15**: `…**音楽的妥当性の真実源はここ**（requirements #92/#151＝AIは引く/選ぶ/直す、根拠なきものは作らない）。`

作曲の音符については、この線でよい（コードに合う・調内は仕組みが保証する）。だが作詞に同じ線をそのまま伸ばすと、**機械が読み取った読み・高低が、人が手で直したものより上位**になる。コンセプトは逆を言っている：「機械が読みや高低を間違えたら、人が手で直せる」「点数で優劣を付けない。韻やアクセントの理屈は、間違いに気づくための根拠であって、良し悪しを裁くものではない」。

しかも現物の読み取りは実際に間違えている。音符に載ったかなを読み取りに掛けているため（`apps/api/src/accent.ts:76-81`）、30行の実測で句の割れ方が30行すべて変わり、高低は284モーラ中139（48.9%）が反転した。**モーラの数だけは一致するので、機械は誤りに気づかず「読み取り済み」として通す**（棚卸し(accent)§4）。＝いま「元になるもの」と書かれている場所の中身が、半分外れている。

### 衝突E. 黙って実体を作らない、がアーキに無い（L22-26 全体）

要件に足す体験原則7（曲・セクション・メロディを道具が黙って作らない）は、画面の作法である前に**データの持ち方の話**なのに、アーキの「データの持ち方」節には一行も無い。

現物で該当しうるものが既にある：歌詞を流し込むと、モーラが音符より多いときに一番長い音符を機械が半分に割る（`apps/api/src/lyric.ts:42-55`）。人は詞を書いただけで、メロの音符が増える。これが原則7に触れるかどうかは裁定が要る（下の§3）。

### 衝突F. 仮歌がアーキのどこにも書かれていない（L36）

> **L36**: `- 音：**Tone.js**（中核：テンポ/小節/スケジューリング/シンセ）＋ smplr/SoundFont（音色）＋ **@tonejs/midi**（MIDI入出力…）`

コンセプトの中心の一つが「仮歌で鳴らして確かめられる」。ところがアーキの音の構成にも、配置（L38）にも、歌声合成が一行も無い。実装は既にあり、しかも**3つ目のプロセス**である：`apps/api/src/sing.ts:15-17` が `~/voicevox-poc/extracted/linux-cpu-x64` の歌声エンジンを既定 :50121 で、起動していなければ api が勝手に立ち上げる。systemd の登録は cm-api / cm-search / cm-backup の3つだけで、歌声エンジンは入っていない（`deploy/systemd/`）。

＝上位（アーキ）に無いものが下位（コード）だけで動いている。コンセプトが仮歌を中心に据えた以上、ここは埋めないと乖離したままになる。

## 3. アーキの段で決まること／設計の段に降ろすこと

### アーキの段で決めた（上の差分に入れた）

1. 歌詞に**元の文章と、そこから導かれるかな・割付**の2つがあり、導かれた側は作り直せるものとして扱う。
2. **人の手直しが機械の読み取りより上**。作詞で機械が出すのは材料であって裁きではない。
3. 日本語の読み取りは **K8-Plus の Python**（pyopenjtalk）に置き、**まとめて一度に渡す**。
4. ドメインの中身は1つ、入口は2つ（**会話から＝MCP／画面から＝HTTP**）。
5. 仮歌＝**VOICEVOX が3つ目のプロセス**であること、常駐でないこと。
6. **黙って実体を作らない**をデータの持ち方の段にも効かせる。
7. 階層は「歌詞をどこが持つか」を先に決めない。

### 設計（design.md）へ降ろす

- 元の文章をどのネタのどこに、どんな形で持つか（フィールドの形）。
- **句という単位を保存するか**。裁定「字余りとメロが途中を分ける」は、句が保存されていないと表せない（今はどこにも無い／棚卸し(ui)§3-2）。
- **かなは「読み」（ニワ／ヘ）と「発音」（ニワ／エ）のどちらを音符に載せるか**。既存の実データは発音の側で入っている。
- 語↔モーラ↔音符の対応を最初から持つか（後から手でずらせるようにするための足がかり。後付けだとデータの入れ直しが要る）。
- 赤黄の印を出す規則。
- 歌詞を流し込むときに既存の割付を守る引数（`flowLyric` は純関数で呼び側4つ＝足すこと自体は容易）。**音符の自動分割が原則7に触れるかの裁定もここ**。
- `kind:"lyric"` のネタの行き先（下書き置き場として残すか）。
- 通しの面・範囲の編集画面の作り、表示するパーツの選択をどこに覚えるか。
- design.md の書き換え（`:1647`「歌詞は `Note.syllable` が正典」／`:1658`「入力源は syllable で完結」／`:794` の幽霊参照）。**アーキの L43 は「worker の split_mora は撤去済」と正しく書いており、腐っているのは design 側**。

## オーナーに聞くこと（アーキの段で残るもの）

**歌声エンジンを常時起動にするか。** いまは仮歌を鳴らそうとした最初の1回だけ、エンジンの立ち上げ待ちが入る（api が自分で起動する）。常時起動にすれば待ちは消えるが、箱の上にプロセスが1つ常に居座る。**これを決めると**、要件「いつ開いても使える状態であってほしい」と体験原則6（待ち時間ゼロは前提）を、仮歌にも同じ強さで適用するかが決まる。＝出先で開いて最初に仮歌を押したときの数秒を、許すか許さないか。
