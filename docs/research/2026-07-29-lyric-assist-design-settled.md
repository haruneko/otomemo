## §0 全体像（1画面ぶん）

- **歌詞の正データ＝句（漢字仮名交じりの普通の文章のひとかたまり）**。メロネタの `content.lyric.phrases` に持つ。
  かな・高低・音符への写しは表記から機械が導き、人がいつでも上書きできる。`Note.syllable` は仮歌のための写し。
- **正の規則（1行）**: 句の範囲にある音符では句の読みが正。どの句にも覆われていない音符では従来どおり
  `Note.syllable` が正（人の手打ち）。＝既存のかな入力の口（`set_lyric`・PianoRoll 流し込み欄・詞先メロ生成）を1つも殺さない。
- **音符を変えずに写す**新しい純関数 `placeMoras`（§3）を `packages/music-core` に1本だけ置く。
- **読みは表記から** pyopenjtalk（`apps/audio/accent.py`）で取り、画面からは新設 `POST /music/reading` で届く（§4）。
  複数句は必ず1回にまとめて渡す（実測: 1句ずつ40回=5,799ms／まとめて1回=149ms）。
- 確定事項（コンセプト・原文つき）に全部従う: 正データは漢字仮名交じり／かな書きは仮歌のため／「っ」「ー」にも音符を立てる／
  字余りとメロが途中を分ける／割付の手直しは最初は作らないが手でずらす・自動符割りを見据えた作りにする。

## §1 検算：スライス1〜4は置き場に依存しないか（結論＝依存しない。ただし守ることが2つ）

判断材料文書 §5 の「スライス1〜4は置き場に依存しない」を、実コードで検算した。

**依存しないことの根拠（経路を全部当たった）**

| スライス | 触るデータ・経路 | 置き場との関係 |
|---|---|---|
| 1（詞を書くと正しい読みで仮歌） | `melody.content.lyric`（新設）・`useNetaEditor.ts:334` の保存・`/music/reading`（新設）・`sing.ts:141-148` | 音符を持つメロ自身の中に閉じる。曲(song)の content には読みも書きもしない |
| 2（印と高低が表記由来） | `analyzeLyricFit`（`prosody.ts:332`）への `noteHl` 追加・`lyricFit.ts:31` | 句オブジェクトと音符列だけが入力＝句がどのネタにあるかを知らない |
| 3（言い分け・音符を増やさない） | 言い分けの純関数（新設）・`flowLyric` の呼び場所の限定 | 入力は（範囲・モーラ数・音符列）のみ |
| 4（手直し） | 句の中の `edits`（§7） | 句の中に閉じる |

4案の違いは「**メロの無い区間**の句がどこに入るか」だけで、スライス1〜4が扱うのは**音符を持つメロの句**だけ。
曲の content への書き込み口（4案の(あ)だけが要る）はスライス5の領分で、スライス1〜4のコードはそこに触れない。

**守ること（依存しかけた箇所が2つ見つかった）**

1. **句の範囲の既定を「音符の広がり」で定義しない。** 既定＝そのメロの**尺**（`bars` × 1小節の拍数。`bars` は
   保存時に必ず入る＝`useNetaEditor.ts:334` の `bars: Math.ceil(len/bpb)`）。音符から導くと、(い) 系を採ったとき
   音符0個の空メロで範囲が定義できなくなる。尺から導けばどの案でも同じ式で立つ（1-C の「範囲は音符から導かない」
   とも整合。字余り／メロが途中の言い分けは範囲が音符と独立であることが前提）。
2. **スライス1の保存は「メロの content に lyric を透過する」以上のことを決めない。** (い-b)（共有の空メロ1つ・
   何か入った瞬間に産む）が裁定された場合、保存の**前段**に「産む」フックが挟まる（`useNetaEditor.ts:450` の
   `flushSave` は既に CoW ゲートという前段を持っており、同じ位置に挟める＝作りを塞がない）。フック自体は
   スライス5以降の仕事で、スライス1では作らない。

**付随の発見**: スライス7（詞先メロと分析の入口を表記にそろえる）**も置き場に依存しない**。生成が返すのは
メロネタの content（`generate.ts:784`）で、句を載せる先はメロ自身。1-C はスライス7を5・6の後ろに置いていたが、
順番の制約は「音符数が変わるので耳で確かめてから入れる」だけ＝5・6 と並行に進めてよい。

**結論**: 判断材料文書の結論（乗り換えは安い・分岐はスライス5だけ）を支持する。覆す依存は見つからなかった。

## §2 句のデータの形（設計として必ず決めること 1）

### 現況

- 音符の型は `packages/music-core/src/index.ts:9-15`＝`{pitch, start, dur, vel?, syllable?}`。`syllable` は1音符1かな片で、
  どの語の一部かも出所も持たない。
- 歌詞テキストは4経路すべてで捨てられる: `apps/web/src/components/PianoRoll.tsx:69`（`lyricDraft` は「永続せずUIだけ」と
  コード自身が明記）・`apps/web/src/lyrics.ts:70-73`（詞モード手打ち）・`apps/api/src/mcp.ts:944-957`（`set_lyric`）・
  `apps/api/src/music/generate.ts:762,784`（詞先メロ＝返り content は `{notes, feel}` のみ）。
- メロの content の既存キーは `notes / program / sing / feel`（`useNetaEditor.ts:334`）。content は素通しの JSON
  （`apps/api/src/schemas.ts:16` が `z.unknown()`）＝DB スキーマ変更・移行は不要。

### 変更の形＝`content.lyric`（メロネタ）

型は `packages/music-core/src/lyric.ts`（新設）に置き、web/api で共有する（純データ＋純関数のみ＝music-core の憲章
「アプリ非依存の純粋派生」に収まる。`index.ts` から re-export）。

```ts
export interface LyricLayer { phrases: LyricPhrase[] }

export interface LyricPhrase {
  id: string;        // 札。表記を直しても直し・割付が剥がれないための不変キー
  start: number;     // 開始拍（このメロの中の拍。弱起の負拍も可）
  beats: number;     // 拍数。既定＝そのメロの尺（§1）。人が切れば分かれる
  text: string;      // 表記＝正データ（漢字仮名交じり。改行可。穴は「＿」1個以上＝§4）
  memo?: string;     // 人が書く意味メモ（機械は書かない＝意味・感情遷移に踏み込まない、の置き場側）
  plan?: { moras?: number; bars?: number; note?: string };  // 予定（音数・小節数・自由記述。すべて任意）
  reading?: LyricReading;   // 機械の読みの控え（下）
  edits?: LyricEdit[];      // 人の直し（§7）
  source?: { netaId: string; line: number };  // 写し元（lyric ネタから写したとき機械が記録・任意）
  // 割付（モーラ→音符）は最初は保存しない＝省略時「範囲内の音符へ頭から1対1」。
  // 手でずらす・自動符割りを足すときは alloc?: を足すだけ＝データの入れ直し不要（裁定「見据えた作りにする」の担保）
}

export interface LyricReading {
  forText: string;   // 控えたときの表記。今の text と違えば控えは使わない＝古い読みが残らない
  words: { surface: string; read: string; pron: string; moraCount: number }[]; // 語の列（run_frontend 由来）
  moras: { kana: string; word: number }[];  // pron 由来のモーラ列（「’」除去済み）。word=-1＝語対応が取れない区間
  hl: (0 | 1)[] | null;   // モーラごとの高低。門番（§4）で不一致なら null＝読みは出すが高低は出さない
  breaks: number[];       // 読みの句の切れ目（モーラ添字）
}
```

**決め（かなの使い分け）**: 音符と仮歌に載せるのは **`pron`（発音・「は」→ワ）から「’」を除いたもの**。
`read`（読み・「は」→ハ）はふりがな表示用に語列へ持つ。根拠＝「かな書きは仮歌のためにある」（原文）＋
既存実データ4件が発音側で入っている（「思い**わ**」「だろ**お**」＝引き継ぎ書 5-1 実測）。
※これはオーナーの明示裁定が無い設計判断（引き継ぎ書 4-13）＝§14 の裁定待ちに残す。

**範囲の規則**: 同じネタの句同士は重ならない・隙間があってよい。「範囲内の音符」＝
`phrase.start <= note.start < phrase.start + phrase.beats` の音符（start 昇順）。

**曲(song)側**: 4案の(あ)を採った場合だけ `song.content.lyric` を同じ `LyricLayer` で持つ（§12）。
**スライス1〜4では作らない・触らない。**

**`kind:"lyric"` ネタ**: 曲もセクションも無い思いつきのメモ・下書き置き場として残す（Q3「曲もセクションもないなら
メモできたらいい」）。句へ写すときは**表記のまま**（かなに潰さない）＋ `source` を記録。既存8件は全部 QA の捨てデータ
（content 8件とも NULL・text 4件に QA 文字列＝実測済み）。

**既存の `syllable` 持ちメロ4件**: 表記は機械で復元できない（仮歌用に崩れたかな）。句を作るまでは「句に覆われていない
音符」として従来どおり鳴る＝後退ゼロ。句を作った時点で旧 `syllable` は「音符のかな上書き」（§7 の kind:"kana"）として
取り込める。

## §3 音符を変えずに読みを音符へ写す関数（設計として必ず決めること 2）

### 現況

- `syllable` を書く純関数は `flowLyric` だけで、**同じものが2本ある**（`apps/api/src/lyric.ts:37-63` と
  `apps/web/src/lyrics.ts:34-65`）。どちらも (1) モーラが多ければ最長音符を半分に割る（下限16分＝`MORA_FLOOR=0.25`）
  (2) 全音符の `syllable` を頭から無条件に上書き (3) 余ったモーラは最後の音符に連結。既存の割付を守る引数は無い。
  ＝**音符を変えずに写す処理はリポジトリに存在しない**。実装者がこれを呼んだ瞬間、詞を打つたび音符が増える。

### 変更の形＝新設 `placeMoras`（`packages/music-core/src/lyric.ts`・1本だけ）

先行案の名 `castPhrase` は鋳込みの比喩なので採らない（「強い言葉はいらない」「内輪語になってない？？」）。
やることをそのまま英語で言う名にする。

```ts
export function placeMoras(
  notes: Note[],
  moras: string[],                          // effectiveMoras(phrase) の返り＝人の直し反映後のかな列
  range: { start: number; beats: number },  // 句の範囲
): Note[]
```

**契約（テストで縛る）**:
1. 純関数・非破壊。返りの音符列から `syllable` を取り除くと、**入力と完全一致**（数・順序・start・dur・pitch・vel
   すべて。property test）。
2. 範囲外の音符は **`syllable` も含めて**一切触らない（他の句・手打ちかなを壊さない）。
3. 範囲内の音符（start 昇順）へ moras を頭から1対1で `syllable` に書く。音符が余れば `"ー"`（メリスマ。
   `sing.ts:141` と `PianoRoll.tsx:398` がこの文字を読む＝当面変えない）。**モーラが余れば書かない**＝音符は増えない。
   余りの数は書かれない（言い分け §6 が別途言う）。
4. 導出（表記→モーラ・高低）・割付（モーラ→音符＝この関数）・音符の作り替え（`flowLyric`）は**別の段**。
   `flowLyric` は**人が「合わせる」を押したときだけ**走る（当面の形＝§14-2 の裁定待ち。決めた形として書かない）。

**`flowLyric` の二重の始末**: `flowLyric`・`splitMora` を `packages/music-core/src/lyric.ts` へ**移し**、
`apps/api/src/lyric.ts` と `apps/web/src/lyrics.ts` は music-core からの re-export に置き換える（呼び側 import 無変更・
挙動 bit 一致のまま2本→1本）。`placeMoras` を最初から music-core に置くのはこの再発防止。

## §4 読み取り（pyopenjtalk）の経路（設計として必ず決めること 3）

### 現況

- `apps/api/src/accent.ts:76-81` `accentsFromSyllables` が**音符に載ったかなを連結して**渡す。実測30行で句の割れ方が
  30/30行変わり、高低は 139/284モーラ＝**48.9%反転**。モーラ総数は一致するため `mapAccents`（`accent.ts:59-70`）は
  null を返さず、**誤った高低が検出されずに通る**。
- `apps/audio/accent.py:95` は**ローマ字音素しか返さない**（かな・語列を返す経路が無い）。stdin の一括受けには
  対応済み（`accent.py:103-107`＝1行1文）だが、`accent.ts:18-41` の `run()` は stdin に書いていない。
- 画面が叩ける `/music/:op` は35個で**歌詞系ゼロ**（`apps/api/src/http.ts:201-377`）。いま画面の赤黄は9語の内蔵辞書
  （`prosody.ts:185-195`・`lyricFit.ts:31` はブラウザ内同期計算）で、核を持つのは「はし・そら・ゆめ」の3語だけ。
- `/music/:op` は switch 全体を1つの try/catch で包み、投げられたものを**全部 400 に落とす**（`http.ts:379-381`）。

### 変更の形

**(a) `accent.py` に語列とかなを足す**（追加費用実測 0.02ms/回）:
各文の返りに `words: [{surface, read, pron, mora_size, pos}]`（`pyopenjtalk.run_frontend`）を追加。既存の
`moras/hl/trans/phrases/mora_total` は不変（既存呼び出し＝`analyze_lyric_fit` の自動注入は壊さない）。
「’」の除去・`pron` の割り（かな片へ）は TS 側でやる（Python は素通し＝実測値をそのまま持ち帰る）。

**(b) `accent.ts` に一括口を足す**: `extractReadings(texts: string[], signal?): Promise<ReadingResult[]>`＝
texts を改行区切りで **stdin にまとめて書いて1回 spawn**（`run()` に stdin 書き込みを足す。40句149ms）。
1行1文プロトコルのため、**呼び側（api）が句の表記を「行」と「穴」で断片に割ってから渡し、返りを句へ組み戻す**
（表記の改行は行の切れ目・「＿」1個以上は穴＝断片の境。空断片は送らない）。タイムアウトは一括でも 15秒で足りる
（149ms 実測＋起動揺れの余裕）。

**(c) TS 側の門番（2つだけ・順に）**:
1. 語ごとに「pron を割ったかな片の数 ＝ mora_size」。合わない語だけ**語まるごと1区間**（`word=-1` 的な扱い＝
   モーラ対応不明）として持つ＝句全体を捨てない（実測38行199語で不一致1語）。
2. **hl の長さ ＝ モーラ列の長さ**（words は run_frontend・hl は extract_fullcontext＝別々の解析。実測6例は一致だが
   保証が無い）。合わなければ**その句は hl=null**＝読みとモーラは出す・高低と印は出さない。

**(d) 画面から届く口＝`POST /music/reading`（新設・`/music/:op` に case を1つ追加）**:
- 入力: `{ texts: string[] }`（1要素＝1句の表記まるごと。断片化は api 側でやる）。上限＝texts 200件・合計2万字
  （通しの面でも曲1本で足りる）。
- 返り: `{ results: [{ words, moras, hl, breaks, error? }] }`（§2 の `LyricReading` から `forText` を除いた形）。
  1句の解析失敗は `results[i].error`＝他の句は生きる（`accent.py` の流儀と同じ）。
- **失敗の返し方**: 入力が変（配列でない・上限超）＝400。**Python 側の失敗（venv 無し・起動失敗・時間切れ・JSON
  取れず）＝ case の中で自分で `reply.code(502)` を返す**。外側の catch は投げられたものを全部 400 にする
  （`http.ts:381`）ため、**throw で外へ出さない**。402/502 を分けないと画面が「入力が変」と「機械側の失敗」を
  区別できず、失敗時の規則（下）が効かない。
- **失敗時の画面の規則**: 「読みが取れませんでした」と出し、表記・割付・音符はそのまま・**印と高低は出さない**＝
  表記を持つ句では9語辞書に落とさない（誤った高低が「機械の読み取り」の顔で通るのを止める。句に覆われていない
  旧データでは従来どおり9語辞書が動く＝後退ゼロ）。
- MCP には今回足さない（スライス1〜4は画面から使う）。足すときは `CHAT_VERB_NAMES`（`apps/api/src/chat-session.ts:19`）
  への登録が必須（BUG#1「登録したが許可漏れで黙って死ぬ」型の再発防止）。
- **控えを引き直す契機**: 句の表記が変わった状態で保存されたとき（`reading.forText !== text` なら控えを使わない＝
  引き直すまで印も高低も出さない）。

**(e) `analyzeLyricFit` への渡し方＝`noteHl`**（`prosody.ts:332` の opts に追加）:
「音符ごとの高低」＝`(0|1|null)[]`・**音符列と同じ長さ**。モーラ列をそのまま渡さない理由＝字余り（モーラ≠音符）が
一級の状態になるため、添字で突き合わせると途中から1つずつずれた印が出る（いま直そうとしている `accent.ts:76-81` と
同じ形の事故）。呼び側が `placeMoras` と同じ範囲規則で音符の並びに直してから渡す純関数 `noteHlOf(phrase, notes)` を
music-core に置く。`noteHl` が来たら読みの輪郭はそれから直に作り、`accents`（語ごと核位置）からの組み直しはしない
（`AccentEntry={kana,kernel}` は「モーラ1つだけ反転」した人の直しを表現できない＝`buildContour` が
`analyzeMoras(a.kana)` で数え直すため。`prosody.ts:289-325` 実読）。**`noteHl` 未指定＝従来と完全一致**（property）。
`accentSource` に `hand` を足す（`explicit|pyopenjtalk|hand|heuristic`）。

**(f) 同期性**: `planLyricMelody`（`lyricsPlan.ts:85`）と `genLyricMelodyCandidates` の「同期・決定的」は壊さない＝

## §6 字余りとメロが途中の言い分け＋音符を増やさない（スライス3の中身）

言い分けの純関数を music-core に置く。分けられるのは**句が自分の範囲を持つから**（範囲は音符から導かない＝§1）。

```ts
export type PhraseStatus =
  | { kind: "メロなし" }                    // 範囲に音符が1つも無い
  | { kind: "メロが途中"; gapBeats: number } // 範囲のうち音符が覆っていない空きが目盛り（既定1小節）以上
  | { kind: "字余り"; count: number }        // 音符が範囲を埋めていて、モーラが余る
  | { kind: "あと"; count: number }          // 音符が範囲を埋めていて、音符が余る
  | { kind: "ちょうど" };
export function phraseStatus(range, moraCount: number, notes: Note[], opts?: { gapBeats?: number }): PhraseStatus
```

- 「メロなし」は今スライスでは（音符を持つメロを開いているので）ほぼ出ないが、**関数には最初から入れる**＝
  置き場の裁定がどちらに転んでも（曲持ちの句／空メロ）この関数がそのまま言える＝分岐を関数の外に出す（§1）。
- 「1小節」の目盛りは引数（既定値）＝人が変えられる余地を塞がない（§14-8 裁定待ち）。
- **機械は詰めない・削らない・止めない**。直すのは人（表記を変える／メロを変える／「合わせる」を押す）。
- `flowLyric` の呼び出し元を「合わせる」経路だけに限定する: 現在の呼び元は PianoRoll の流し込みボタン
  （`PianoRoll.tsx:280`）・`set_lyric`（`mcp.ts:953`）・詞先メロ（`generate.ts:762`）。PianoRoll のボタンは
  「合わせる」に改名して残す（音符が変わることを明記した確認つき）。`set_lyric`・詞先メロは句に覆われていない
  音符が対象のままなので従来どおり（後退ゼロ）。
- `align_lyrics`（design 1188行）の返りは言い分けの語彙に合わせる（詰める・削るは機械がしない）。

## §7 手で直せる範囲の持ち方（設計として必ず決めること 7）

### 現況

人の直しの置き場は無い。音符のかな手打ち（`lyrics.ts:70-73` `setSyllable`）は `Note.syllable` に直書き＝
機械が写し直すと消える。

### 変更の形＝機械の値と人の直しを別々に持つ（`LyricPhrase.edits`）

```ts
export interface LyricEdit {
  kind: "read" | "hl" | "kana";  // 読み（語単位）／高低（モーラ単位・タップで反転）／音符に載るかな（モーラ単位＝仮歌の崩し）
  from: number; to: number;      // 貼り先＝直した時点の表記の何文字目〜何文字目
  was: string;                   // そのときそこにあった文字列
  mora?: number;                 // hl / kana：その語の中で何番目のモーラか
  value: string | 0 | 1;
  detached?: true;               // 付け先が分からなくなった＝人に見せて「付け直す／捨てる」
}
```

- **貼り先は「文字位置＋そのときの文字列」**。並び順の番号は使わない（表記を直すと全部ずれる）。
- **表記が変わったときの付け直し（純関数・テスト3通り）**: 同じ位置に同じ文字列→そのまま／位置がずれても句の中に
  その文字列が1つだけ→そこへ／見つからない・2つ以上→ `detached` を立てて人に見せる（「この直しの付け先が
  分からなくなりました：〔今日→きょう〕 付け直す／捨てる」）。**黙って捨てない・黙って別の語に付けない。**
- **機械が読み直しても直しは消えない**: 控え（`reading`）を引き直したあと、`edits` を適用した「効いている読み」を
  純関数 `effectiveReading(phrase)` で導く。`placeMoras`・`noteHlOf`・仮歌はこの適用後を読む。
- **読みを直した語の高低（当面の形・§14-7 裁定待ち）**: 機械はその語の高低を作り直せない＝その語のモーラは
  hl 不明（高低表示は空白・印は出さない）とし、「手で直した」と出す。人が続けてタップで高低を与えられる（hl の edit になる）。
- 出所表示: 直しが1つ以上効いている句は `accentSource: "hand"`（§4(e)）。
- 曲から潜って句に覆われた音符へ詞モードでかなを打った値は kind:"kana" の直しとして句へ取り込む。
  ネタ帳から直接開いた（句の無いメロの）詞モードは従来どおり `Note.syllable` へ。

## §8 メロの自動保存が句を落とさないこと（設計として必ず決めること 5）

### 現況

`useNetaEditor.ts:327-349` `savePatch()` は kind ごとに content を**キー決め打ちで作り直す**。メロ分岐（:334）は

### 変更の形（feel の直し方に倣う）

4. container 分岐（:347・content を返さない）は**触らない**＝(あ)を採った場合の曲の書き込みは「歌詞だけを更新する
   専用の口」で別に作る（スライス5・§12）。ここで触らないことが §1 の置き場非依存の担保。

## §9 「っ」「ー」に音符を立てる（設計として必ず決めること 6）

裁定は**立てる**（Q7 原文「立てる」）。実装は2流儀に割れている:

- **立てる側（裁定どおり）**: `splitMora`（web/api）・`flowLyric`＝ー/っ/ん も1モーラ1音符。仮歌も
  `syllable:"ー"`＝母音継続（`sing.ts:141-148`）で音符が立っている。**こちらが正＝触らない。**
- **立てない側（裁定に反する）**: 詞先メロの `isOnsetMora`（`lyricsPlan.ts:30-32`）＝長音=延長・促音=休符として

**直し方**: `isOnsetMora` を「全モーラが音符を持つ」に変える（`planLyricMelody` の音数＝総モーラ数になる）。
`#13d` の受け入れ条件（design 1684行「モーラ⇔音数 100%一致」）の「モーラ」の数え方も っ/ー込みに更新。
**生成される音符数が変わる＝耳で確かめてから入れる（スライス7）**。`suggestLyricRhythm` の候補は「提案」であって
保存物ではないので今回は触らない（候補の見せ方はモック裁定待ちの領分）。
実装時の確認1点: 促音「っ」の音符を VOICEVOX にどの lyric で送るか（`sing.ts:148` は syllable をそのまま送る。
「っ」が歌えない場合の音の扱いはスライス7の耳確認で決める＝設計はデータ（音符は立つ）だけを決める）。
