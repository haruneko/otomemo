### 対応しなかったもの（理由つき）

- **spec#7 の「`set_lyric`・PianoRoll の流し込み欄・詞先メロ生成を表記を書く側に付け替える」**：付け替えない。裁定1 が「かながきは**仮歌のためにあるもの**」と位置づけた以上、メロに直接かなを打つ口は仮歌の道具として正しい。付け替えると、曲に置いていないメロに仮歌を当てる今の作り方が止まる。代わりに「句が覆う音符では句の読みが正」の1行で足りる（§6-3）。
- **原案 §7-2「PianoRoll の詞モードを無効にする」**：撤回する。上と同じ理由＋owner#10（代わりが無い期間ができる）。**動いている機能は1つも止めない。**
- **原案 §7-3「時間範囲を必須にすると裁定6 に触れる」**：この心配は誤りだったので撤回する。裁定6「予定の当ては両方あると良いしオプショナルで必須にしない」は**予定メモ（小節数・音数の見込み）**を任意にする話で、句が曲の中のどこに置かれているかとは別。句は「ここに書く」と開いた場所に置かれる＝範囲は最初から決まっている。

## §1 この改訂の芯（1文）

歌詞の正データは**セクションが持つ句の漢字仮名交じりの文章**。かな（モーラ）・高低・音符への割付は**そこから機械が導くもの**で、`Note.syllable` は正データではなく**仮歌のために音符へ写したもの**に降格する。

### 3-2. 794–795行（目的）

**改訂後**
> **目的**：セクションの句が持つ**表記**（漢字仮名交じり）から読み（モーラ列・高低）を導き、その読みを句の範囲に重なる音符へ割り付けて音符上に表示する。`Note.syllable` は**仮歌のために音符へ写したもの**であって、歌詞そのものではない（正データは句の表記＝#13e）。土台＝表記→読みは `apps/audio/accent.py`＋`pyopenjtalk.run_frontend`。自作のかな分割（web `lyrics.ts`／api `lyric.ts` の `splitMora`。**同じものが2本ある**）は**漢字を含む文字列に渡さない**（漢字を1字1モーラで数えるため＝実測「庭へ」が2、正しくは3）。※`moraLines` は web にしか無い。

### 3-3. 797–799行（決定L1・まるごと差し替え）

**改訂後**
> **決定L1（2026-07-29 改訂・オーナー裁定 2026-07-28 に従う）：正データは表記。読みは導かれるもの。**
> - 原文「基本的にかながきは仮歌のためにあるものであって、歌詞の正データは漢字仮名交じりの普通の文章です。それでも読みやイントネーション間違えるなら手で直せるがよいかと」。
> - **人が書くのは表記だけ**。読み（かな）を丸ごと打ち込む場は作らない。読みは機械が表記から取り、**間違えたら人が上書きできる**（上書き値と出所を持つ＝#13e）。
> - 旧L1の `reading`（行ごとの読みを人が書く欄）は**採らない**。※`reading` はリポジトリに0件＝一度も存在しなかったので捨てるものは無い。
> - **正データの置き場は melody ネタではなく セクション（container）ネタ**＝`content.lyric.phrases`（#13e §4-1。2026-07-15 裁定の一部上書き＝#13e §6-1 に別項で理由）。
> - **表記↔モーラの対応は「語（形態素）の区間↔モーラの区間」で持つ**。文字単位は採らない＝「今日」のキョ・ウのどちらが「今」か機械に根拠が無く、熟字訓で定義が閉じない。生成方法＝`pyopenjtalk.run_frontend`（#13e §4-3）。

## §4 新設：#13e 歌詞の2層（本体）

### 4-1. 置き場＝セクション（container）ネタの `content.lyric`

```
section.content.lyric = { phrases: [ 句, 句, … ] }
```

**melody ネタではなくセクションに置く理由**（5つとも実コード／実測で裏が取れている）：

1. **melody ネタの content は web の自動保存で消える。** `useNetaEditor.ts:334` の melody 分岐は `{ notes, program, ...sing, ...feel }` と**キー決め打ちで作り直す**ので、`content.lyric` はピアノロールで音符を1つ動かした数秒後に落ちる（明示保存は廃止＝デバウンス PATCH・同 435-437）。同じ理由で `feel` が落ちていた前例が同ファイル147行に残っている。**セクションは安全**＝`isContainer` の分岐は `content` を返さない（同 347行）ので自動保存が content に触らず、SectionEditor は `{...secContent, ...next}` と畳んで書く（`SectionEditor.tsx:141`）。
2. **範囲がネタをまたげる。** 曲→セクション→句 の座標で並ぶので、Aメロ末尾からBメロ頭にまたがる範囲・曲全体を「(セクション, 句) の列」で指せる（オーナー「どこでも開くのが正しい」）。
3. **詞もメロも無い区間が表せる。** その区間に句もメロ子も置かない＝データ0。melody ネタに寄せると、詞だけの区間のために**音符ゼロのメロディネタ**を作ることになり、裁定4「ゴミが増えるのは嫌」に触れるうえ、`childDur`（`sectionContext.ts:81`）が notes 空を**1小節扱い**にするのでセクションの尺が狂う。
4. **同じメロを1番2番で使い回せる。** `compose_edge` は子の使い回しが前提で、`useCowGuard` が共有の安全弁になっている。歌詞がメロ側にあると、2番の詞を書いた瞬間に1番が変わるか、打つたびに分家の確認が出る。セクション側なら歌詞は最初から別。
5. **どのメロが歌詞を持つ側かを決めなくてよい。** ハモ（counter）やセクション複数メロがあっても、句は範囲を持ち、音符の側が「その範囲に重なるメロレーンの子」として自動的に決まる。

**残る注意**：SectionEditor は自分がマウント時に読んだ `secContent` に畳んで書く。歌詞を別の面から書くなら、書く前に読み直すか、歌詞だけを更新する専用の書き込みにする（古い控えで畳むと消える）。

| 3 | **表記**（漢字仮名交じり。穴を含みうる） | **人**＝正データ | 裁定1 |
| 4 | **穴**（表記の中の「まだ無い」箇所） | **人** | オーナー「z の中の単語1個が無い」 |
| 5 | **機械の読み取りの控え**（語列・モーラ列・高低・アクセント句） | 機械 | **表記から作り直せる＝速さのための控え**。控えたときの表記も一緒に持ち、表記が変わったら使わない |

**被覆の規則**：句の範囲は**重ならない・曲の頭から順に並ぶ・隙間があってよい**（隙間＝詞の無い区間）。**どの句の範囲にも重ならない音符は、どの句にも属さない**＝その `syllable` は従来どおり人が打つものが正（機械は上書きしない）。

**「歌詞の正データ＝普通の文章」の満たし方**：句の表記を並び順に連結したものが1本の文章になる（§4-9）。**句と行を1対1に固定しない**＝1つの句が複数行でもよいし、連の切れ目（空行）は句と句の隙間として表せる。

### 4-3. 読みを機械が導く経路

**渡す単位＝句の表記1本ずつ。** 実測（4ブロック）：句ごとに読ませた結果と、まとめて1本にして読ませた結果は3ブロックで一致、1ブロックで1モーラ分の高低が変わった（「雨の日は／傘をさして／歩いていこう」）。**画面に出る句の切れ目と読みの切れ目を合わせる**ほうが人に説明できるので句単位を採る。複数句は1回の呼び出しにまとめて渡す（速さの理由＝下記）。

**出す**（1句あたり）：

1. **語の列**＝`{表層, read, pron, モーラ数, 品詞}`（`pyopenjtalk.run_frontend`）
2. **モーラの列**＝かな1つずつ＋そのモーラが何番目の語のものか
3. **高低**＝モーラごとに 高／低 の2値（裁定12）＝`accent.py` の `hl`
4. **アクセント句の切れ目**＝`accent.py` の `phrases`

**モーラ列の正準は1本**＝`mora_size > 0` の語を並べたもの。総数は `accent.py` の `mora_total` と一致する（**実測38行すべて一致**）。高低はこの列と1対1で並ぶ。

**かなの取り方**：語の `pron` から **「’」（アクセント記号）を除いて** `splitMora` で割る。実測で `pron` には「’」が混ざる（のばし→`ノバシ’`／靴→`ク’ツ`／聞こえ→`キ’コエ`／明日→`アシ’タ`／光っ→`ヒ’カッ`）＝そのまま音符に載せると「’」が表示され、VOICEVOX にも渡る。`read`（表記寄りの読み・「トオリスギル」）は画面のふりがな用に句へ持つ。

**取り出しの検査**（門番にするのは1つだけ）：

- **門番**：語ごとに「割ったかなの数 ＝ `mora_size`」。**合わない語だけ、その語をモーラに割らず「語まるごと1区間」として持つ**（実測：38行199語のうち合わなかったのは1語＝「フュージョン」。`mora_size=5` に対し `フュ|ー|ジョ|ン`=4。openjtalk が「フュ」を2モーラに数えるため）。**句全体を捨てない**＝この1語のせいで句全体が光らなくなるのを避ける。
- **門番にしない**：語の表層を連結したものが渡した表記に一致すること。**実測で普通の歌詞行のほぼ全部が落ちる**（半角スペース→`\u3000`、`1000年`→`千年`、`Tokyo`→`Ｔｏｋｙｏ`）。文字位置は「表記を語で順に食っていく」で当て、正規化で長さが変わった語だけ位置不明として粗く持つ。
- **記号の語（`mora_size==0`）は対応から外す**。実測で**半角スペースは `{string:"　", read:"、", pron:"、", mora_size:0, pos:記号}`** として返る＝読点も空白も同じ形。裁定1の正データは句読点のある普通の文章なので、これは例外ではなく常態。

**穴を含む句**：穴で区切った断片を**別々に**読ませる（穴をまたいで読ませない）。＝穴の前後で読みがつながらないことを画面にも出す。穴が埋まったら句全体を読み直す。

**実行の場所**＝`apps/audio/accent.py` に `run_frontend` の返りを足す（別スクリプト・別プロセスにしない）。実測：`run_frontend` の追加費用は **0.012ms/回**（`extract` 本体が 0.106ms／300回平均）＝計測できない差。1回の spawn は **0.14秒**で、そのほとんどは Python の起動と辞書ロード。**40句を stdin で1回にまとめても 0.14秒**（3回とも）＝句ごとに spawn すると破綻する。`accent.py` は stdin の一括入力に既に対応しているが、**`accent.ts` の `run()` は子の stdin に書かず閉じもしない**ので、`write`＋`end` を足す必要がある（argv を外すだけでは stdin 待ちで timeout する）。

### 4-4. 人が手で直せる＝データとして何を持つことか

**機械の値と、人が上書きした値を、別々に持つ。** 直せるのは3種：

| 直す対象 | 単位 | 何のため |
|---|---|---|
| **読み（かな）** | 語 | 「今日」を「きょう」と読ませる。裁定1 |
| **高低** | モーラ | タップで反転。裁定1・裁定12 |
| **音符に載るかな** | モーラ | 仮歌の崩し（「思い**わ**」「だろ**お**」）。既存4件がこれ |

**貼り先＝「直した時点の表記の何文字目から何文字目」＋「そのときそこにあった文字列」。** 並び順の番号（何番目の語・何番目のモーラ）は使わない。表記を1文字足すだけで全部ずれるため（「今日は雨」の「雨」を直したあとに「今日はきっと雨」と足すと、3番目の語は「雨」ではなく「きっと」になる）。

**表記が変わったときの付け直し**：
1. 同じ位置に同じ文字列があれば、そのまま付け直す。
2. 位置がずれていても、その文字列が句の中に**1つだけ**あれば、そこへ付け直す。
3. 見つからない／2つ以上ある → **外して人に見せる**（「この直しの付け先が分からなくなりました：〔今日→きょう〕 付け直す／捨てる」）。**黙って捨てない・黙って別の語に付けない。**

**出所**は画面に出せること（機械の読み取り／手で直した）。`analyze_lyric_fit` の `accentSource` に `hand` を足す（#13c 1668行）。

**読みを直した語の高低**：読みを打ち直すとその語のモーラ数が変わるので、機械にその語の高低を作り直させる口が無い（pyopenjtalk に「この語はこう読め」と教えられない）。**直した語は、その語だけ高低を平らにして「手で直した」と出す**（人が続けて高低を触れる）。※これは設計側の決めで、オーナーに確認する（§7-2）。

**アクセント句の切れ目**を直せるようにするかは**未決**（v8 枚9 の案2 に「句切れは直らない」差が絵で出ている＝裁定待ち12）。実測では誤りが一番よく出るのはここ（かな入力で 35/38 行が変わる）。

### 4-5. 割付（モーラと音符の対応）

裁定2＝**最初は作らない。ただし後から足せない作りにしない。** そのために今決めておくこと（実装は0行でよい）：

1. **3つを別の段として書く**：①導出（表記→モーラ・高低） ②割付（モーラ→音符） ③音符の作り替え（分割・メリスマ埋め）。**②は音符を一切変えない。③は人が「合わせる」を押したときだけ走る。**
   - ※現状認識の訂正：①と②は既に分かれている（`flowLyric(notes, moras[], floor)` で、かな分割は呼び側＝`mcp.ts:953`・`PianoRoll.tsx:280`）。分かれていないのは②と③（`lyric.ts:42-61`＝モーラが多ければ最長音符を割り、余ったモーラを最後の音符に連結し、音符が余れば "ー" で埋める＝**流し込み後は必ず モーラ数=音符数**）。
2. **割付は句の中に閉じる**＝その句の範囲に重なる音符を、その句のモーラで頭から順に1対1。**句をまたいで食い込まない。** これがあるので、途中の句でも独立に「字余り」「あとN音」が出る（句をまたいで詰めると、余りは必ず最後の句にだけ出る）。
3. **割付の宛先になる言い方を先に決める**＝「句の札 ＋ 語の貼り先（§4-4）＋ その語の中で何番目のモーラか」。最初はこれを保存しない（省略＝頭から順に1対1）。手でずらす／自動符割りを足すときは、句の割付（§4-2 の10番）に「モーラ→音符の並び順」を書くだけで済む。
4. **メリスマ（余った音符）は `syllable` に書かない**＝割付の側に「この音符は直前のモーラの続き」と持つ。理由＝`pron` の長音も「ー」なので（「通り過ぎる」→`トーリスギル`）、`syllable` に埋め草の「ー」を混ぜると**導出された長音なのか埋め草なのか区別できなくなり、「字余りN／あとN音」の数えが狂う**。仮歌へ渡すときだけ "ー" に直す（§4-8）。
5. **`flowLyric` の契約に「既にある割付を保つ」引数を足せる**と書いておく。純関数で呼び側は3つ＋テスト（`mcp.ts:953`・`music/generate.ts:761`・`PianoRoll.tsx:280`）。**web と api に同じ関数が2本ある＝両方直す。**

### 4-6. 「字余り」と「メロがまだ途中」の言い分け（裁定3）

**現状**：両方が「モーラ数 > 音符数」という同じ1つの事実から出ていて、しかも `lyricsPlan.ts:133` の生成時の警告文字列1箇所しか無い。同じ句が通しの面で「字余り5」、足し込みの画面で「メロ未定」と出て食い違う。

**分けられるのは、句が自分の範囲を持つから。**（範囲は音符から導かない＝§4-2）

| 句の状態 | 言うこと |
|---|---|
| 範囲に音符が1つも無い | **メロなし** |
| 範囲のうち音符が覆っていない空きが**1小節以上**ある | **メロが途中** ← 余ったモーラの数は言わない |
| 音符が範囲を埋めていて、モーラが余る | **字余りN** |
| 音符が範囲を埋めていて、音符が余る | **あとN音** |
| ちょうど | 何も言わない |

「1小節」は外部DAWと突き合わせる単位（オーナーも小節で話す）。ここは人が変えられる目盛りにしてよい。**この表で v8 枚1 の 9–10小節「鍵をかけて 外に出る」は「メロが途中」になる**（今は「字余り5」）。

**機械は詰めない・削らない・止めない。** 直すのは人（表記を変える／メロを変える／割付をずらす／「合わせる」を押す）。

### 4-7. 読みに届く口（新設）

今はブラウザから読みに届く経路が無い（`/music/:op` に歌詞系の op はゼロ・pyopenjtalk への配線は MCP 側だけ）。

- **パス**：`/music/reading`（既存の `/music/:op` に op を1つ足す）。
- **入力**：`{ texts: string[] }`＝句の表記の配列。**1回にまとめる**（実測：1文 0.14秒／40文 0.14秒）。
- **返り**（1文につき）：`{ words:[{surface, read, pron, moraSize, pos}], moras:[{kana, wordIdx, hl}], accentPhrases:[{moras, kernel}], moraTotal, warnings:[…] }`。`warnings` に「この語はモーラに割れなかった（語まるごと1区間）」を入れる。
- **失敗時**（venv 無し・spawn 失敗・timeout）：502＋`{error}`。画面は「読みが取れませんでした」と出し、**表記・割付・音符はそのまま**。**印と高低は出さない**＝内蔵9語辞書へは落とさない（誤った高低が「機械の読み取り」として通るのを止める。実測で高低の40.0%が反転する）。表記を持たない旧データでは従来どおり9語辞書のフォールバックが動く。
- **控えを引き直す契機**：句の表記が変わった状態で**保存されたとき**（web は自動保存＝デバウンス PATCH と同じタイミング）。控えには**控えたときの表記**を一緒に持ち、今の表記と違えば使わない（＝古い読みが残らない）。
- **MCP verb も足すなら**、`chat-session.ts` の `CHAT_VERB_NAMES` へ必ず登録する（#13b が自分で書いている BUG#1 再発防止の作法）。

### 4-8. 仮歌への渡し（`Note.syllable` はどうなるか）

**消さない。仮歌のための写しとして残す。** 消せない理由（実コード）＝VOICEVOX（`sing.ts:141-148`）・音符上の表示（`PianoRoll.tsx:423`）・アクセント色（`lyricFit.ts`）・MCPのガード・歌唱難度レンズが全部これを読む。型（`packages/music-core/src/index.ts`）も変えない。

**規則は1行**：
> **句の範囲に重なる音符では、句の読みが正。句の範囲に重ならない音符では、`Note.syllable` が正（従来どおり人が打つ）。**

これで既存の入力口を1つも殺さずに済む：

- `set_lyric`（`mcp.ts:945-957`）＝そのまま。仮歌のかなを載せる道具。
- PianoRoll の「流し込む」欄（`PianoRoll.tsx:262-290`）＝そのまま。
- PianoRoll の詞モード（`PianoRoll.tsx:224-260`・音符1つずつかなを打つ）＝そのまま。**句に覆われた音符でここに打った値は「モーラのかな上書き」として句側に取り込む**（§4-4 の3種目）。曲から潜って開いたときは句側へ、ネタ帳から直接開いたときは従来どおり `syllable` へ書く（後で句に覆われたときにモーラのかな上書きの初期値として取り込む）。
- 詞先メロ生成（`music/generate.ts:737`）＝そのまま。生成したメロを曲に置いて句を作った時点で、その句の表記から読み直される。

**仮歌へ渡す形**：`POST /sing` は **notes（`syllable` 付き）を受ける・ネタ非依存**（`http.ts:746` 実読）なので、句の読みから組み立てた notes を渡せる＝**共有されたメロでも 1番と2番で別の詞を歌わせられる**（保存された `syllable` に縛られない）。今の web は `compositeNotes`（＝保存された content.notes）から組んでいる（`playback.ts:47`）ので、**組み立ての時に句の読みを差し込む口を1つ足す**。埋め草のメリスマはこの時だけ `syllable:"ー"` に直す（`sing.ts:143` が "ー" を母音継続として読む）。

### 4-9. 通しの1本をどう作るか

**並び**＝曲 → その子セクション（`compose_edge.position` 順。position は**拍**＝`sectionContext.ts:92` の是正で確定） → 各セクションの句（開始拍順）。同じ position のときは `ord` 順。

- **まだ曲に置いていないネタの句は通しに出ない。** 出したい下書きは `kind:"lyric"` ネタの側に居る（通しの面には出ない・ネタ帳から開く）。裁定5（合図なければ作られたくない）を守る以上、置いていないものは通しに無い。
- **どのメロが歌詞を持つか、を決める必要は無い。** 句は範囲を持ち、音符は「その範囲に重なるメロレーンの子の音符」として決まる。ハモ（counter）は別レーン＝歌詞の対象にしない（＝歌詞が二重に出ない）。
- 通しの文章＝句の表記を並び順に連結（句と句の隙間は空行）。**句と行は1対1でない**（1句が複数行でも、1文が2句にまたがってもよい）。

### 4-10. 既存データ

実測（`data/cm.sqlite`・全523ネタ）：`syllable` を持つ melody ネタは **4件**（みなそこイントロ／68_melody／Cメロ一回目／二回目）、`kind:"lyric"` は **8件で全部 QA の捨てデータ・content 長0**。

- lyric ネタ8件＝捨ててよい。
- melody ネタ4件＝**機械では表記を復元できない**（かなから「にわ」→「庭」か「二羽」か決められず、しかも入っているのは仮歌用に崩したかな＝「思い**わ**」「だろ**お**」＝元の読みですらない）。**オーナーが句に表記を書く以外に道は無い。**
- **旧 `syllable` は捨てない**：句を作って表記を書いた時点で、旧 `syllable` を**その句の「モーラのかな上書き（仮歌の崩し）」として取り込む**（§4-4）。＝仮歌の崩しが消えない。取り込みの結果が気に入らなければ人が消せる。
- 表記を書くまでは、その音符はどの句にも覆われていない＝従来どおり鳴る（後退ゼロ）。
- **「移行は要らない」とは書かない。** 正しくは「**DBスキーマとマイグレーションは要らない／手で表記を書くのが4件／新しくかなだけのデータが増え続けても壊れない（覆われていない音符は従来どおり）**」。

## §7 オーナーに聞く（推測で埋めなかったもの）
