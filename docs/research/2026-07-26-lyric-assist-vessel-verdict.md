# 作詞補助の「器」の裁定＝A/Bでなく第三の形＋最初の縦スライス（Fable裁定・Opus4.8コード裏取り）

- 日付: 2026-07-26
- 問い: Otomemoに作詞補助をどう作り込むか。(A)既存Otomemo（メロエディタ等）に混ぜ込む / (B)独立した歌詞エディタとして切り出す / どちらでもない第三の形か。＋最初の縦スライス。
- 前提（オーナー確認済み・最上位）: 本人の作詞は「曲先が主」ではない。曲先も詞先も両方あり、1曲の中でセクション単位に方向が反復的に入れ替わる往復作業（Aメロにメロ→詞を当て→2番を作詞→サビ作詞→その詞からメロ…）。

## 0. 前提として確定させた事実（すべてコードで裏取り済み）

器の判断に効く事実を先にコードで確かめた。docと食い違うものが3件見つかった。

- **赤黄ハイライトは配線済み**。`apps/web/src/lyricFit.ts` の `computeLyricHits` が `@cm/music-core` の `analyzeLyricFit` を呼び、`apps/web/src/components/PianoRoll.tsx:5,73` で歌詞チップに fit-red/fit-yellow を重ねている（トグルで消せる）。2026-07-26サーベイの「未配線」は古い転記で誤り。

- **メロエディタの歌詞まわりは想像より完成している**。流し込み（かな入力→`flowLyric`）、詞モード（音符タップ→1音ずつリタッチ→自動で次へ・`apps/web/src/lyrics.ts` の `setSyllable`/`nextNoteIndex`）、整合ハイライト、仮歌楽器（`content.sing`→VOICEVOX）が全部PianoRoll上に揃っている。＝**曲先方向（メロ→詞）の道具は器として既に一式ある**。

- **逆方向＝詞先（詞→メロ）は、エンジンは完成しているのにユーザーが触れるどの器からも到達不能**。これが今回の最重要発見。
  - `gen_melody` の `lyrics` 引数（design #13d・音数厳密一致・`planLyricMelody`＋`genLyricMelodyCandidates`・テスト済み）は `apps/api/src/mcp.ts:741` にあるが、この登録は `if (legacy) {`（mcp.ts:278〜）**の内側**＝chat面（`surface:"chat"`）には登録されない。
  - `apps/api/src/chat-session.ts` の `CHAT_VERB_NAMES`（19〜31行）に `gen_melody` が無い。一方**同ファイル109〜110行のプレイブックは「歌詞先行なら gen_melody を lyrics 引数で呼べ」と常駐Claudeに指示している**＝プロジェクト自身が「過去BUG#1型」と呼ぶ「登録/許可漏れで黙って死ぬ」がそのまま起きている。
  - 既存の機械照合テスト（`apps/api/test/mcp.test.ts:439`「chat面verbs⇔CHAT_VERB_NAMES一致」）は「両方に無い」を整合として通すので検出できない。
  - web側も `lyrics` は `apps/api/src/http.ts` の `/music` gen_melodyルートに無く、`apps/web/src/useMelodyGen.tsx`/`api.ts` にも無い。＝詞先メロは開発用のfull面MCPクライアントからしか呼べない。

- おまけの乖離: design L1決定「lyric content＝{lines:[{text,reading}]}」の `reading` はweb/apiのどこにも実装されていない（歌詞ネタは素のtextarea＋行別モーラ数表示、`KindEditorBody.tsx:332`）。docがコードより先行している例。

つまりオーナーの往復のうち、**曲先の半周は完成済み・詞先の半周は断線**というのが現在地。

## 1. 裁定（一文）

**第三の形＝「新しい画面もデータモデルも作らない。歌詞エディタは『歌詞ネタ（下書きテキスト）＋メロエディタ（syllable編集・既存）＋チャット（言葉の脳）』の三点セットであると定義し、最初の仕事は断線している詞先方向をチャット面に開通させることだ」——Aともいえず、B（切り出し）は棄却。**

「歌詞エディタ」を画面/データ/会話に分解すると、A/Bは偽の二分法になる。
- データとしての歌詞エディタは #13裁定（歌詞×メロの正準は `Note.syllable` 埋め込み・同メロ別歌詞は別ネタ）により**存在してはならない**（独立ドキュメントモデル＝正準の分裂）。
- 画面としての歌詞エディタは、往復がセクション単位で反転する以上**メロのいる場所と同じ画面**でなければ毎往復に切替コストを払う＝既にPianoRollがその画面。
- 会話としての歌詞エディタ＝チャットは、アーキテクチャ上すでに脳の指定席。

よって「作るもの」は器ではなく配線である。実装者に一意に伝わる粒度で言うと: **新規画面ゼロ・新規kindゼロ・新規スキーマゼロ。作るのは (1) chat面への `gen_melody` 登録＋allowlist追加、(2) プレイブック⇔allowlistの契約テスト、の2点だけ**（詳細は §4）。

## 2. 根拠

### 判断基準ごとの採点（B vs 第三の形）

1. 往復1サイクルの手数: B=方向反転のたび画面切替＋対象再選択 / 第三=メロエディタ内で曲先完結・詞先はチャット1往復
2. データ正準(#13)との整合: B=独立歌詞ドキュメントを持ちたくなる＝正準分裂の引力 / 第三=`Note.syllable`＋lyricネタ下書きの現行二重構造そのまま
3. スマホ細切れ時間の到達手数: B=新画面の動線新設が要る / 第三=既存タイル/チャットFABのまま（トップに何も足さない）
4. 脳=チャット/真実源=MCP/web=薄いビュー: B=画面に言い換え・韻・診断が生える圧＝webに脳 / 第三=言葉の生成はClaude・判定はmusic-core/MCP・webは表示のみ
5. 可逆性・保守費: B=画面2系統を恒久に養う / 第三=差分は1動詞の露出＋テスト＝ほぼ無料で引き返せる
6. 「歌詞エディタ」の定義明確性: B=画面と定義した瞬間にデータ問題を裏口で抱える / 第三=画面/データ/会話に分解して各層で答えを固定
7. 作者の手番を構造に挟めるか（サーベイ読了後に追加した基準）: 第三=オーナーがlyricネタ/チャットに先に書き、機械は候補・警告まで＝手番を奪わない

不採用にした基準: 「6本柱のカバレッジ」。柱は汎用ツール市場の需要一致であって、この個人道具の優先度を決める物差しではない（依頼主バイアス4への抵抗として明示的に棄却）。

### 決め手になった3点

1. **ボトルネックは器ではなく断線だとコードが示した。** 「専用の器が要る」仮説を潰しに行った結果、曲先半周は既存の器で完成しており、詞先半周は器がないのではなく配線ミス（chat面未登録＋allowlist漏れ、しかもプレイブックは呼べと書いてある）で死んでいた。新しい部屋を建てる前に、既にある部屋の切れた電線をつなぐのが唯一筋の通った第一手。これで「既存のメロエディタ＋チャット＋sing_netaで足りるか」という潰すべき仮説そのものが、初めて実地検証可能になる。

2. **#13裁定（譜割り一体論）が独立エディタの土台を先回りで殺している。** 独立歌詞エディタの実装価値は「歌詞を独立ドキュメントとして育てる」ことにあるが、このプロジェクトの正準は「歌詞が変われば音符列が変わる＝歌詞はメロに埋め込む」。Bを選ぶことは器の選択ではなく既決データモデルの蒸し返しになる。

3. **トップ画面の負債構造に対し、本裁定は増分ゼロ。** 情報過多の病理は「kind追加のたびタイル＋フィルタが恒久割込み」（[[2026-07-14-topview-inventory]]）。本裁定は新kind・新タイル・新画面を一切足さないので、Aに向けられた「さらに混みあわせる圧」の警告が当たらない。Bは逆に画面と動線の新設費＋実在10件（project内lyric）という薄い利用実態に対して過大投資。

### 依頼主の「潰すべき前提」への回答

1. 専用の器が要る→**未証明。断線修理後の実セッションで初めて判定可能**（逆転条件2へ）。
2. 統合ビュー不在は穴→**今は埋めない**。外部に無いのは需要薄の可能性があり、オーナーの往復にフォーム全体を俯瞰しながら行単位prosodyを詰める作業パスの実在が未確認（確認事項1）。必要になっても読み取り専用レンズ（song_state系）として後から安く足せる＝先送りが可逆。
3. 既存資産が多いからAが安い→**半分誤り・半分正しい**。prosody/モーラ/生成資産はmusic-core/MCP層で器に中立（Bでも使える）。ただし流し込み・詞モード・赤黄・仮歌というUI資産はPianoRoll固有＝実在するA側の重み。Bはこれを複製するか捨てるかを迫られる。
4. 6本柱→器の裁定に効くのは「往復に乗るか」だけ。今回拾ったのは音数割付・アクセント整合（既存）・詞先生成（断線修理）のみ。
5. 「候補まで機械」の器への転用→**しない**。器の判断は基準1〜7で行い、この思想は縦スライスの受け入れ条件（selectしない・赤ゼロ強制しない）にだけ使った。
6. docの現状記述→上記のとおり3件の乖離を実測。

## 3. 逆転条件（これが判明したら裁定を覆す）

1. **オーナーが「歌詞を通しで書く/推敲する長文パス」を主要な作業として持っていた場合**（確認事項1）。セクション往復でなく歌詞全体を一気に書く時間が実在し、そこで行単位モーラ×フォーム俯瞰を同時に見たいなら、B-lite（同一データモデル・別ビューの歌詞画面）が正当化される。
2. **断線修理後の実セッションで、チャット経由の詞先往復が細切れ時間に乗らないと観測された場合**（候補カードがスマホで拾えない・応答待ちがリズムを壊す等）。その場合は次段としてメロエディタ内に詞先入口（歌詞欄→/music経由で候補トレイ）を足す。それでも摩擦が残るなら、そのとき初めて専用画面を再検討する。
3. **「同じメロに複数の歌詞案を並行保持したい」が実需だと判明した場合**（確認事項2）。#13の譜割り一体論が実運用で破れるなら、歌詞は独立エンティティ＋版管理（SongPad型）に倒れ、データモデルごと裁定をやり直す。

## 4. 最初の縦スライス: 「詞先メロをチャットから到達可能にする」

合格線＝実機で、自分の歌詞（lyricネタの下書き or チャット貼り付け）→チャット「この歌詞にメロを」→音数一致の候補→capture→メロエディタで赤黄確認→仮歌で試聴、が通しで一度できる。曲先方向は既に全部通っているので、**このスライスで往復の輪が初めて閉じる**。

- **要件**: 新規追記不要。requirements.md「頼み方」例2「この歌詞があるから、音数に配慮してメロディを3つ作って」が既にこのスライスの要件（未達の実現）。
- **設計**（design.md #13d WP-L1(c) の是正が先）: 記述と実態（chat面未登録）が乖離。designに次を明記してから下ろす——(a) `gen_melody` はchat面にも登録する（legacyブロックの外へ移動。他のgen_*は据置＝chat面の膨張はこの1本だけ）。(b) `CHAT_VERB_NAMES` に `gen_melody` を追加。(c) 再発防止の一般化＝「プレイブック本文が名指しするMCP verbは全てCHAT_VERB_NAMESに含まれる」を契約テスト化。※weaveへの歌詞統合はしない（2026-07-21裁定の維持）。
- **タスク**: 起票「詞先メロ生成をチャット面に開通（#13d出口の断線修理）＋プレイブック⇔allowlist契約テスト」。
- **テスト（赤）**:
  1. `apps/api/test/mcp.test.ts`: 「chat面に gen_melody が登録されている」（`buildMcpServer({surface:"chat"})` のツール列挙に gen_melody を含む）。既存439行の機械照合が「CHAT_VERB_NAMES追加漏れ」を自動で赤にするのでペアで効く。
  2. 同: 「CHAT_VERB_NAMES が gen_melody を含む」。
  3. 新規 `apps/api/test/chat-playbook-verbs.test.ts`: 「プレイブック文字列中の `mcp verb 名`（gen_melody/set_lyric/… の正規表現抽出）⊆ CHAT_VERB_NAMES」＝今回の事故の一般形を恒久検出。
  4. `apps/api/test/lyrics-first-melody.test.ts` 追補: 「chat面サーバ経由で lyrics 付き gen_melody を呼ぶと候補が返り、全候補で音数=計画オンセット数・meta.lyricFit 付き」。
- **コード（触るファイルと契約）**:

  - web・music-core・スキーマ・画面: **変更なし**。
- **新設する契約**: MCPツール/スキーマの新設ゼロ。新設は「プレイブック⇔allowlist包含」というテスト契約のみ。
- スライス2候補（今回はやらない・順序だけ）: lyricネタ画面から「この詞でメロ候補」ワンタップ導線（/musicルートにlyrics追加）→ 実セッション観測後に言い換え候補のMCP化を判断 → 統合ビューは確認事項1の答え待ち。

## 5. 捨てた選択肢

1. **B＝独立歌詞エディタ（専用画面＋独自データモデル）**: #13正準と正面衝突（独立ドキュメント化は正準の分裂）・往復のたび画面切替・ソロ開発で画面2系統を恒久に養う・言い換えや韻の道具が画面に生える＝webに脳が生える圧。実利用もproject内lyric 10件と薄く、投資根拠がない。
2. **「フォーム俯瞰×行単位prosody統合ビュー」を初手の目玉にする案**: サーベイの「穴」アンカーそのもの。誰も作っていないのは需要が薄い可能性があり、オーナーの作業にフォーム全体パスが実在するか未確認。読み取り専用レンズとして後から安く足せるので、先送りしても失うものがない。
3. **「言い換え候補（モーラ数フィルタ付き類語）」を最初の縦スライスにする案**: 3軸一致の最有力柱だが、チャットは今日でもClaudeの語彙力＋`suggest_lyric_rhythm` のモーラ検算で8割回せる。専用ツール化の増分は小さく、器の裁定に影響しない。断線修理後の実セッションで「チャット言い換えが使いものにならない」観測が出てからMCP化を積むのが順序（品質の苦情には真因研究が先、の家訓とも整合）。
   （補足: weaveへの歌詞統合も捨てた——2026-07-21に名前ごと切った偽友の復活になる。）

## 6. オーナー確認事項（最大3件）

1. **歌詞を「通しで」書く/直す時間はあるか**: セクション往復とは別に、歌詞全体を一気に書き下ろす・全番を並べて推敲する作業パスが実在するか。→ Yesなら統合ビュー（読み取りレンズ→将来B-lite）の優先度が上がる（逆転条件1）。
2. **同じメロに複数の歌詞案を並行で持ちたいことがあるか**: #13裁定（同メロ別歌詞＝別メロネタ）で実運用上困った経験の有無。→ Yesなら版管理・独立エンティティの再検討（逆転条件3）。
3. **詞先のとき、歌詞の下書きは今どこに書いているか**（lyricネタ／チャット／外部メモ）。→ lyricネタなら「この詞でメロ候補」ワンタップ導線（スライス2）の価値が確定する。

## 補足: Opus4.8による裏取り（この裁定の linchpin を独立確認）

裁定と「今すぐ実害」の両方の土台＝断線の主張を、Opus4.8が別途コードで確認した（他者所見は過大評価が常態、の家訓に従い）:

- `gen_melody` の登録は `apps/api/src/mcp.ts:741` の1箇所だけで、`if (legacy) {`（278行〜）の内側＝chat面には出てこない（grep で単一登録を確認）。
- `CHAT_VERB_NAMES`（chat-session.ts:19-31）に `gen_melody` は無い。リストには `set_lyric`・`suggest_lyric_rhythm`・`analyze_lyric_fit`・`sing_neta` 等が並び各行に「許可漏れ厳禁＝過去BUG#1型」コメント付き。詞先メロ本体だけが抜けていた。
- プレイブック chat-session.ts:109-110 は「歌詞先行なら gen_melody を lyrics 引数で呼べ」と常駐Claudeに明示指示。

＝呼べと書いてあるツールが許可リストに無い。詞先を頼むと常駐Claudeは黙って失敗するか search に逃げる。[[2026-07-19-creative-agent-field-observation-3]] 系で観測された「作詞ツールが呼ばれない」症状の一因の可能性が高い。**このスライスは器の裁定とは独立に、今日ただちに直す価値のある実バグ**。
