### 批判(spec)

## 1. 裁定3（字余りとメロ途中を分ける）の判定材料が、自分の定義で潰れている

**何が問題か**：区別の土台に据えた「句が占める時間範囲」を §2-2 が「メロがあれば音符から導く」と定めているため、音符がある句では範囲の末尾＝最後の音符の終わりになり、「範囲の末尾まで音符が届いていない」＝メロが途中が永久に成立しない。

**どこか**：§2-2 の表3行目「**占める時間範囲**（開始拍・拍数）｜メロがあれば音符から導く／無ければ人が置く」と、§5 の表2行目「時間範囲があり、その末尾まで音符が届いていない → **メロが途中**」。

**何が起きるか**：v8 枚1 の 9–10小節「鍵をかけて 外に出る」（メロが2小節のうち途中までしか無い句）は、範囲を音符から導く定義では範囲=音符の実在区間になり、そのまま「字余りN」に落ちる。＝裁定3 の前と何も変わらない。実装者は「導く」の意味（音符の実在区間か／句が割り当てられた小節か）を読んで決められない。

**どう直すか**：時間範囲は**音符から導かない**と決める。範囲の出所は「句が置かれた小節（セクション内の位置）」だけにし、音符はその範囲を埋める側とする。範囲を持たない句と持つ句の見分けが §5 の3分岐（メロなし／途中／字余り）を決める唯一の鍵なので、「誰がいつ範囲を書き込むか」を1通りに書き切ること。

## 2. 表記を1文字直すと、人が手で直した読み・高低が全部剥がれる（裁定1の後半が最初の編集で壊れる）

**何が問題か**：§2-2 の1番（札）は**句**の同一性しか守らないのに、§3-2 の上書きは「語の単位」「モーラの単位」で持つと決めており、語番号もモーラ番号も表記を編集した瞬間に全部ずれる。何に貼り付けるかが書かれていない。

**どこか**：§2-2 1番「表記を直しても、その句に付けた手直し・割付が剥がれないため」／§2-2 5番「機械が読み直しても人の直しが消えない」／§3-2「読み…語の単位／イントネーション…モーラの単位」。

**何が起きるか**：v8 枚8 の実例そのもの（「早く」を足すと「窓」の割付が6つ目→9つ目へずれる）が、割付だけでなく**人が直した読みと高低にも起きる**。「今日」の読みを手で直した句に一語足すと、その上書きが別の語に付くか消える。裁定1が名指しした「間違えたら人が手で直せる」が、2回目の編集で無効になる。

**どう直すか**：上書きの貼り先を、句の中の順番ではなく**表記の文字位置＋その語の文字列**のような、編集で壊れたことが検出できる形で持つと決める。壊れたと判定したときに「捨てる」のか「人に確認させる」のかまで書く。§4-3 の「モーラ番号を先に決めておく」も同じ理由で今のままでは成立しない（番号は表記が動けば動く）。

## 3. 人がモーラ単位で高低を反転しても、下流の契約がそれを表現できない

**何が問題か**：§3-2 は「タップで高低を反転」を決定として書いているが、印を出す本体（`analyzeLyricFit`）が受け取れるのは `AccentEntry = {kana, kernel}`＝**語ごとのアクセント型**だけで、途中の1モーラだけ反転した高低は型で表せない。しかも §付 は「#13b の契約本体（1660–1662行）は触らない」と宣言している。

**どこか**：§3-2「イントネーション（高低）…モーラの単位（タップで高低を反転）」／§付「`analyzeLyricFit` の契約本体。**入力源（1658行）だけ直し、規則は触らない**」。

**何が起きるか**（実コードで確認）：`packages/music-core/src/prosody.ts:288-322` の `buildContour` は kernel から高低を**計算し直す**ので、人が直した高低は捨てられる。`apps/api/src/accent.ts:59-70` の `mapAccents` も accent.py が返す `hl`（モーラごとの高低）を読まず kernel だけ拾っている。＝人が手で直した高低の上に、機械が計算し直した高低で赤黄の印が出る。画面のイントネーション表示と印が食い違う。

**どう直すか**：`analyzeLyricFit` の入力に**モーラごとの高低の列**を受ける道を足す（accent.py の `hl` はすでに出ている）。＝§付 の「契約は触らない」は誤りなので、触る節の表に #13b 1660–1662 を足す。

## 4. 表記を打つたびに機械がメロのリズムを書き換える（§2-3 と 決定L2 と §5 の三つ巴）

**何が問題か**：§2-3 は「表記層を持つ句は、`syllable` を毎回、表記からの導出で上書きされる」と決めた。導出の実体は `flowLyric` で、これは モーラ>音符 のとき**音符を半分に割って増やす**（決定L2＝§付 で「変えない」と宣言）。一方 §5 は「機械は詰めない・削らない」と書く。3つが同時には成り立たない。

**どこか**：§2-3「毎回、表記からの導出で上書きされる」／§付「決定L2 の音数合わせの規則…**変えない**」／§5「**機械は詰めない・削らない・止めない。**」

**何が起きるか**：メロが未完成の句に詞を1行打った瞬間、既存の音符が16分まで刻まれて「字余り」が消える。裁定3 で分けようとしていた状態そのものが、入力のたびに自動で消える。逆に音符が余れば `syllable:"ー"` のメリスマが機械的に生える（§5 の「あとN音」と衝突）。

**どう直すか**：導出（表記→読み）と割付（読み→音符）と**音符の作り替え**を3つに分け、音符の作り替えは人が明示的に頼んだときだけ走ると書く。決定L2 は「変えない」ではなく「**呼ばれたときだけ効く規則に格下げ**」と明記する（＝§付 の据置対象から外す）。

## 5. モーラ列の正準が2本ある（`read` を割ったものと、音符に載る `pron`）

**何が問題か**：§3-1 は「モーラの列＝かな1つずつ（**`read` を分割**）」、§2-3 は「音符に載せるかなは **`pron`**」と書いており、どちらが「そのモーラが何番目か」の定義かが決まらない。改訂案自身が「`read` だと外来音で割れるが `pron` なら消える」＝**2つは長さが違いうる**と書いている。

**どこか**：§3-1 の出力2／§2-3「音符に載せるかなは `pron`」／§1-2「かな→モーラの自作分割…を**かな入力専用の道具に用途を限定**する」（にもかかわらず §3-1 は機械が出した `read` をその道具で割る前提）。

**何が起きるか**（実コードで確認）：`buildContour` は渡された `accents[].kana` を `analyzeMoras` で**数え直して**語の長さを決める（prosody.ts:295）。表記から取った語の読みと、音符に載っている `pron` のモーラ数がずれると、高低が1つずれた位置のモーラに付く。しかも §1-5 が指摘した「モーラ総数が合うので null にならず誤った値が通る」と同じ事故の形になる。

**どう直すか**：モーラ列の正準を1本に決め（どちらでもよいが1本）、もう一方は「画面のふりがな」等の用途に限定と書く。§4-3 の「モーラ番号」はこの1本の上で定義する。

## 6. 「歌詞全体を通しで見る」ためのデータが組み立てられない（並び順とどのメロが歌詞を持つかが未定義）

**何が問題か**：§2-1 は表記を**メロディネタの content の中**に置くと決めたが、句を曲の頭から並べる順序も、セクションに複数のメロ子ネタがあるときどれが歌詞を持つ側かも、どこにも書かれていない。

**どこか**：§2-1「歌詞と音符は同じ入れ物に住む」／§2-2「句の表記を改行で連結したものが1本の文章になる」（連結の順序の定義が無い）。design 側の既存前提＝「Section 複数メロ」（#13c・1674行）とハモ/対旋律 kind（counter）。

**何が起きるか**：この道具の最重要要求「書くのは通しではないが**推敲は必ず通しでする**」（事実資料 §2）に対して、通しの1本を作る手順が仕様から出てこない。ハモを1本足すと歌詞が二重に出るか、どちらを採るか実装者が勝手に決めることになる。v8 の「範囲の編集画面」「全部選択」もこの並びの上に載っている。

**どう直すか**：句の並びは「曲→セクション→そのセクションの**歌詞を担うメロ1本**→句の順」と決め、担う1本の決め方（先頭のメロか・印を付けるか）を書く。あわせて、時間範囲を持つ句と持たない句が混ざったときの並び順も決める（今は配列順か開始拍かも未定義）。

## 7. 表記層を持たないデータを作り続ける口が閉じていない＝「移行は要らない」が成り立たない

**何が問題か**：§7-2 は「音符に直接かなを打つ」を PianoRoll の詞モード（224-260行）だけ名指しで殺しているが、**同じことをする口が他に3つ生きている**。

**どこか**：§7-2／§2-4「既存データの移行は**要らない**…melody ネタ4件」。

**何が起きるか**（実コードで確認）：
- MCP `set_lyric`（mcp.ts:945-957）＝かな文字列を受けて `flowLyric` で syllable を書く。説明文も「歌詞(かな)を各音符へ」。
- PianoRoll の「流し込む」欄（PianoRoll.tsx:262-290・`placeholder="かな（読み）を入力→流し込む"`）＝詞モードとは別の入力バーで、こちらは殺す対象に入っていない。
- 詞先メロ生成（generate.ts:762 `genLyricMelodyCandidates`）＝生成した新しいメロネタに syllable だけを書く。表記層を書くとは §3-4 にも書かれていない。

つまり今日以降も「表記層を持たないメロ」が増え続け、「今が一番安いタイミング（手で直すデータが4件で済む）」（§2-4）は成り立たない。またチャットから `set_lyric` を呼ばれた瞬間に、正データが表記とかなの2つになる（§2-3 が禁じた状態）。

**どう直すか**：表記を受け取る口を1つ決め、`set_lyric`・PianoRoll の流し込み欄・詞先メロ生成の3つを**表記を書く側**に付け替える（かな受けは残すなら「表記が無い旧データ専用」と明記）。§7-2 に3つとも列挙する。

## 9. ブラウザから読みに届く口を「新設する」と言っているが、契約がどの節にも無い

**何が問題か**：新しい HTTP の口が要ることは §3-3・§6(b) で認めているのに、design 側の差分（§1）に口の契約が1文字も無い。architecture.md の1行だけが根拠になっている。

**どこか**：§3-3「ブラウザから読みに届く口＝**無い**」／§6(b) 改訂後「**ブラウザから読みに届く HTTP の口を新設する**」／§1 の差分表（該当節が無い）。

**何が起きるか**（実コードで確認）：今の web は `computeLyricHits`（apps/web/src/lyricFit.ts:31）が**ブラウザ内で同期に**印を計算しており、サーバも Python も呼んでいない。表記由来にすると、この面が非同期・ネットワーク依存になる。パス・入出力・1回にまとめる単位（§3-1 は40句一括が要ると実測している）・失敗時（オフライン／spawn 失敗）に何を表示するか・保存した読みの控えをいつ引き直すか（§2-2 4番は「表記が変われば作り直す」と書くが、作り直す**契機**が無い）が全部未定義。加えて控えが2箇所（句が持つ読みと `Note.syllable`）にできるので、食い違ったときどちらを鳴らすか（仮歌は `sing.ts` が syllable を読む）も決まらない。

**どう直すか**：#13e に口の節を1つ足し、パス・1回に渡す単位・返す形・失敗時の見え方・控えを引き直す契機（保存時か開いた時か）を書く。

## 10. 「音符ゼロのメロディネタ」の影響が section 側に降りていない

**何が問題か**：§7-4 は音符ゼロのメロディネタができることをオーナー確認事項にしているが、確認しているのは裁定5（勝手に作らない）だけで、**そのネタが配置面・再生・尺・書き出しでどう振る舞うか**という設計の宿題が書かれていない。

**どこか**：§7-4／§8-4。

**何が起きるか**：4レーンは子の kind でレーンを決める（design 871行）ので、音符ゼロのメロは「メロレーンに空のブロックが載る」ことになる。セクションの尺の計算・再生（`audibleChildren`）・MIDI書き出し・レーンの表示既定（design 409行「中身のあるレーン＋定番4」）が、中身ゼロの子をどう扱うか未定義。裁定4「ゴミが増えるのは嫌なので暗黙の操作はあまり増やさないでほしい」にも触れる（詞だけの区間の数だけネタが増える）が、§7 はこれを別項に立てていない。

**どう直すか**：音符ゼロのメロを「表示はするが再生・書き出しには出ない」等、既存の4レーン契約の言葉で1文決める。裁定4 に触れる点は §7 に別項として立てる。

## 11. 句と音符の被覆規則が無い（どの音符がどの句のものか決まらない）

**何が問題か**：句が時間範囲を持つ／持たないの両方を許し（§2-2 3番・§5 最終行）、範囲どうしが重ならないか・隙間があってよいか・範囲の外にある音符は誰のものかを決めていない。

**どこか**：§2-2 3番／§5 の表／§2-3「表記層を持つ句 → `syllable` は毎回、表記からの導出で上書きされる」。

**何が起きるか**：どの句にも属さない音符が出たとき、その `syllable` は導出で上書きされる側なのか、人が打ってよい側なのか（§7-2 で殺す対象なのか）が決まらない。同じメロの中で「表記層を持つ句の音符」と「持たない音符」が混在し、§2-3 の「持つ／持たない」の二分（ネタ単位のつもりで書かれている）が音符単位では効かない。

**どう直すか**：句の範囲は重ならない・曲の頭から順に並ぶ・範囲外の音符は「どの句にも属さない」と明示し、属さない音符の `syllable` の扱い（メリスマ扱いか、旧来どおり手打ち可か）を1文で決める。

## この改訂案でコードに進んでよいか

**直してから。**

一番の理由＝**裁定3 に答えるための唯一の材料（句の時間範囲）が §2-2 と §5 の間で自己矛盾していて、区別が定義上成立しない**（項目1）。加えて、裁定1 の後半「間違えたら人が手で直せる」も、貼り先が未定義（項目2）＋下流の契約が高低の反転を表現できない（項目3）で、書いてあるとおりには実装できない。この3つは新しい調査ではなく**この文書の中の書き直しで閉じられる**ので、閉じてから着手すれば足りる。

なお、§2-4 の移行の事実関係は実データで裏が取れた（DB実測＝`syllable` を持つネタ4件＝みなそこイントロ／68_melody／Cメロ一回目／二回目、`kind:"lyric"` 8件はすべて QA の捨てデータで content 長0）。ただし §2-4 の「移行は要らない」という言い方は、同じ節が「オーナーが手で表記を書き直す以外に道は無い」と書いていることと項目7（表記なしデータを作り続ける口が開いている）の両方から**言い過ぎ**なので、「手作業4件＋新規に作らせない口の付け替え」と書き換えるべき。

### 批判(owner)

## 1. 句の切れ目と並びをデータが持っていない（範囲の指し方が無い・以下3件の共通の根）

**何が問題か**：句がどこからどこまでかを、案は「メロディネタの中の配列の順番」と「音符から導く」でしか表しておらず、ネタをまたぐ範囲も、句の終わりも表せない。

**改訂案のどこか**：§2-1「置き場＝melody ネタの `content.lyric = { phrases: [句,…] }`」／§2-2 の3「占める時間範囲＝メロがあれば音符から導く」／§4-3「最初はこの番号を保存しない（省略＝頭から順に1対1）」。

**何が起きるか**：オーナー発言「往復はSection単位なんて言ったっけ？ **どこでも開くのが正しい**」「穴は最小1単語から、大きければ曲全体が斑」に対し、v8の範囲バー（◀のばす／のばす▶）と「全部選択」が指せる範囲は、この案では**1つのメロディネタの中に閉じた連続する句**だけになる。Aメロ末尾からBメロ頭にまたがる範囲、セクションをまたぐ範囲、曲全体は、データ上「そういうもの」として指せない。さらに句の終わりを音符から導くと、句が音符を頭から食う順で決まるので、**句の境界＝直前の句のモーラ数**になり、表記を1文字足すだけで後ろの全句の境界が動く。

**どう直すか**：句が自分の終わりを自分で持つ（人が置いた範囲か、保存された割付のどちらか）ことと、範囲を「(ネタ, 句)の列」で表せることを design に書く。裁定2「最初は取り扱わなくて良い」が先送りにしたのは**割付を手でずらす操作**であって、句の境界をデータに持たないことまでは許していない。

## 2. 「歌詞の正データ＝普通の文章」が、1本の文章として存在しない

**何が問題か**：正データが N 個のメロディネタに散った断片の配列で、通しの文章は毎回の再構成物になる。

**改訂案のどこか**：§2-2 末尾「句の表記を改行で連結したものが1本の文章になる形で満たす」／§2-1「歌詞と音符は同じ入れ物に住む」。

**何が起きるか**：オーナー「**書くのは通しではない。ただし推敲は必ず通しでする**」「音韻のチェックとかする以上、**現状の歌詞全体はみえるべき**」。連結の順序は `compose_edge` の position/ord に依存するので、**まだ曲に置いていないネタの句は通しに出ない**。裁定5「実体を明確に作る合図なければ作られたくない」を守る以上、置いていない断片は普通に存在する。加えて「1句＝1行」を暗黙に強制しているので、1文が2句にまたがる書き方（普通の文章では当たり前）と、連の区切り（空行）が表せない。推敲の(i)意味・(ii)感情遷移は人が通しで読む作業なので、読める1本が無いことが直接効く。

**どう直すか**：通しの1本を何から作るか（順序の出どころ・未配置の句の扱い・句と行と文の関係）を design に書く。句と行を1対1に固定しない。

---

## 3. 裁定3（字余りとメロ途中の区別）が、この持ち方では最後の句にしか出せない

**何が問題か**：§5の表は句の時間範囲を前提にしているが、その範囲を音符から導く（§2-2の3）ので定義が循環し、途中の句は常に「ぴったり嵌っている」ことになる。

**改訂案のどこか**：§5の表全体／§2-2 の3／§4-3「省略＝頭から順に1対1」。

**何が起きるか**：割付が保存されず頭から順に1対1なら、句1がモーラ数ぶんの音符を食い、句2はその続きから食う。**モーラが余るのは必ず最後の句だけ**で、途中の句は「音符が範囲を埋めていて、モーラが余る＝字余りN」に絶対に該当しない。v8枚1の9–10小節「鍵をかけて 外に出る」（途中の句でメロが途中）はどうやっても言い分けられず、不足は末尾の句に押し出される（v8枚8で「窓」が6つ目→9つ目にずれた現象と同じ）。§7-3は「時間範囲を持たない句では分けられない」と限界を書いているが、**実際は時間範囲を音符から導く句でも分けられない**＝限界を過小に書いている。

**どう直すか**：句が自分の終わり（範囲か割付）を持つことを、裁定3を実装する前提として先に決める。この1点は「最初は作らない」で逃げられない。

## 4. 人が手で直した分が、表記を1文字直した瞬間に別の語に付く

**何が問題か**：上書きの宛先が、表記から作り直すたびに振り直される並び順の番号しかない。

**改訂案のどこか**：§2-2 の5「人が手で直した分（＋出所）」／§2-2 の4「表記が変われば作り直す」／§3-2「読み…語の単位／イントネーション…モーラの単位」。

**何が起きるか**：「今日は雨」の「雨」の読みを直したあとに「今日は**きっと**雨」と足すと、語の3番目は「雨」ではなく「きっと」になる。＝直した値が別の語に貼り付く。札（id）は句にしか無く（§2-2 の1）、語とモーラには何も無い。裁定1の後半「読みやイントネーション間違えるなら手で直せる」は、**直したものが残ること**まで含むはずで、推敲で表記を触り続けるオーナーの作り方では、この壊れ方が常態になる。

**どう直すか**：上書きの宛先を、直した時点の表記の文字位置＋その時の表記文字列で持ち、表記が変わったら「付け直せた／付け直せず外した」を人に見せる、といった形を design に書く。

## 5. 機械が黙ってメロを書き換える経路が残っている（案の中で矛盾している）

**何が問題か**：§5が「機械は詰めない・削らない・止めない」と書く一方、付記が決定L2（モーラが多い＝一番長い音符を半分に割る）を「変えない」と明示し、§2-3が「表記層を持つ句は毎回、表記からの導出で上書きされる」と書いている。

**改訂案のどこか**：§2-3／§5 末尾／付「決定L2 の音数合わせの規則…変えない」。

**何が起きるか**：3つを合わせると、**表記を1文字打つたびに音符が半分に割られる**（`flowLyric` は現に音符を分割する＝`apps/api/src/lyric.ts:43-59`・`apps/web/src/lyrics.ts` の2本とも）。人が作ったメロが打鍵で変わる。裁定4「暗黙の操作はあまり増やさないでほしい」と、原文「作る努力の部分を人間から奪うと自作感がなくなるので、**最後に選ぶのは人間**」に当たる。しかも裁定3で「字余りN」と言う設計は、機械が字余りを自動で解消しないことが前提なので、L2の自動分割とそもそも両立しない。

**どう直すか**：表記編集時の再導出は `syllable` の割り直しだけ（音符数は動かさない）と明記し、L2の音符分割は人が「流し込む」を押したときに限る、と design に書く。これは付記の「決定L2は変えない」を実質的に変えるので、別項に立てて理由を書く必要がある。

## 6. 「詞もメロも無い区間」と「1語の穴」の置き場が無い

**何が問題か**：句は表記＝1本の文字列で、穴を表す言葉が無い。ネタが無い区間には何も置けない。

**改訂案のどこか**：§2-2 の2「表記（漢字仮名交じりの文字列）」／§7-4「音符ゼロのメロディネタができる」。

**何が起きるか**：オーナー「**詞もメロも両方とも空白の区間が普通にある**」「z だけ無い／z の後ろ半分が無い／z の中の単語1個が無い」。§7-4 は「詞だけあってメロが無い区間」を音符ゼロのメロディネタで受けているが、**詞も無い区間はそれでも受からない**（置き場が melody ネタしか無いのに、作る合図が無い＝裁定5）。v8枚12の27–28小節「詞もメロも無い区間」に対応するデータが案のどこにも無い。句の中の1語の穴も、表記にどう書くか（空欄記号か空白か）が未定義で、**穴を含む表記をそのまま pyopenjtalk に渡すと読みも句切れも崩れる**（かな書きで崩れることは事実資料で実測済み＝同じ性質）。

**どう直すか**：穴を表記の中でどう持つか（穴も札を持つ要素として持つのか、文字列に印を入れるのか）と、穴を含む表記を読みに渡すときにどう扱うかを決める。詞もメロも無い区間の置き場は、melody ネタに寄せる方針そのものの再検討になる。

## 7. 人が書く層（意味メモ・予定）だけが保存されない

**何が問題か**：§2-2 は「句が持つもの（6つ）」と閉じた列挙で、意味（言いたいこと）と予定（音数・小節数・アクセントの枠）が入っていない。

**改訂案のどこか**：§2-2 の表（6項目）／§6「反していない」の確認範囲。

**何が起きるか**：v6欠陥17（意味欄に出所が無い）→ v8で「自分で書く欄（機械は書かない）」として全編集画面に載った欄が、データ側に置き場を持たない。裁定6「予定の当ては両方あると良いしオプショナルで必須にしない」も同じ。とくにオーナーが名指しした意味側からの入口＝「**ここに『通り過ぎる』という言葉で、3文字、このアクセント**」は、メロがまだ無い場所に音数とアクセントの枠を置く話で、v6欠陥10・v8統合報告で「半分後退」と判定された当の項目。この案でも置き場が無く、**同じ穴が3周目に入る**。

なお「機械が踏み込んでよいのは音韻とイントネーションまで」に反する仕組みは、案の中には見つからなかった。問題は逆で、**機械が触らないと決めた層（意味）だけが保存先を持っていない**。

**どう直すか**：6つに足すか、「別スライスで決める・この改訂では触らない」と design に明記する（黙って落とすと再発する）。

## 8. 句読点のある普通の文章で、語とモーラの対応が全句で作れなくなる（実測）

**何が問題か**：§3-1 の整合検査が、読点・句点を含む文で必ず落ちる。

**改訂案のどこか**：§3-1「各語で『`read` の分割数 ＝ モーラ数』」「満たさない句は対応を作らない＝光らせないだけ」。

**何が起きるか**：`run_frontend` は読点を1語として返し、`read:"、"` `mora_size:0` になる（この場で実測：「思い出は、通り過ぎる」→ `{"string":"、","read":"、","pron":"、","mora_size":0}`）。`read` を割ると1、モーラ数は0で不一致。裁定1の正データは**句読点のある普通の文章**なので、これは例外ではなく常態。結果、v8枚5の「『飲ん』をタップすると対応するモーラが光る」も、枚8の「『窓』の光りがずれ先を示す」も、句読点が1つ入った途端に出なくなる。

**どう直すか**：品詞が記号の語をモーラ0の語として対応から外す、と検査の規則に書く。

## 9. 「ー」が2つの意味を持ち、数え分けができなくなる

**何が問題か**：音符に載せるかなを `pron` にすると長音が「ー」で入るが、「ー」は既にメリスマの印として予約済み。

**改訂案のどこか**：§2-3「音符に載せるかなは `pron`」／付「決定L2…余りは `syllable:"ー"` のメリスマ…変えない」／§8-1（「っ」「ー」に音符を立てるかの質問）。

**何が起きるか**：実測で「通り過ぎる」の `pron` は「トーリスギル」。一方 `flowLyric` は余った音符に "ー" を詰め、`sing.ts:143` は `syllable === "ー"` をメリスマ（lyric 空＝母音継続）として扱う。**導出された長音モーラなのか、モーラが足りず詰めた埋め草なのかがデータ上区別できない**ので、裁定3の「字余りN／あとN音」の数えが「ー」の入った句で狂う。§8-1で「ーに音符を立てるか」を聞いているが、どちらに答えてもこの取り違えは残る。

**どう直すか**：長音モーラと余り音符の埋め草を別の書き方にする（埋め草は割付側だけに持ち、`syllable` に混ぜない）。

## 10. 今できることが、代わりができる前に消える

**何が問題か**：詞モードの無効化と、代わりの手直しの実装順が書かれていない。

**改訂案のどこか**：§7-2「詞モードは表記層を持つ句では無効にする」／§1-2 の段階「LS4 表記層 → LS5 割付の手直し／自動符割り（将来）」。

**何が起きるか**：§2-4 が自ら書いているとおり、既存4件の `syllable` は「思い**わ**」「だろ**お**」＝**仮歌のために人が手で打ったかな**。裁定1も「かながきは仮歌のためにある」と言っている。LS4 で表記層が入った時点で音符ごとの手打ちが無効になり、割付の手直しは LS5（将来）。その間、**仮歌のかなを人が直す手段がゼロになる**期間ができる。読みの手直し（§3-2）が LS4 に含まれるのかも書かれていない。

**どう直すか**：無効化は「語の読みの手直しが動いてから」と順序を明記する。

## 11. 同じメロを1番と2番で使い回している場合の扱いが無い

**何が問題か**：メロディネタは複数箇所に置ける（実コード：`compose_edge` は子の使い回しが前提、`placementCount>=2` で共有と判定し、web に共有時の確認ゲート `apps/web/src/useCowGuard.ts` がある）。歌詞を melody ネタに入れると、共有されたメロは歌詞を1つしか持てない。

**改訂案のどこか**：§2-1「置き場を melody ネタにする理由＝譜割り一体論を壊さないため」／§1-4「同じ音・違う歌詞は別のメロディネタ」。

**何が起きるか**：1番Aと2番Aで同じネタを置いている曲では、2番の詞を書いた瞬間に1番の詞が変わるか、**歌詞を打つたびに分家するかの確認が出る**。裁定4「ゴミが増えるのは嫌なので暗黙の操作はあまり増やさないでほしい」に当たる。v8枚1の「同じメロ:」チップと裁定6（1番2番の突き合わせ）もここに乗るのに、案はこの点にまったく触れていない。

**どう直すか**：歌詞を書いた時点で分家するのか、共有のまま置き場ごとに歌詞を持つのかを決めて design に書く（後者は §2-1 の理由付けと衝突するので、衝突を明示して裁定を仰ぐ）。

## 12. 下書きの歌詞ネタと表記層の二重持ち（往復すると必ず起きる）

**何が問題か**：写した後、同じ詞が2箇所にある状態の扱いが決まっていない。

**改訂案のどこか**：§1-3「lyric ネタは…メロディネタの表記層へ写す」／§1-4「メロと出会った時点で表記層へ表記のまま写す」／§8-3。

**何が起きるか**：オーナー「曲先と詞先が**1曲の中で往復する**」。写したあとも下書き側は残るので、詞を直す場所が2つになる。裁定1「正データは1つ」に反する状態を、道具が作れてしまう。§8-3 は歌詞ネタの「行き先」を聞いているが、**写した後の重複をどちらが正とするか**は聞いていない。

**どう直すか**：写したら下書き側を参照だけにする／写しは切り離すが画面で「写し元」を出す、等を決めてから聞く。

## 軽微

- **§1-2 の改訂後で `splitMora` を「かな入力専用の道具に用途を限定する」と書きながら、§3-1 の出力2で `read` を1モーラずつ割るのに同じ道具を使う**（§4-2 は「web と api に2本ある、両方直す」と書いている）。「限定」ではなく「漢字を含む文字列に渡さない」と書くのが実態に合う。
- **§3-1 が pyopenjtalk に渡す単位を「句の表記」としているが、§2-2 は正データを「連結した1本の文章」としている**。渡す単位が読みを変えうることは事実資料に実測がある（「にわへ」と「庭へ」）。句で渡すか文で渡すかを規則として書き、書いた側の実測を残すこと（今回、句と文で高低が変わる例は手元の8組では出なかった＝安全とも危険とも言えない）。

## この改訂案でコードに進んでよいか

**直してから。** 一番の理由は §1・§3 の根＝**句が自分の切れ目（終わり）をデータに持たず、音符から導く循環になっている**こと。これがあるために、「どこでも開く」（範囲がネタと句をまたげない）も、裁定3（字余りとメロ途中の区別が最後の句にしか出せない）も、通しの推敲（1本の文章が存在しない）も、同じ場所で成立しなくなる。裁定2が先送りにしたのは割付を手でずらす**操作**であって、句の切れ目を**持たない**ことではないので、この1点だけは実装前に決着させる必要がある。

### 批判(reality)

## 1. `content.lyric` は web の自動保存で消える（最重）

**何が問題か**：`neta.content` は zod 素通しだが、web のネタ編集は content を**キー決め打ちで作り直す**ので、表記層は保存のたびに落ちる。

**改訂案のどこか**：§2-1「melody ネタの `content` に歌詞層を足す。**DBスキーマ変更もマイグレーションも不要**（`neta.content` は JSON 文字列・zod は `content: z.unknown()`＝検証も剥ぎ取りも無い・実測）」。

**何が起きるか**：zod の観察（`apps/api/src/schemas.ts:16`）は正しいが、保存経路の実体は違う。

```
apps/web/src/useNetaEditor.ts:334
  if (isMelody || isBass || isCounter || isRiff) return { content: { notes, program, ...singContent(), ...(feel ? { feel } : {}) }, key, mode, ... };
```

これが `fullPatch()`（`useNetaEditor.ts:430`）に入り、**デバウンス自動保存**で PATCH される（同 435-437 のコメント「明示『保存』は廃止。編集で patch が変わったらデバウンスで PATCH」）。つまり**ピアノロールで音符を1つ動かした数秒後に `content.lyric` が消える**。明示保存が無いので気づく機会も無い。`feel` が同じ理由で落ちていた前例が同ファイル147行のコメントに残っている（「savePatch が … feel を落とす非対称バグの根治」）。

**どう直すか**：§2-1 を「DB とスキーマは不要。ただし `useNetaEditor.ts:334` の melody 分岐に lyric を透過させることが必須（`feel`/`sing` と同じ扱い）」に書き換え、#13e に明記。テストは「notes を編集して保存 → lyric が残る」を先に赤で書く。

## 2. §5 の5つの状態は、決定L2（`flowLyric`）が生きている限り一つも観測できない

**何が問題か**：`flowLyric` は音符数とモーラ数を**必ず一致させてしまう**ので、「字余りN」「あとN音」「音符に載っていないモーラN」という状態がデータ上に存在しない。

**改訂案のどこか**：付「決定L2 の音数合わせの規則（801–803行）＝多い＝一番長い音符を半分に割る／少ない＝余りは `syllable:"ー"` のメリスマ／下限16分。**変えない。**」と、§5 の状態表。

**何が起きるか**：`apps/api/src/lyric.ts:42-61`（web は `apps/web/src/lyrics.ts:40-63`・同一実装）が、

- モーラ > 音符 → 16分に達するまで**最長音符を割って枠を増やす**（42-55行）
- それでも余ったら → **残りモーラ全部を最後の音符の syllable に連結**（58-61行）

**どう直すか**：§4-1 の「段を分ける」を強い形に書き直す＝「割付は notes を一切変えない（分割もメリスマ埋めもしない）。L2 の自動音数合わせは、割付から切り離した**任意の操作**へ格下げする」。そして付の「決定L2 は変えない」は撤回する（オーナー裁定ではなく設計決定なので上書きできるが、撤回すると明示すること）。

## 3. 「音符に載せるかなは `pron`」は、`pron` が素のかなではないので成立しない

**何が問題か**：`pron` にはアクセント記号「’」が混ざる。実測で歌詞行15本中**8本**が該当。

**改訂案のどこか**：§2-3「音符に載せるかなは **`pron`**（発音・「は→ワ」「通り過ぎる→トーリスギル」）…**TSのモーラ分割と食い違わない（実測：`read` だと外来音で割れるが `pron` なら消える）**」。

**何が起きるか**（`apps/audio/.venv/bin/python` で `pyopenjtalk.run_frontend` を実測）：

| 表記 | read | pron | mora_size | splitMora(pron) |
|---|---|---|---|---|
| のばし | ノバシ | **ノバシ’** | 3 | 4 |
| 聞こえ | キコエ | **キ’コエ** | 3 | 4 |
| 靴 | クツ | **ク’ツ** | 2 | 3 |
| 光っ | ヒカッ | **ヒ’カッ** | 3 | 4 |
| 明日 | アシタ | **アシ’タ** | 3 | 4 |

15行中8行で発生。`read` は素のカタカナなので、この記号は `pron` 固有。そのまま `Note.syllable` に載せると音符に「’」が表示され（`PianoRoll.tsx:423`）、`sing.ts:141-148` 経由で VOICEVOX の lyric にも「’」が渡る。

さらに、括弧内の「実測」は**逆**：「フュージョン」は read も pron も `フュージョン` で `mora_size=5`、`splitMora` は 4（`フュ|ー|ジョ|ン`）。音素列は `f-u / y-u / u / j-o / N` ＝ openjtalk は「フュ」を2モーラと数えるので、**read でも pron でも食い違う**。`pron` にすれば消える、という根拠は成り立たない。

**どう直すか**：(a) `pron` を使うなら「’」除去を規則として書く。(b) より安全なのは、モーラかな列を `splitMora(read/pron)` で作らないこと＝`accent.py` が既に音素から畳んでいるモーラ列（`extract()` の `moras`）を、語の `mora_size` で切る。実測で `sum(mora_size) == mora_total` は試した全例（記号・数字・英字・外来語・促音・撥音を含む）で一致した。ローマ字→かなの対応表が要る、と #13e に書く。

## 4. §3-1 の整合検査3を門番にすると、スペース入りの行がほぼ全部落ちる

**何が問題か**：run_frontend は半角スペースを全角「　」に正規化して返すので、「語の表層文字列を連結＝渡した表記」は普通の歌詞行でほぼ成立しない。

**改訂案のどこか**：§3-1「**取り出す整合の検査**（満たさない句は対応を作らない＝光らせないだけで、読みは出す）… 語の表層文字列を連結したもの ＝ 渡した表記（全角化・「10時→十時」の正規化で食い違う場合がある＝実測）」。

**何が起きるか**：実測15行のうち**11行**が不一致。原因は全部「半角スペース → `\u3000`」。

```
'沈みゆく この体'      → 表層連結 '沈みゆく\u3000この体'
'鍵をかけて 外に出る'  → '鍵をかけて\u3000外に出る'
'雨の日は 傘をさして'  → '雨の日は\u3000傘をさして'
```

数字も同様（`'1000年後の君へ'` → `'千年後の君へ'`）、英字も同様（`'Tokyo'` → `'Ｔｏｋｙｏ'`）。改訂案どおり門番にすると、**v6/v8 のダミー歌詞のほぼ全行で語↔モーラ対応が作られない**＝裁定1（間違えたら手で直せる）と v8 枚5 の「語をタップで光る」が実データでは死ぬ。設計は「食い違う場合がある」と軽く書いているが、実測は「ほぼ毎行」。

**どう直すか**：検査3を門番から外す。突合は表層の一致ではなく、`mora_size == 0` の語（空白・句読点）を飛ばしたうえで**正規化後の表層で位置合わせ**する、と規則を書く。数字・英字のように表記と表層の文字数が変わる語は「対応を粗く持つ（語全体↔モーラ区間）」で十分（文字単位は元から採らない方針なので矛盾しない）。

## この改訂案でコードに進んでよいか

**直してから。** 一番の理由は項目2＝**§5 の状態表がそのままでは一つも計算できない**こと。`flowLyric` が音符を割り、余りを連結し、余った音符を「ー」で埋めるので、流し込み後は必ず モーラ数 = 音符数 になる。付が「決定L2 は変えない」と明言している以上、この改訂案どおりに作ると裁定3（「字余り」と「メロが途中」を分ける）は**画面に一度も出ない**。次いで項目1（自動保存で表記層が消える＝裁定1の土台ごと消える）、項目3・4（pron の「’」混入とスペース正規化で、語↔モーラ対応が実データのほぼ全行で作られない＝「手で直せる」が効かない）。この4点を潰せば残りは実装中に直せる粒度。
