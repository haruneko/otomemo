# 作詞補助UI 既存アプリ当て込みメモ（モック前調査・Step 2）

- 日付: 2026-07-27
- 位置づけ: ゴール「既存アプリと統合した際のイメージがつく程度のUIの絵を数枚」への Step 2。既存WebアプリのUI実態を調べ、入口・再利用・新規・データの痛点を整理する。**設計の確定ではない＝絵を描くための土台**。物差しはオーナー。
- 調査体制: UI構造調査＝Sonnet（Exploreエージェント）／負荷のかかる主張3点の実コード裏取り＝Sonnet 5（セッション本体）。
- 前提の裁定（オーナー・2026-07-27）: 双方空白の表現＝**B案（句＋予定マーク）**／意味と音の入口＝**B案（二欄並置）**／候補の並べ方＝**A（適合度順）とB（事実区分のみ）を両方描いて絵で比べる**。

---

## 1. 既存アプリの器の実態

- **ルーターなしの単一ページ状態機械**。`apps/web/src/App.tsx` が唯一のトップで、`active`/`projectView`/`chatOpen` 等の useState でメインペーンの中身を差し替える。URLページは存在しない。**新画面＝新ルートではなく「activeの新分岐 or 新しい画面状態」として足す**のが既存の作法。
- **モバイルは 820px 境界の1画面切替**。`useIsMobile.ts`（matchMedia 820px）＋ `workspace` への `mv-home`（一覧が主役）/`mv-pane`（編集が主役）クラス切替で、スマホでは常にどちらか1枚。モバイル編集中はヘッダを隠し、エディタ側の「← 戻る」で戻る。**新UIもこの作法（全体画面=mv-home相当、穴の編集=mv-pane相当）に乗せると导線が既存と同型になる**。
- オーバーレイ系: チャット（右下FAB・ネタの「相談」・プロジェクト起点入力の3入口）、受け取りトレイ、作成の棚（ボトムシート `cm-sheet`）、絞り込み引き出し。
- 階層: Project ⊃ Song(`kind:"song"`) ⊃ Section(`kind:"section"`) ⊃ leaf（melody等）。`SectionEditor` がレーン×小節の配置タイムライン。

## 2. 歌詞まわりの現状（裏取り済み）

- **歌詞はアプリ内で2箇所に分裂しており、橋が無い**:
  1. **歌詞ネタ**（`kind:"lyric"`）＝プレーンテキスト＋行モーラ数パネルのみ（`KindEditorBody.tsx:330-341`）。音符との対応・ハイライト・穴の概念なし。
  2. **メロネタの `Note.syllable`**（design #13）＝PianoRoll内でのみ編集可（詞モード=1音ずつフォーカス送りのリタッチバー `PianoRoll.tsx:226-260`・流し込み `lyrics.ts flowLyric`・赤黄ハイライト `lyricFit.ts`→`analyzeLyricFit`・仮歌再生 `playback.ts`+VOICEVOX）。
- **セクションのレーン定義に歌詞レーンは無い**（`sectionLanes.ts:13-24`＝コード/骨格/メロ/対旋律/コード楽器×2/リフ/管弦/ベース/リズムのみ。裏取り済み）。歌詞ネタは曲構造（placeChild）に配置されない＝**「まだ音の無い詞」を曲内の位置付きで持つ場所が現状どこにも無い**。
- 曲全体のツリーは `api.getComposition(id)` で再帰一括取得できる（`api.ts:392`。裏取り済み）。**歌詞全体ビューは「compositionツリーを歩いて各melodyの `notes[].syllable` を集約する射影」で作れる見込み**だが、その集約ロジックはUI側に皆無＝新規。

## 3. C-8痛点の具体化（工数材料・要求は削らない）

要求C-8「現状の歌詞全体が穴も含めて見える」に対し、現状データで**見えるもの／見えないもの**:

| 状態 | 現状データでの置き場 | 全体ビューに出せるか |
|---|---|---|
| 詞も音もある | melodyの `Note.syllable` | ○（composition射影で出る） |
| 音はあるが詞が無い | syllable空のNote | ○（音数分の空き枠として導出可） |
| **詞はあるが音が無い** | 歌詞ネタのtext（曲構造の外） | **×（曲内の位置を持たない）** |
| 双方空白（予定マーク） | 存在しない | **×（新規データが要る）** |

＝設計B案の「句」構造（句が詞側/メロ側の対を持つ）と「予定マーク」は、**どちらも新しいデータの置き場を要求する**。design #13（歌詞はNote埋め込み）を壊さずに足すなら「句＝セクション配下の軽い並び（詞テキスト＋対応するメロ範囲への参照＋予定マーク）」を新設し、syllableは正のまま射影で突き合わせる形が候補。ここは**案が固まった後の設計判断**であり本メモでは決めない。

## 4. 入口の当て込み（絵に直結する選択）

既存の作法に沿う入口候補:

- **(a) 曲（songネタ）から開く**: SectionEditor（曲の配置画面）に「歌詞」ボタン→歌詞全体画面へ。「曲の姿の一つとして歌詞面がある」という位置づけ。曲⊃セクション構造をそのまま句の骨組みに使える。
- **(b) ホーム/一覧から独立に開く**: HomeHub か作成の棚（`CreateShelf.tsx:38` に「歌詞」タイル既存）から。「作詞の作業場」を曲と対等な入口にする位置づけ。
- **(c) 歌詞ネタ（lyric kind）を開いたら新画面**: 既存の歌詞ネタtextareaを置き換え/拡張する位置づけ。ただし歌詞ネタは曲と紐付かないため、全体画面の「曲のセクション構造」が取れない＝単体では成立しにくい。

## 5. 再利用できる部品（モックに反映する既存資産）

| 新UIの要素 | 再利用元 |
|---|---|
| 穴の編集＝1箇所ずつフォーカス送り | PianoRoll詞モードの固定リタッチバー（IME保持・確定→次） |
| 候補一覧のモーダル/シート | `FormSuggest.tsx`（候補列挙→選択→適用のViewステートマシン）・`cm-sheet` ボトムシート |
| 音韻・イントネーションの印 | `analyzeLyricFit`（music-core）＋`lyricFit.ts` の赤黄クラス付与 |
| モーラ数の計測・表示 | `splitMora`/`moraLines`（`lyrics.ts`）＋歌詞ネタのモーラパネル |
| 仮歌・再生 | `TransportBar` ＋ `playback.ts` の sing（VOICEVOX）経路 |
| AI候補の受け渡し | Chatの `ChatToolCard`（candidate＝試聴して保存）パターン |
| 一覧カード・ミニプレビュー | `NetaCard`/`MiniRoll` |

## 6. 新規実装が要る領域（絵では新規と分かるように描く）

1. composition射影による歌詞全体ビュー（集約ロジック皆無）
2. 「句」構造＋予定マーク（データ新設。§3）
3. 穴の導出（空き連続範囲の計算）
4. 枠検索（意味＋音数＋アクセント→言い方の列挙）＝**語彙資源ごと存在しない**（HANDOFF実測どおり収束側の道具は空白）
5. 歌詞ネタ⇄メロsyllableの橋（現状完全独立）

## 7. Step 3（絵）の計画

スマホ幅（820px未満・mv-home/mv-pane同型の1画面切替）の静的HTMLモックを5枚:

1. **歌詞全体画面**＝句の縦並び・穴4状態（詞音両有/詞のみ/音のみ=音数分空き枠/予定マーク）・ダミー詞
2. **穴の編集画面（候補=適合度順版）**＝前後固定表示＋意味欄/音の枠欄の二欄並置
3. **同（候補=事実区分版）**＝並べ方だけ差し替え（オーナーが絵で比べる用）
4. **推敲の表示切替**＝素/音韻/イントネーションの3態
5. **既存アプリ内の導線**＝入口（§4の裁定結果）から全体画面までの遷移図

描き手＝Sonnet（機械的作画）。骨格が要求と衝突する疑いが出た場合のみFable監査を提案。
